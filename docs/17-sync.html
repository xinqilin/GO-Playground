sync 與 data race

好幾個店員共用同一本帳簿，沒有規矩，帳一定會記錯。Mutex 是帳簿旁邊唯一的那支筆，拿到筆的人才能寫；atomic 是按一下就完成的計數器，不會按到一半。

1. data race

好幾個 goroutine 同時存取同一個變數，其中至少一個在寫，而且彼此之間沒有任何同步，這就是 data race。最常見的就是一起做 served++：它看起來是一個動作，其實是「讀出來、加一、寫回去」三步。把兩個店員交錯執行的步驟一行一行排出來：

func lostUpdateDemo() {
	served := 5
	a := served    // 店員 A 讀到 5
	b := served    // 店員 B 也讀到 5
	served = a + 1 // A 寫回 6
	served = b + 1 // B 也寫回 6
	fmt.Println("兩個店員各記一份，結果是", served)
}

輸出

兩個店員各記一份，結果是 6

真的讓 10 個 goroutine 各做 1000 次 served++，這個程式故意寫錯，放在沒有測試的子資料夾裡：

func main() {
	served := 0
	var wg sync.WaitGroup
	for range 10 {
		wg.Go(func() {
			for range 1000 {
				served++ // data race：好幾個 goroutine 同時讀寫 served
			}
		})
	}
	wg.Wait()
	fmt.Println("賣出", served, "份（應該是 10000）")
}

執行五次

賣出 8550 份（應該是 10000）
賣出 6761 份（應該是 10000）
賣出 10000 份（應該是 10000）
賣出 7979 份（應該是 10000）
賣出 10000 份（應該是 10000）

每次結果都不一樣，有時候還剛好是對的。這正是 data race 可怕的地方：在你的電腦上測十次都過，上線之後才偶爾算錯。而且不只是少算：Go 的記憶體模型說，slice、string、interface 這種由好幾個欄位組成的值，被同時讀寫時可能讀到拼湊出來的內容，進一步讓記憶體損壞、程式當掉。

Go 內建了 race detector。在 go run、go build、go test 後面加上 -race，程式執行時會記錄每一次記憶體存取，一抓到沒有同步的同時存取就印出報告：

go run -race ./chapters/17-sync/race
==================

  main.main.func1()
      …/chapters/17-sync/race/main.go:21 +0x38

Previous write at 0x00c000012158 by goroutine 8:
  main.main.func1()
      …/chapters/17-sync/race/main.go:21 +0x48

Goroutine 13 (running) created at:
  sync.(*WaitGroup).Go()
      …/src/sync/waitgroup.go:238 +0x6c
…
==================
賣出 7667 份（應該是 10000）
Found 2 data race(s)
exit status 66
  • 報告指出兩次衝突的存取：哪一行讀、哪一行寫、各是哪個 goroutine，以及這兩個 goroutine 是在哪裡開出來的。
  • 平常最常用的是 go test -race。寫並行程式時，測試一律加上它，CI 也要跑。
  • 它只抓得到這一次執行真的發生的 race。沒被執行到的程式碼、測試裡沒有同時發生的情況，它都看不到，所以測試要真的開好幾個 goroutine 去打同一個東西。
  • 代價不小：官方文件說，一般的程式記憶體會多用 5 到 10 倍，執行時間多 2 到 20 倍。用在測試和 CI，不要用在正式環境。

修正的方法有三大類：不要共用（每個 goroutine 寫自己的格子，14 章）、用 channel 把資料交給另一個 goroutine（15 章）、真的要共用時加上同步，也就是這一章的 sync 和 atomic。

2. Mutex

sync.Mutex（互斥鎖）只有兩個方法：Lock 拿鎖，拿不到就等；Unlock 還鎖，讓下一個人進來。慣例是把 Mutex 和它保護的欄位放在同一個 struct 裡，而且放在那些欄位的上面：

type Stock struct {
	mu   sync.Mutex
	left int
}

func (s *Stock) Take() bool {
	s.mu.Lock()
	defer s.mu.Unlock()
	if s.left == 0 {
		return false
	}
	s.left--
	return true
}

func (s *Stock) Left() int {
	s.mu.Lock()
	defer s.mu.Unlock()
	return s.left
}

func stockDemo() {
	s := &Stock{left: 30}
	sold := make([]bool, 100)
	var wg sync.WaitGroup
	for i := range sold {
		wg.Go(func() { sold[i] = s.Take() })
	}
	wg.Wait()

	n := 0
	for _, ok := range sold {
		if ok {
			n++
		}
	}
	fmt.Printf("100 個人搶 30 份：賣出 %d 份，剩 %d 份\n", n, s.Left())
}

輸出

100 個人搶 30 份：賣出 30 份，剩 0 份
  • 零值的 Mutex 就是沒上鎖的鎖，不用初始化，&Stock{left: 30} 就能用。
  • Lock 之後馬上寫 defer Unlock()：中途 return、甚至 panic，鎖都會還回去。
  • 只是讀也要上鎖。Left 沒有上鎖的話，它和 Take 裡的寫入一樣構成 data race。
  • 含有 Mutex 的 struct 不能複製，方法一律用指標 receiver，傳遞時也傳指標（常見錯誤 3）。
  • 臨界區要短：鎖裡面只做讀寫共用資料的事。拿著鎖去讀檔、打 API、等 channel，其他人就全部跟著等。

Take 的重點不只是「有上鎖」，而是「檢查還有沒有」和「減一」在同一段鎖裡。如果分成兩次各自上鎖，先呼叫 Left 查，再另外改，兩次之間就可能被別人插隊。把兩個客人的步驟排出來：

func oversellDemo() {
	s := &Stock{left: 1}
	a := s.Left() // 客人 A 查：還有 1 份
	b := s.Left() // 客人 B 也查：還有 1 份
	if a > 0 {
		s.set(a - 1)
		fmt.Println("A 買到了")
	}
	if b > 0 {
		s.set(b - 1)
		fmt.Println("B 買到了")
	}
	fmt.Println("只有 1 份，卻賣出 2 份，剩", s.Left())
}

輸出

A 買到了
B 買到了
只有 1 份，卻賣出 2 份，剩 0

這裡每一次讀寫都有鎖，race detector 一個字都不會說，但結果還是錯的。這叫 race condition：結果取決於執行的先後順序。data race 是記憶體層級的錯誤，工具抓得到；race condition 是邏輯上的錯誤，要靠你決定「哪些動作必須是一個整體」，然後用同一段鎖包起來。

Go 內建的 map 也不能同時寫。執行時期偵測到時，不是 panic，而是直接讓整個程式結束，recover 也接不住：

func main() {
	orders := make(map[int]int)
	var wg sync.WaitGroup
	for shop := range 10 {
		wg.Go(func() {
			for n := range 1000 {
				orders[shop*1000+n] = n // 好幾個 goroutine 同時寫 orders
			}
		})
	}
	wg.Wait()
	fmt.Println("共", len(orders), "筆")
}

goroutine 20 [running]:
internal/runtime/maps.fatal(…)
…
main.main.func1()
	…/chapters/17-sync/mapcrash/main.go:20 +0x44
…

這個偵測不保證每次都抓得到，抓不到的時候資料就悄悄壞掉了。給多個 goroutine 用的 map，一律和一把鎖放在一起（練習 3）。

3. RWMutex

價目表一天改不到幾次，卻隨時有人在查。用 Mutex 的話，查價的人也得一個一個排隊。sync.RWMutex 多了一組讀鎖：RLock / RUnlock 給只讀的人用，可以很多人同時拿；要寫的人照樣用 Lock / Unlock，拿到時一個讀的人也沒有：

type Menu struct {
	mu     sync.RWMutex
	prices map[string]int
}

func NewMenu() *Menu {
	return &Menu{prices: make(map[string]int)}
}

func (m *Menu) Price(item string) (int, bool) {
	m.mu.RLock()
	defer m.mu.RUnlock()
	p, ok := m.prices[item]
	return p, ok
}

func (m *Menu) SetPrice(item string, price int) {
	m.mu.Lock()
	defer m.mu.Unlock()
	m.prices[item] = price
}

func menuDemo() {
	m := NewMenu()
	m.SetPrice("排骨飯", 90)

	seen := make([]int, 50)
	var wg sync.WaitGroup
	for i := range seen {
		wg.Go(func() { seen[i], _ = m.Price("排骨飯") })
	}
	wg.Go(func() { m.SetPrice("排骨飯", 95) })
	wg.Wait()

	ok := true
	for _, p := range seen {
		if p != 90 && p != 95 {
			ok = false
		}
	}
	p, _ := m.Price("排骨飯")
	fmt.Printf("50 個人查到的不是 90 就是 95：%t\n", ok)
	fmt.Println("現在的價格", p)
}

輸出

50 個人查到的不是 90 就是 95：true
現在的價格 95

改價和查價同時進行，每個人查到的不是舊價就是新價，不會讀到改到一半的 map。用 go test -race 跑也乾乾淨淨。使用 RWMutex 前，先知道這幾件事：

  • 不能升級：拿著讀鎖時呼叫 Lock，會等所有讀的人離開，包括你自己，永遠等不到。也不能從寫鎖降級成讀鎖。
  • 不能重複拿讀鎖：有人在等寫鎖時，新的 RLock 會先等寫的人做完，避免寫的人一直等不到。所以同一個 goroutine 拿著讀鎖再 RLock 一次，可能和等待中的寫入卡成死結。
  • 不一定比較快：RWMutex 本身要記的狀態比 Mutex 多。讀的區間很短、或寫入其實很頻繁時，換成 RWMutex 沒有好處。先用 Mutex，等 benchmark（「測試」那一章）證明鎖的競爭真的是瓶頸，再考慮換。

4. 只做一次

讀設定檔、建立連線、載入菜單這類初始化，常常希望「第一次用到時才做，而且只做一次」。好幾個 goroutine 可能同時第一次用到，自己用 bool 判斷會變成 data race。sync.OnceValue 把這件事包好了：

func onceDemo() {
	loads := 0
	menu := sync.OnceValue(func() []string {
		loads++
		fmt.Println("讀取菜單")
		return []string{"排骨飯", "雞腿飯"}
	})

	var wg sync.WaitGroup
	for range 10 {
		wg.Go(func() { menu() })
	}
	wg.Wait()
	fmt.Println(menu(), "讀取次數", loads)
}

輸出

讀取菜單
[排骨飯 雞腿飯] 讀取次數 1

OnceValue 收一個函式，回傳一個包好的新函式。第一次呼叫時執行 f；其他同時呼叫的人會等 f 跑完，不會跑第二次；之後的呼叫直接回傳存好的結果。f 裡寫入的東西（例如 loads），等到的人保證看得到，不用另外上鎖。同一系列還有：

  • sync.OnceFunc(f)：f 沒有回傳值，只要「做一次」。
  • sync.OnceValues(f)：f 回傳兩個值，通常是 (T, error)。
  • sync.Once：比較早的寫法，var once sync.Once 再呼叫 once.Do(f)，結果要自己存在外面的變數裡。上面三個函式是 Go 1.21 加入的，新程式優先用它們。

要注意 OnceValues 連失敗也只算一次：

func onceErrDemo() {
	tries := 0
	load := sync.OnceValues(func() (int, error) {
		tries++
		return 0, errors.New("價目表讀取失敗")
	})

	for range 3 {
		_, err := load()
		fmt.Println(err)
	}
	fmt.Println("實際嘗試", tries, "次")
}

輸出

價目表讀取失敗
價目表讀取失敗
價目表讀取失敗
實際嘗試 1 次

第一次讀取失敗，之後每次呼叫都拿到同一個錯誤，不會重試；f 如果 panic，之後每次呼叫也都用同一個值 panic。暫時性的錯誤（網路不穩）需要重試時，Once 系列就不適合，要自己用 Mutex 寫（練習 5）。

5. atomic

只有一個數字要共用時，用一把鎖有點大材小用。sync/atomic 提供的型別，每個操作都是不可分割的：別的 goroutine 只會看到操作之前或之後的值，不會看到做到一半的狀態。最常用的是計數：

func ticketDemo() {
	var next atomic.Int64
	got := make([]int64, 200)
	var wg sync.WaitGroup
	for i := range got {
		wg.Go(func() { got[i] = next.Add(1) })
	}
	wg.Wait()

	slices.Sort(got)
	last := got[len(got)-1]
	unique := len(slices.Compact(got)) == len(got)
	fmt.Printf("發出 %d 張，號碼不重複：%t，最大 %d\n", next.Load(), unique, last)
}

輸出

發出 200 張，號碼不重複：true，最大 200

next.Add(1) 一步完成「加一，並拿到加完的值」，所以 200 個人同時抽，號碼也不會重複。如果寫成先 Add(1)、再另外 Load() 拿號碼，兩步之間別人可能也加了，就會拿到重複的號碼。atomic 型別都是零值就能用、不能複製，常用的有：

型別用途
atomic.Int64、Int32、Uint64……計數器、序號：Add、Load、Store、Swap、CompareAndSwap
atomic.Bool旗標，例如「已經關閉了嗎」
atomic.Pointer[T]整份換掉的資料，例如設定、公告

Load 和 Store 各自是不可分割的，但「讀出來、判斷、寫回去」三步合起來就不是了，又回到第 2 節的先查再改。atomic 的解法是 CompareAndSwap（CAS）：只有值還是我剛剛讀到的那個時，才換成新的，並回傳 true；被別人搶先改過就回傳 false，重讀再試：

func raiseTo(best *atomic.Int64, v int64) {
	for {
		cur := best.Load()
		if v <= cur || best.CompareAndSwap(cur, v) {
			return
		}
	}
}

func maxDemo() {
	var best atomic.Int64
	var wg sync.WaitGroup
	for _, amount := range []int64{320, 85, 1260, 470, 990} {
		wg.Go(func() { raiseTo(&best, amount) })
	}
	wg.Wait()
	fmt.Println("今天最大的一筆：", best.Load())
}

輸出

今天最大的一筆： 1260

好幾個欄位要一起換時，用 atomic.Pointer[T]：做一份全新的值，把指標整個換上去。讀的人拿到的永遠是某一份完整的值：

type Notice struct {
	Text  string
	Until string
}

func noticeDemo() {
	var board atomic.Pointer[Notice]
	board.Store(&Notice{Text: "正常營業", Until: "21:00"})

	old := board.Swap(&Notice{Text: "颱風提早打烊", Until: "18:00"})
	now := board.Load()
	fmt.Println("換下來的：", old.Text, old.Until)
	fmt.Println("現在的：", now.Text, now.Until)
}

輸出

換下來的： 正常營業 21:00
現在的： 颱風提早打烊 18:00

換上去之後，就不要再改那一份 Notice 的欄位：讀的人可能正拿著它，改了就是 data race。要改就再做一份新的換上去（練習 4）。

atomic 還是 Mutex？只有一個獨立的值（計數、旗標、整份換掉的指標）用 atomic；好幾個值必須互相一致（次數和金額、名單和人數），用 Mutex。兩個各自 atomic 的欄位，分開讀時可能一個已經更新、另一個還沒有（練習 1）。拿不定主意時用 Mutex，比較不容易寫錯。

6. sync.Map 與 sync.Pool

sync 套件裡還有兩個常被過度使用的型別。先講結論：大多數情況都用不到。

sync.Map 是可以直接給多個 goroutine 用的 map。它的鍵和值都是 any，沒有型別檢查，官方文件明說大多數程式應該用一般的 map 搭配鎖。它只在兩種情況比較快：鍵寫入一次之後就只會被讀（只會長大的快取），或是每個 goroutine 讀寫的鍵各不相同。它的方法把常見的「先查再改」做成一步，例如 LoadOrStore：

func seenDemo() {
	var seen sync.Map
	for _, id := range []string{"A-01", "A-02", "A-01"} {
		if _, loaded := seen.LoadOrStore(id, true); loaded {
			fmt.Println(id, "重複，略過")
			continue
		}
		fmt.Println(id, "接單")
	}
}

輸出

A-01 接單
A-02 接單
A-01 重複，略過

這個例子用 map[string]bool 加一把 Mutex 一樣做得到，而且型別清楚。需要同時維護其他欄位（例如重複次數）時，map 加鎖更是唯一合理的選擇。

sync.Pool 存放可以重複使用的暫時物件，減少一直配置新記憶體、又讓 GC 回收的負擔。標準庫的 fmt 就用它保存輸出用的緩衝區：

var slips = sync.Pool{
	New: func() any { return new(bytes.Buffer) },
}

func receipt(item string, price int) string {
	b := slips.Get().(*bytes.Buffer)
	defer func() {
		b.Reset()
		slips.Put(b)
	}()
	fmt.Fprintf(b, "%s NT$%d", item, price)
	return b.String()
}

func poolDemo() {
	fmt.Println(receipt("排骨飯", 90))
	fmt.Println(receipt("雞腿飯", 100))
}

輸出

排骨飯 NT$90
雞腿飯 NT$100
  • Get 回傳 any，要做型別斷言；Pool 是空的時候呼叫 New 做一個新的。
  • 還回去之前要 Reset，下一個借的人才不會看到上一張收據。
  • 還回去之後就不能再用它。這裡回傳 b.String() 是安全的，因為它會複製一份；回傳 b.Bytes() 的話，拿到的 slice 和 Buffer 共用底層陣列，下一個借走的人會改掉它。
  • Pool 裡的東西隨時可能被清掉，所以不能拿來當連線池或快取，只能放「沒有也沒關係、重做一個就好」的東西。
  • 它是效能最佳化，不是預設寫法。先用 benchmark 和 profiling 證明配置記憶體真的是瓶頸（效能與 profiling那一章），再加上它。

7. happens-before

最後回答一個問題：為什麼一定要用 channel、鎖、atomic，不能自己用一個 bool 當「準備好了」的訊號？

錯：用普通的 bool 等

func waitFlag() []string {
	var menu []string
	ready := false
	go func() {
		menu = []string{"排骨飯", "雞腿飯"}
		ready = true
	}()
	for !ready {
	}
	return menu
}

對：用 channel 等

func waitDone() []string {
	var menu []string
	done := make(chan struct{})
	go func() {
		menu = []string{"排骨飯", "雞腿飯"}
		close(done)
	}()
	<-done
	return menu
}

waitDone 的輸出

[排骨飯 雞腿飯]

waitFlag 在同一個 goroutine 裡讀起來很合理：先寫 menu，再把 ready 設成 true。但編譯器和 CPU 為了效率，可以在單一 goroutine 看不出差別的前提下重新安排讀寫順序，或把值放在暫存器裡不重讀。結果是另一個 goroutine 可能永遠看不到 ready 變成 true，也可能看到 true，卻讀到還沒寫好的 menu。這段程式本身就是 data race，-race 會直接抓到。

Go 的記憶體模型用「happens-before」描述「某件事保證先發生、而且結果看得到」：同一個 goroutine 裡，照程式的順序；不同 goroutine 之間，只有同步操作能建立這個關係。waitDone 裡，寫 menu 在 close 之前（同一個 goroutine），close 保證先於 <-done 完成，收到之後才讀 menu，一路串起來，讀的時候一定看得到。

記憶體模型官方文件開頭的建議很直接：如果你得讀完整份文件才能理解自己的程式在做什麼，代表你寫得太聰明了。照這一章的規矩用 channel、鎖、atomic、Once、WaitGroup，就不必擔心這些細節。

深入：第一次讀可以先跳過

7.1 哪些操作建立 happens-before

  • go f() 這個敘述先於 f 開始執行：go 之前寫好的值，goroutine 裡看得到。反過來，goroutine 結束不保證先於任何事，要等它就用 WaitGroup 或 channel。
  • channel：送出先於對應的收完成；close 先於「因為 channel 已關閉而收到零值」的那次收；無緩衝的 channel，收先於對應的送完成。容量 C 的 channel，第 k 次收先於第 k+C 次送完成，這也是用 buffered channel 限制同時數量的依據（「並行模式」那一章）。
  • Mutex：第 n 次 Unlock 先於第 n+1 次 Lock 返回，所以上一個人在鎖裡寫的東西，下一個拿到鎖的人看得到。
  • Once：f 返回先於任何一次 Do 返回；OnceValue 等函式也一樣。
  • WaitGroup：Done（或 wg.Go 裡的 f 返回）先於它放行的那次 Wait 返回，所以 Wait 之後可以直接讀 goroutine 寫好的格子。
  • atomic：如果 B 讀到了 A 寫入的值，A 就先於 B；所有 atomic 操作看起來像是照某一個全域的順序執行，和 Java 的 volatile 語意相同。

常見錯誤

1. 只有寫的時候上鎖

「讀而已，不會改壞東西」是錯的：讀和寫同時發生就是 data race，讀到的可能是寫到一半的值。共用資料的每一次存取都要在同一把鎖底下（第 2 節）。

2. 先查再改，分成兩次上鎖

錯：查和改各自上鎖，中間會被插隊

func (s *Stock) takeSplit() bool {
	n := s.Left()
	if n == 0 {
		return false
	}
	s.set(n - 1)
	return true
}

對：查和改在同一段鎖裡

func (s *Stock) Take() bool {
	s.mu.Lock()
	defer s.mu.Unlock()
	if s.left == 0 {
		return false
	}
	s.left--
	return true
}

race detector 抓不到這種錯（第 2 節的 race condition）。設計方法時就要想好：哪些步驟必須是一個整體，就放進同一個方法、同一段鎖。

3. 複製了含有 Mutex 的值

package main

import (
	"fmt"
	"sync"
)

type Stock struct {
	mu   sync.Mutex
	left int
}

// Take 用了值 receiver：每次呼叫都複製一份 Stock，連同裡面的 Mutex。
func (s Stock) Take() bool {
	s.mu.Lock()
	defer s.mu.Unlock()
	if s.left == 0 {
		return false
	}
	s.left--
	return true
}

func main() {
	s := Stock{left: 1}
	fmt.Println(s.Take(), s.Take())
}

go vet

main.go:14:9: Take passes lock by value: example.Stock contains sync.Mutex

值 receiver 讓每次呼叫都拿到一份複本：鎖的是複本的鎖，減的是複本的份數。這個程式可以編譯，執行會印出 true true，只有 1 份卻賣了 2 次。含有 Mutex、RWMutex、WaitGroup、atomic 型別的 struct，方法一律用指標 receiver，傳遞時也傳指標。go vet 會抓到大部分的複製。

4. 拿著鎖，再呼叫一個也要拿同一把鎖的方法

Go 的 Mutex 不能重複進入（Java 的 synchronized 可以）：同一個 goroutine 拿著鎖又 Lock 一次，會等自己 Unlock，永遠等不到（練習 6）。常見的整理方式是：公開的方法負責上鎖，真正的工作寫在一個「假設已經拿著鎖」的私有方法裡，公開方法之間互相呼叫時改呼叫私有的版本。

5. 拿著鎖做慢的事

鎖裡面讀檔、打 API、送 channel，其他所有要這把鎖的 goroutine 都跟著等；送 channel 時對方如果也在等這把鎖，還會卡成死結。在鎖裡把需要的資料複製出來，Unlock 之後再做慢的事。

6. 以為 -race 沒報錯就沒問題

它只抓得到這次執行真的發生的 data race（第 1 節），也抓不到 race condition（常見錯誤 2）。測試要真的讓好幾個 goroutine 同時打同一個東西，邏輯上的整體性要靠你自己設計。

7. 用普通變數當訊號

用 bool 或 int 告訴另一個 goroutine「好了」，沒有 happens-before，看不看得到都沒有保證（第 7 節）。要通知就用 channel（close 一個 done）、WaitGroup，或 atomic.Bool。

    和 OnceValues 一樣只成功一次，但失敗時不記住錯誤，下次呼叫再試。

    func OnceOK[T any](f func() (T, error)) func() (T, error) {
	// TODO: 實作
	return func() (T, error) {
		var zero T
		return zero, nil
	}
}

    測試：TestOnceOK。

    提示

    在回傳的函式外面宣告 mu sync.Mutex、done bool、val T，讓 closure 共用它們。回傳的函式一開始就 Lock，整段（包括呼叫 f）都拿著鎖：done 就直接回傳 val；否則呼叫 f，成功才把 done 設成 true。

	names []string
}

	q.mu.Lock()
	defer q.mu.Unlock()
	q.names = append(q.names, name)

	q.mu.Lock()
	defer q.mu.Unlock()
	return len(q.names)
}

	q.mu.Lock()
	defer q.mu.Unlock()
	if q.Len() == 0 {
		return "目前不用等"
	}
	return fmt.Sprintf("%d 組候位，下一組：%s", q.Len(), q.names[0])
}

    常見錯誤 4。

重點回顧

  • 好幾個 goroutine 同時存取同一個變數、至少一個在寫、又沒有同步，就是 data race，結果無法預期。
  • 並行程式的測試一律加 -race；它只抓得到真的發生的 race，抓不到邏輯上的 race condition。
  • Mutex 保護共用資料：讀寫都要上鎖、defer Unlock、不能複製、臨界區要短。
  • 先查再改必須在同一段鎖裡；Go 的 Mutex 不能重複進入。
  • map 不能同時寫，偵測到時整個程式直接結束。
  • RWMutex 適合讀很多、寫很少，不能升級或降級；不確定時先用 Mutex。
  • sync.OnceValue、OnceValues、OnceFunc 做只執行一次的初始化，錯誤和 panic 也只會發生一次。
  • atomic 適合單一的值：Add 拿號碼、CompareAndSwap 做先查再改、Pointer 整份換掉；好幾個值要一致就用 Mutex。
  • sync.Map 和 sync.Pool 是特定情況的工具，預設用 map 加鎖、直接配置。
  • 不同 goroutine 之間，只有同步操作能保證「先發生、看得到」，不要用普通變數當訊號。
