1. go 敘述：多開一位廚師

goroutine 是 Go 裡「同時執行」的單位。每個程式一開始只有一個 goroutine，就是執行 main 的那一個。在函式呼叫前面加上 go，就會開一個新的 goroutine 去執行那個呼叫：

func main() {
	go func() {
		time.Sleep(100 * time.Millisecond)
		fmt.Println("排骨飯做好了")
	}()
	fmt.Println("點完餐，走人")
}

輸出（go run ./chapters/14-goroutines/nowait）

點完餐，走人

「排骨飯做好了」沒有印出來。go func() { … }() 這一行只是把函式交給新的 goroutine，立刻就返回，main 繼續往下印「點完餐，走人」，然後 main 回傳。規格寫得很清楚：main 回傳時程式就結束，不會等其他 goroutine。那個還在睡的 goroutine 就這樣跟著程式一起消失了。

  • go 後面一定要是函式呼叫。最常見的是 go func() { … }()：寫一個匿名函式，結尾的 () 呼叫它。
  • 被呼叫的函式就算有回傳值，也會被丟掉，沒有地方可以接。結果要怎麼拿回來，是第 3 節的主題。
  • 沒有任何 API 可以從外面「殺掉」一個 goroutine，也沒有 API 可以取得 goroutine 的編號。goroutine 只能自己結束：函式 return，或程式結束。

這支程式的輸出取決於時間，所以它放在 nowait 子目錄，沒有測試。本章其他示範都會先等 goroutine 做完再印，輸出才會固定。等的方法就是下一節。

2. 等它們做完：sync.WaitGroup

sync.WaitGroup 是一個計數器：開一個 goroutine 就加 1，做完一個就減 1，Wait 會等到計數變成 0 才返回。Go 1.25 起，「加 1、開 goroutine、做完減 1」這三件事可以用一個 wg.Go 完成：

func prepare(order string) string {
	return order + "好了"
}

func kitchenDemo() {
	orders := []string{"排骨飯", "雞腿飯", "魚排飯"}
	done := make([]string, len(orders))
	var wg sync.WaitGroup
	for i, o := range orders {
		wg.Go(func() {
			done[i] = prepare(o)
		})
	}
	wg.Wait()
	fmt.Println(strings.Join(done, "、"))
}

輸出

排骨飯好了、雞腿飯好了、魚排飯好了
  • WaitGroup 的零值就能用，var wg sync.WaitGroup 就好。
  • wg.Go(f) 開一個新的 goroutine 執行 f，並把它登記在 WaitGroup 上；f 回傳時自動登出。
  • 三份餐是同時做的，完成的順序每次可能不同。但每個 goroutine 只寫 done 裡自己那一格，Wait 之後再依照索引印出來，結果就固定了。
  • Go 1.22 起，for 迴圈每一圈的 i、o 都是新的變數（03 章），每個 goroutine 抓到的是自己那一圈的值，可以放心在 closure 裡使用。

Go 1.25 以前沒有 wg.Go，要自己寫 Add 和 Done。舊的程式碼裡到處都是這種寫法，一定要看得懂：

func kitchenAddDone() {
	orders := []string{"排骨飯", "雞腿飯", "魚排飯"}
	done := make([]string, len(orders))
	var wg sync.WaitGroup
	for i, o := range orders {
		wg.Add(1)
		go func() {
			defer wg.Done()
			done[i] = prepare(o)
		}()
	}
	wg.Wait()
	fmt.Println(strings.Join(done, "、"))
}

輸出

排骨飯好了、雞腿飯好了、魚排飯好了

wg.Add(1) 必須寫在 go 之前，在開 goroutine 的那一方執行。如果寫在 goroutine 裡面，main 可能在任何一個 goroutine 來得及 Add 之前就執行 Wait，看到計數是 0，直接放行（常見錯誤 2）。defer wg.Done() 寫在 goroutine 的第一行，不管函式從哪裡 return 都會減 1。新寫的程式用 wg.Go 就不會犯這些錯。

go 和 defer 有一個共同點：後面那個呼叫的參數，在 go 這一行就求值了，goroutine 晚一點才開始跑也不影響：

func argsNowDemo() {
	var wg sync.WaitGroup
	order := "排骨飯"
	wg.Add(1)
	go func(o string) {
		defer wg.Done()
		fmt.Println("廚房收到", o)
	}(order)
	order = "雞腿飯"
	wg.Wait()
	fmt.Println("櫃台現在的單", order)
}

輸出

廚房收到 排骨飯
櫃台現在的單 雞腿飯

參數 o 在 go 那一行就拿到了「排骨飯」，之後櫃台把 order 改成雞腿飯，廚房收到的還是排骨飯。如果 goroutine 不用參數，而是直接在 closure 裡讀 order，就變成 main 在寫、goroutine 在讀同一個變數，這是 data race，go test -race 會抓到（「sync 與 data race」那一章）。

3. 把結果交回來

goroutine 沒有回傳值，常見的交回結果方式有兩種：寫進事先準備好的位置，或透過 channel 送回來（「channel」那一章）。這一章先用第一種，它不需要任何新工具：

func sumParallel(nums []int, parts int) int {
	parts = max(parts, 1)
	partial := make([]int, parts)
	size := (len(nums) + parts - 1) / parts
	var wg sync.WaitGroup
	for p := range parts {
		lo := min(p*size, len(nums))
		hi := min(lo+size, len(nums))
		wg.Go(func() {
			for _, n := range nums[lo:hi] {
				partial[p] += n
			}
		})
	}
	wg.Wait()

	total := 0
	for _, s := range partial {
		total += s
	}
	return total
}

func sumDemo() {
	nums := make([]int, 1000)
	for i := range nums {
		nums[i] = i + 1
	}
	fmt.Println(sumParallel(nums, 4))
}

輸出

500500

1 到 1000 切成四段，每段由一個 goroutine 加總到 partial[p]，Wait 之後再把四個部分和加起來。這樣做之所以安全，有兩個原因：

  • 不同的 goroutine 寫不同的格子。slice 的每個元素是不同的記憶體位置，同時寫不同的元素不算衝突。但如果大家都 total += n 寫同一個變數，或對同一個 slice append，就是 data race。
  • 讀取發生在 Wait 之後。WaitGroup 保證：goroutine 在結束前寫的東西，在 Wait 返回之後一定看得到。在 Wait 之前偷看 partial，可能看到寫了一半的結果。

錯誤也是一樣的道理：每個 goroutine 把自己的錯誤寫進 errs 的對應格子，Wait 之後用 errors.Join 合起來（11 章），順序和輸入一致：

var ErrNoStore = errors.New("沒有這家分店")

var shelves = map[string]int{"中山店": 12, "雙連店": 0, "民權店": 7}

func stock(store string) (int, error) {
	n, ok := shelves[store]
	if !ok {
		return 0, fmt.Errorf("%s：%w", store, ErrNoStore)
	}
	return n, nil
}

func checkStores(stores []string) ([]int, error) {
	counts := make([]int, len(stores))
	errs := make([]error, len(stores))
	var wg sync.WaitGroup
	for i, s := range stores {
		wg.Go(func() {
			counts[i], errs[i] = stock(s)
		})
	}
	wg.Wait()
	return counts, errors.Join(errs...)
}

func storesDemo() {
	counts, err := checkStores([]string{"中山店", "雙連店", "圓山店", "民權店"})
	fmt.Println(counts)
	fmt.Println(err)
	fmt.Println(errors.Is(err, ErrNoStore))
}

輸出

[12 0 0 7]
圓山店：沒有這家分店
true

四家分店是同時查詢的，真實的程式裡每次查詢是一個網路請求，同時查比一家一家查快得多。圓山店查不到，但其他三家的結果照樣拿得到；errors.Join 會略過 nil，全部成功時回傳的就是 nil。

map 不能這樣用：好幾個 goroutine 同時寫同一個 map，就算 key 不同，也可能讓程式直接當掉（07 章）。需要的話，讓每個 goroutine 寫自己的 map，Wait 之後再合併（練習 4）。

4. goroutine 很便宜

作業系統的執行緒（thread）在建立時就要預留一大塊 stack，建立和切換也要經過作業系統，開幾千條就很吃力。goroutine 由 Go 的 runtime 自己管理：

  • 每個 goroutine 的 stack 一開始只有幾 KB，不夠用時 runtime 會配置一塊更大的，把內容搬過去。
  • 建立 goroutine 和在 goroutine 之間切換，都不需要進入作業系統，比執行緒便宜得多。
  • runtime 把大量的 goroutine 分配到少數幾條執行緒上執行（第 5 節）。
func spawn(n int) int {
	done := make([]bool, n)
	var wg sync.WaitGroup
	for i := range n {
		wg.Go(func() { done[i] = true })
	}
	wg.Wait()

	count := 0
	for _, d := range done {
		if d {
			count++
		}
	}
	return count
}

func spawnDemo() {
	fmt.Println(spawn(10000))
}

輸出

10000

一萬個 goroutine 一瞬間就開完、跑完了。stack 會自動長大，所以在 goroutine 裡遞迴十萬層也沒問題：

func depth(n int) int {
	if n == 0 {
		return 0
	}
	return 1 + depth(n-1)
}

func growDemo() {
	var got int
	var wg sync.WaitGroup
	wg.Go(func() {
		got = depth(100_000)
	})
	wg.Wait()
	fmt.Println(got)
}

輸出

100000

但「便宜」不等於「免費」。每個 goroutine 在結束之前都佔著自己的 stack 和它抓住的變數；而且 goroutine 要做的事通常會用到外部資源，例如資料庫連線、對方伺服器的處理能力。一口氣對資料庫開一萬個查詢，倒下的會是資料庫。限制同時執行數量的做法，在「並行模式」那一章。

5. 排程器：並行與平行

這兩個詞常被混用，但意思不同：

  • 並行（concurrency）：把程式寫成好幾件可以各自進行的工作。只有一個核心時，它們輪流執行，看起來像同時。
  • 平行（parallelism）：好幾件工作在同一個瞬間，分別在不同的核心上執行。

goroutine 讓你寫出並行的程式；有沒有平行，由 runtime 和機器決定。GOMAXPROCS 是「同時最多有幾條執行緒在跑 Go 的程式碼」，預設等於這台機器可用的 CPU 數：

func main() {
	fmt.Println("CPU 數", runtime.NumCPU())
	fmt.Println("GOMAXPROCS", runtime.GOMAXPROCS(0))
	fmt.Println("goroutine 數", runtime.NumGoroutine())
}

輸出（在一台 10 核心的筆電上執行 go run ./chapters/14-goroutines/procs，你的數字會不同）

CPU 數 10
GOMAXPROCS 10
goroutine 數 1
  • runtime.GOMAXPROCS(0) 只查詢不修改。幾乎不需要自己設定它，預設值就是對的。
  • Go 1.25 起（go.mod 寫 go 1.25 以上時），在 Linux 容器裡執行，預設值也會參考容器的 CPU 配額，而不是只看整台主機有幾顆 CPU；之後配額改變時，runtime 也會跟著調整。
  • goroutine 數是 1：程式剛開始時只有 main 自己。

goroutine 什麼時候執行、在哪個核心上執行、輪到誰，都由 runtime 的排程器決定，你無法控制，也不應該依賴它的順序。Go 1.14 起，排程器可以強制暫停一個跑太久的 goroutine，讓其他 goroutine 有機會執行，所以就算有一個 goroutine 在跑沒有函式呼叫的無窮迴圈，其他 goroutine 也不會因此餓死。

多開 goroutine 不一定會變快。工作是在等網路、等磁碟的（I/O bound），同時等很多個會快很多，第 3 節的分店查詢就是這種。工作是純計算的（CPU bound），最多只能快到核心數那麼多倍，而且切太細的話，開 goroutine、合併結果的成本還會超過省下的時間。要不要並行，用 benchmark 量過再決定。

深入：第一次讀可以先跳過

5.1 G、M、P

runtime 的排程器常用三個字母描述。這是實作細節，不是語言規格，版本之間可能調整，了解概念就好：

  • G：一個 goroutine，記錄它的 stack 和執行到哪裡。
  • M：一條作業系統執行緒，真正在 CPU 上跑的東西。
  • P：執行 Go 程式碼需要的資源，數量就是 GOMAXPROCS。M 必須拿到一個 P，才能執行 G；每個 P 有自己的一排等待執行的 G。

一個 P 的佇列空了，它會去別的 P 那裡拿一些 G 過來，讓工作平均分配。一個 G 因為系統呼叫（例如讀檔）卡住時，它所在的 M 也卡住，P 會交給另一條 M 繼續執行其他的 G，所以一個 goroutine 卡住不會拖累其他人。等 channel、等鎖這類 Go 自己的等待，則只是把 G 放到一邊，M 和 P 馬上去執行下一個 G。

6. panic 與洩漏

04 章說過，recover 要寫在 defer 裡，接住同一個函式呼叫鏈上的 panic。關鍵在「同一個」：每個 goroutine 有自己的呼叫鏈，main 的 recover 管不到別的 goroutine：

func main() {
	defer func() {
		fmt.Println("main 接到了：", recover())
	}()

	var wg sync.WaitGroup
	wg.Add(1) // wg.Go 的文件規定傳進去的函式不可以 panic，所以這裡用 Add 和 Done
	go func() {
		var stock map[string]int
		stock["排骨飯"]-- // 寫入 nil map：panic
		wg.Done()
	}()
	wg.Wait()
	fmt.Println("不會印出來")
}

輸出（go run ./chapters/14-goroutines/crash，後面的 stack trace 省略）

panic: assignment to entry in nil map

goroutine 35 [running]:
main.main.func2()

main 的 defer 根本沒有執行，「main 接到了」沒有印出來，程式以 exit status 2 結束。goroutine 的編號每次執行都可能不同。後果比單一執行緒的程式嚴重：一個處理請求的 goroutine panic，整個伺服器都會掛掉，連帶所有正在處理中的請求。

  • 可能 panic 的 goroutine，要在它自己的第一行寫 defer 和 recover，把 panic 轉成錯誤交回來（練習 5）。
  • wg.Go 的文件規定：傳進去的函式不可以 panic。要在 wg.Go 裡跑可能 panic 的程式，recover 一樣要寫在傳進去的函式裡面。
  • 標準庫的 HTTP 伺服器會替每個請求的 goroutine 接住 panic，但那是它自己寫的保護，你自己開的 goroutine 沒有。

另一個問題是 goroutine 洩漏（goroutine leak）：goroutine 在等一個永遠不會發生的事，例如等一個沒有人會送資料的 channel、等一把沒有人會放開的鎖。它不會結束，也沒有辦法從外面殺掉，它的 stack 和抓住的變數就一直佔著記憶體。伺服器每處理一個請求漏一個，跑幾天就會把記憶體吃光。

避免洩漏的原則很簡單：每開一個 goroutine，都要知道它什麼時候、怎麼結束。用 WaitGroup 等它、用 channel 的 close 通知它（「channel」那一章）、用 context 取消它（「context」那一章）。說不出它怎麼結束的 goroutine，就不要開。

常見錯誤

1. main 沒有等就結束了

goroutine 的工作做到一半，程式就結束了，而且沒有任何錯誤訊息（第 1 節）。用 WaitGroup 等所有 goroutine 做完。

2. wg.Add 寫在 goroutine 裡面

package main

import (
	"fmt"
	"sync"
)

func main() {
	orders := []string{"排骨飯", "雞腿飯"}
	done := make([]string, len(orders))
	var wg sync.WaitGroup
	for i, o := range orders {
		go func() {
			wg.Add(1)
			defer wg.Done()
			done[i] = o + "好了"
		}()
	}
	wg.Wait()
	fmt.Println(done)
}

go vet

main.go:14:10: WaitGroup.Add called from inside new goroutine

main 跑到 Wait 時，goroutine 可能都還沒開始，計數還是 0，Wait 直接放行，印出空的結果。Add 要在 go 之前、在開 goroutine 的那一方呼叫；或者直接用 wg.Go。

3. 把 WaitGroup 當值傳進函式

package main

import (
	"fmt"
	"sync"
)

func cook(wg sync.WaitGroup, order string) {
	defer wg.Done()
	fmt.Println(order, "好了")
}

func main() {
	var wg sync.WaitGroup
	wg.Add(1)
	go cook(wg, "排骨飯")
	wg.Wait()
}

go vet

main.go:8:14: cook passes lock by value: sync.WaitGroup contains sync.noCopy
main.go:16:10: call of cook copies lock value: sync.WaitGroup contains sync.noCopy

cook 拿到的是一份複本，它的 Done 減的是複本的計數，main 的 WaitGroup 永遠等不到 0。要傳就傳指標 *sync.WaitGroup；更好的做法是讓 cook 根本不知道 WaitGroup 的存在，在呼叫端寫 wg.Go(func() { cook("排骨飯") })。

4. 用 time.Sleep 等 goroutine

「等一秒應該夠了吧」在你的電腦上夠，在忙碌的伺服器或 CI 上不一定夠；夠的時候又白白浪費了時間。等 goroutine 要用 WaitGroup 或 channel，讓它做完時明確地通知你。

5. 好幾個 goroutine 寫同一個變數

total += n、對同一個 slice append、寫同一個 map，都是 data race：結果可能少算、可能壞掉，map 甚至會讓程式當掉。讓每個 goroutine 寫自己的格子（第 3 節），或用鎖保護（「sync 與 data race」那一章）。寫並行的程式時，測試一律加上 -race。

6. 以為 main 的 recover 能接住所有 panic

只能接住 main 自己那個 goroutine 的 panic（第 6 節）。每個可能 panic 的 goroutine 都要有自己的 recover。

7. 開了 goroutine 就不管

說不出它什麼時候結束，就可能洩漏（第 6 節）。寫下 go 的那一刻，就要想好它的結束方式。

練習

題目在 exercises/14-goroutines/exercises.go。幾題的測試會檢查工作是不是真的同時在跑：一個接一個做的寫法，會等到逾時才失敗。寫完之後也用 -race 跑一次。

go test ./exercises/14-goroutines/                 # 跑全部練習
go test ./exercises/14-goroutines/ -run TestEach  # 只跑一題
go test -race ./exercises/14-goroutines/           # 檢查 data race
go test -tags solution ./exercises/14-goroutines/  # 跑參考解答

  1. 入門練習 1：大家一起開工

    同時呼叫 f(0) 到 f(n-1)，全部結束才回傳。

    func Each(n int, f func(i int)) {
	// TODO: 實作
}

    測試裡的 f 會等其他人到齊才結束，所以一個接一個呼叫會失敗。測試：TestEach。

    提示

    一個 WaitGroup，迴圈裡 wg.Go(func() { f(i) })，迴圈結束後 Wait。range n 在 n 小於等於 0 時一圈都不跑。

  2. 入門練習 2：同時算，照順序交

    每個元素一個 goroutine，結果的順序要和輸入一樣。

    func MapParallel[T, U any](s []T, f func(T) U) []U {
	// TODO: 實作
	return nil
}

    測試：TestMapParallel。

    提示

    先 make([]U, len(s))，每個 goroutine 只寫 out[i]（第 3 節）。不要 append，那是好幾個 goroutine 改同一個 slice。

  3. 進階練習 3：每家分店都檢查一遍

    同時檢查每一家分店，把所有錯誤依分店順序合在一起。

    func CheckAll(stores []string, check func(store string) error) error {
	// TODO: 實作
	return nil
}

    測試：TestCheckAll。

    提示

    和第 3 節的 checkStores 一樣，用一個 []error 讓每個 goroutine 寫自己的格子，Wait 之後 errors.Join(errs...)。

  4. 進階練習 4：數點餐單上的詞

    好幾份點餐紀錄，每份交給一個 goroutine 數詞，最後合併。

    func CountWords(docs []string) map[string]int {
	// TODO: 實作
	return nil
}

    寫完用 -race 跑，好幾個 goroutine 寫同一個 map 會被抓到。測試：TestCountWords。

    提示

    準備 []map[string]int，每個 goroutine 建立並填好自己的 map，放進自己那一格。Wait 之後，在原本的 goroutine 裡把它們加總到一個新的 map。

  5. 挑戰練習 5：鍋子破了也不能倒店

    在新的 goroutine 裡執行 f，把 panic 轉成錯誤交回來，不讓整個程式當掉。

    func Try(f func()) error {
	// TODO: 實作
	return nil
}

    測試：TestTry。

    提示

    Try 用具名回傳值 (err error)。在 wg.Go 的函式裡，第一行 defer 一個呼叫 recover 的函式：r 不是 nil 時，用 r.(error) 判斷它是不是 error，分別用 %w 或 %v 包成錯誤，指定給 err。recover 寫在 Try 本身是接不到的（第 6 節）。

  6. 挑戰練習 6：總店加總營業額

    總店底下有分店，分店底下還有分店，每一家子分店交給一個 goroutine 遞迴計算。

    type Branch struct {
	Name     string
	Sales    int
	Children []*Branch
}
    func Total(b *Branch) int {
	// TODO: 實作
	return 0
}

    測試：TestTotal。

    提示

    每一層都有自己的 WaitGroup 和一個 []int，第 i 個 goroutine 把 Total(b.Children[i]) 寫進第 i 格，Wait 之後加上 b.Sales。goroutine 裡再開 goroutine 完全沒問題。

  7. 找錯練習 7：說好的一起做呢

    每個工作都有做到，但測試說它們沒有同時執行。

    func RunAll(tasks []func()) {
	var wg sync.WaitGroup
	for _, t := range tasks {
		wg.Go(t)
		wg.Wait()
	}
}

    測試：TestRunAll。

    提示

    每開一個 goroutine 就等它做完，等於一個接一個做。先把全部都開起來，最後才 Wait 一次。

參考解答：先自己寫完再看。測試通過、而且 -race 沒有警告的寫法都是對的。

重點回顧

  • go f(x) 開一個新的 goroutine 執行 f，go 這一行立刻返回；參數在 go 這一行就求值，回傳值會被丟掉。
  • main 回傳時整個程式結束，不等其他 goroutine。
  • 用 sync.WaitGroup 等一群 goroutine：Go 1.25 起用 wg.Go，以前的寫法是 go 之前 Add(1)、goroutine 裡 defer Done()。
  • WaitGroup 不能複製，要傳就傳指標。
  • goroutine 沒有回傳值：讓每個 goroutine 寫自己的格子，Wait 之後再讀；錯誤也一樣，最後用 errors.Join 合起來。
  • 好幾個 goroutine 寫同一個變數或 map 是 data race；測試並行的程式一律加 -race。
  • goroutine 的 stack 從幾 KB 開始、會自動長大，可以開上萬個，但它用到的外部資源不是免費的。
  • 並行是程式的結構，平行是執行的方式；GOMAXPROCS 預設就是可用的 CPU 數。
  • 沒被 recover 的 panic，不管在哪個 goroutine，都會讓整個程式結束；recover 只接得到同一個 goroutine 的 panic。
  • 每開一個 goroutine，都要知道它怎麼結束，否則會洩漏。
