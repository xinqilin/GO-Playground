錯誤處理

Go 沒有例外。錯誤是一個普通的值，函式把它和結果一起交給你；每一層補上自己知道的事再往上傳，最外層決定怎麼回應。

1. 錯誤是一個值

error 是 Go 內建的一個 interface，只有一個方法：type error interface { Error() string }。任何有 Error() string 方法的型別都是一種錯誤（10 章）。慣例是把它放在回傳值的最後一個：

func parsePeople(s string) (int, error) {
	n, err := strconv.Atoi(s)
	if err != nil {
		return 0, err
	}
	if n < 1 || n > 12 {
		return 0, fmt.Errorf("人數 %d 不在 1 到 12 之間", n)
	}
	return n, nil
}

func basicsDemo() {
	for _, s := range []string{"4", "四", "20"} {
		n, err := parsePeople(s)
		if err != nil {
			fmt.Printf("錯誤：%v\n", err)
			continue
		}
		fmt.Println("人數", n)
	}
}

輸出

人數 4
錯誤：strconv.Atoi: parsing "四": invalid syntax
錯誤：人數 20 不在 1 到 12 之間
  • 呼叫完立刻寫 if err != nil { … }：先處理錯誤，正常的流程留在左邊不縮排（03 章的 guard clause）。
  • 失敗時其他回傳值給零值（return 0, err），呼叫的人看到 err 不是 nil，就不該再用它們。少數例外會寫在文件裡，例如 io.Reader 的 Read 可能同時回傳讀到的 n 個 byte 和一個錯誤。
  • errors.New("…") 建立一個固定訊息的錯誤，fmt.Errorf 用格式化的方式建立，例如加上使用者輸入的值。
  • 錯誤訊息會被一層一層串起來，所以 Go 的慣例是：英文小寫開頭、結尾不加句號，內容寫「在做什麼、對誰、為什麼失敗」。strconv.Atoi: parsing "四": invalid syntax 就是標準庫的示範。

這和 Java 的例外差很多：錯誤寫在函式簽名上，看得到；處理錯誤的流程就是一般的 if，沒有看不見的跳躍。代價是程式裡會有很多 if err != nil。這是刻意的取捨：Go 要你在每一個可能失敗的地方，明確決定要怎麼辦。

2. sentinel error

呼叫的人常常需要分辨是哪一種錯誤：賣完了要請客人改點別的，菜單上沒有的東西則是輸入有問題。最簡單的做法是在 package 層級事先建立幾個錯誤值，叫做 sentinel error，名稱慣例用 Err 開頭：

var (
	ErrSoldOut   = errors.New("賣完了")
	ErrNotOnMenu = errors.New("菜單上沒有")
)

type dish struct {
	price int
	left  int
}

var menu = map[string]dish{
	"排骨飯": {price: 85, left: 10},
	"雞腿飯": {price: 95, left: 0},
}

func price(name string) (int, error) {
	d, ok := menu[name]
	if !ok {
		return 0, ErrNotOnMenu
	}
	if d.left == 0 {
		return 0, ErrSoldOut
	}
	return d.price, nil
}

func sentinelDemo() {
	for _, name := range []string{"排骨飯", "雞腿飯", "珍奶"} {
		p, err := price(name)
		switch {
		case err == nil:
			fmt.Println(name, p)
		case errors.Is(err, ErrSoldOut):
			fmt.Println(name, "今天賣完了，明天請早")
		default:
			fmt.Printf("%s 錯誤：%v\n", name, err)
		}
	}
}

輸出

排骨飯 85
雞腿飯 今天賣完了，明天請早
珍奶 錯誤：菜單上沒有
  • 比對 sentinel 用 errors.Is(err, ErrSoldOut)。為什麼不直接寫 err == ErrSoldOut，下一節就會看到。
  • sentinel 必須是同一個值：每次呼叫 errors.New 都會產生一個新的錯誤，就算訊息一模一樣也不相等。所以它一定是 package 層級的變數，只建立一次。
  • 標準庫的例子：io.EOF（讀到結尾，其實是「沒有更多資料了」的訊號）、fs.ErrNotExist（檔案不存在，os.Open 回傳的錯誤可以用 errors.Is(err, fs.ErrNotExist) 判斷）、context.Canceled。
  • 匯出的 sentinel 是 API 的一部分：別人的程式會開始依賴它，之後就不能隨便拿掉或改變意思。只有呼叫的人真的需要分辨時，才匯出。

3. 包裝：%w 與錯誤鏈

只回傳「賣完了」，最上層的人不知道是哪一張單、哪一道菜。每一層應該補上自己知道的資訊再往上傳。fmt.Errorf 的 %w 動詞會產生一個新的錯誤：訊息照格式組好，同時把原本的錯誤包在裡面：

func quote(name string, qty int) (int, error) {
	p, err := price(name)
	if err != nil {
		return 0, fmt.Errorf("報價 %s：%w", name, err)
	}
	return p * qty, nil
}

func placeOrder(no int, name string, qty int) error {
	total, err := quote(name, qty)
	if err != nil {
		return fmt.Errorf("訂單 %d：%w", no, err)
	}
	fmt.Println("訂單", no, "合計", total)
	return nil
}

func wrapDemo() {
	err := placeOrder(17, "雞腿飯", 2)
	fmt.Println(err)
	fmt.Println(err == ErrSoldOut, errors.Is(err, ErrSoldOut))

	for e := err; e != nil; e = errors.Unwrap(e) {
		fmt.Printf("%T：%v\n", e, e)
	}
}

輸出

訂單 17：報價 雞腿飯：賣完了
false true
*fmt.wrapError：訂單 17：報價 雞腿飯：賣完了
*fmt.wrapError：報價 雞腿飯：賣完了
*errors.errorString：賣完了
  • 印出來的訊息從外到內讀起來就像一條路徑：訂單 17，在報價雞腿飯的時候，發現賣完了。每一層只加自己的部分，不要再加「失敗」「錯誤」這種字，串起來才不會囉嗦。
  • 包裝之後，err 已經不是 ErrSoldOut 本身了，== 是 false。errors.Is 會呼叫 errors.Unwrap 一層一層拆開，每一層都比對一次，所以找得到。比對錯誤一律用 errors.Is，不管現在有沒有包裝，以後有人加上包裝也不會壞。
  • 最後的迴圈自己用 Unwrap 拆給你看：兩層 *fmt.wrapError（%w 產生的型別），最裡面是 errors.New 產生的 *errors.errorString。平常不需要自己拆，交給 errors.Is 和 errors.As 就好。

深入：第一次讀可以先跳過

3.1 %w 還是 %v

func wrapVsFormat() {
	_, err := price("雞腿飯")
	w := fmt.Errorf("報價：%w", err)
	v := fmt.Errorf("報價：%v", err)
	fmt.Println(w, errors.Is(w, ErrSoldOut))
	fmt.Println(v, errors.Is(v, ErrSoldOut))
}

輸出

報價：賣完了 true
報價：賣完了 false

兩個錯誤印出來一模一樣，差別在 %v 只把訊息變成文字，原本的錯誤沒有被包進去，errors.Is 就找不到了。

那什麼時候該故意用 %v？用 %w 包裝等於把裡面的錯誤公開給呼叫的人：假設你的 package 裡面用了某個資料庫，把資料庫的錯誤用 %w 包出去，呼叫的人就可能開始寫 errors.Is(err, 資料庫的某個錯誤)，以後你換資料庫，他們的程式就壞了。這種內部實作的細節，應該翻譯成你自己的 sentinel（例如 ErrNotFound）再回傳，或用 %v 只留下文字。

Go 1.20 起，一個 fmt.Errorf 裡可以用好幾個 %w，產生的錯誤同時包著好幾個原因，errors.Is 會每一個都找。這種錯誤的 Unwrap 方法回傳的是 []error，所以 errors.Unwrap 對它回傳 nil，要走訪就得自己處理兩種 Unwrap（練習 5）。

4. 自訂錯誤型別

庫存不夠時，呼叫的人可能想告訴客人「只剩 3 份」。這種需要攜帶資料的錯誤，就定義一個 struct 型別，替它寫 Error 方法：

type StockError struct {
	Item string
	Left int
}

func (e *StockError) Error() string {
	return fmt.Sprintf("%s 只剩 %d 份", e.Item, e.Left)
}

var stock = map[string]int{"排骨飯": 3, "雞腿飯": 0}

func reserve(item string, qty int) error {
	if left := stock[item]; qty > left {
		return &StockError{Item: item, Left: left}
	}
	return nil
}

Error 用指標 receiver，所以滿足 error 的是 *StockError，回傳時寫 &StockError{…}。reserve 沒問題時直接寫 return nil，避開 10 章的 nil 陷阱。

讓自己的型別也能包裝：Unwrap

type OrderError struct {
	No  int
	Err error
}

func (e *OrderError) Error() string {
	return fmt.Sprintf("訂單 %d：%v", e.No, e.Err)
}

func (e *OrderError) Unwrap() error {
	return e.Err
}

func asDemo() {
	err := &OrderError{No: 18, Err: reserve("排骨飯", 5)}
	fmt.Println(err)

	var se *StockError
	if errors.As(err, &se) {
		fmt.Println("As", se.Item, se.Left)
	}

	if se, ok := errors.AsType[*StockError](err); ok {
		fmt.Println("AsType", se.Item, se.Left)
	}
}

輸出

訂單 18：排骨飯 只剩 3 份
As 排骨飯 3
AsType 排骨飯 3
  • OrderError 有一個 Unwrap() error 方法，回傳它包著的錯誤。errors.Is、errors.As 拆錯誤鏈時，就是在呼叫這個方法，所以自己的型別只要寫了 Unwrap，就和 %w 一樣能參與錯誤鏈。
  • errors.As(err, &se) 是傳統寫法：先宣告一個目標變數，傳它的地址進去，找到型別相符的錯誤時，As 把它存進 se 並回傳 true。
  • errors.AsType[*StockError](err) 是 Go 1.26 加入的泛型版本：把要找的型別寫在中括號裡，直接回傳找到的值和 ok，不必先宣告變數，型別寫錯在編譯時就會發現。新程式用它；go fix 會建議把 errors.As 改成這個寫法，本章刻意保留一個 errors.As 來對照。中括號的語法在 12 泛型說明。

三種錯誤，怎麼選

種類呼叫的人需要什麼怎麼做
不透明的錯誤只需要知道失敗了，訊息給人看fmt.Errorf("…：%w", err) 或 errors.New，不匯出任何東西
sentinel要分辨是哪一種匯出 var ErrX = errors.New(…)，用 errors.Is 比對
錯誤型別要分辨，還要取出細節匯出 struct 型別，用 errors.AsType 取出

大部分的錯誤應該是第一種。每匯出一個 sentinel 或錯誤型別，就多一個要長期維護的承諾，所以等到有人真的需要分辨時才加。

5. 一次回報多個錯誤：errors.Join

var ErrBadPhone = errors.New("電話要 10 碼")

type Booking struct {
	Name   string
	People int
	Phone  string
}

func validate(b Booking) error {
	var errs []error
	if b.Name == "" {
		errs = append(errs, errors.New("要留名字"))
	}
	if b.People < 1 || b.People > 12 {
		errs = append(errs, fmt.Errorf("人數 %d 不在 1 到 12 之間", b.People))
	}
	if len(b.Phone) != 10 {
		errs = append(errs, ErrBadPhone)
	}
	return errors.Join(errs...)
}

func joinDemo() {
	err := validate(Booking{People: 20, Phone: "0912"})
	fmt.Println(err)
	fmt.Println(errors.Is(err, ErrBadPhone))
	fmt.Println(validate(Booking{Name: "王小明", People: 4, Phone: "0912345678"}))
}

輸出

要留名字
人數 20 不在 1 到 12 之間
電話要 10 碼
true
<nil>

驗證表單時，一次只回報第一個問題，使用者就得改一次、送一次、再看到下一個問題。validate 把所有問題收集起來，最後交給 errors.Join（Go 1.20 起）：

  • Error() 把每個錯誤的訊息用換行接起來。
  • errors.Is、errors.As 會檢查裡面的每一個錯誤，所以 ErrBadPhone 找得到。
  • 傳進去的錯誤全部是 nil，或一個都沒有時，回傳 nil。所以 validate 不用特別判斷 errs 是不是空的，最後一行就能同時處理兩種情況。

6. Close 也會失敗

檔案、網路連線、HTTP 回應的 Body 用完都要 Close，而 Close() error 也會回傳錯誤。對寫入來說這個錯誤很重要：寫進去的資料可能還在緩衝區裡，Close 時才真正寫出去，這時候發生的錯誤（例如磁碟滿了）只能從 Close 拿到。直接寫 defer w.Close() 會把它丟掉，呼叫的人以為存好了，資料其實不見了。

type receiptFile struct {
	closeErr error
}

func (f *receiptFile) Write(p []byte) (int, error) {
	return len(p), nil
}

func (f *receiptFile) Close() error {
	return f.closeErr
}

func saveReceipt(w io.WriteCloser, total int) (err error) {
	defer func() {
		err = errors.Join(err, w.Close())
	}()
	_, err = fmt.Fprintf(w, "合計 %d 元\n", total)
	return err
}

func closeDemo() {
	fmt.Println(saveReceipt(&receiptFile{}, 290))
	fmt.Println(saveReceipt(&receiptFile{closeErr: errors.New("磁碟滿了，收據沒有存進去")}, 290))
}

輸出

<nil>
磁碟滿了，收據沒有存進去
  • receiptFile 是一個假的 io.WriteCloser，用來模擬「寫入成功、關閉失敗」，不必真的把磁碟塞滿（10 章的假實作）。
  • saveReceipt 的回傳值有名字 (err error)，defer 裡的函式在 return 之後執行，還能修改它（04 章）。
  • errors.Join(err, w.Close())：兩個都是 nil 就是 nil；只有一個有錯就是那一個；兩個都有錯就兩個都留著。
  • 只讀不寫的檔案，Close 失敗通常不影響結果，直接 defer f.Close() 是常見而且可以接受的寫法。檔案的完整用法在 20 章「檔案與 I/O」。

7. 什麼時候用 panic

panic 的機制在 04 章已經看過了。這裡要回答的是什麼時候該用它。判斷的方法是問：這個失敗是誰的錯？

  • 使用者打錯字、檔案被刪掉、網路斷線、便當賣完，這些都是正常運作中一定會遇到的狀況，程式應該好好處理，所以回傳 error。
  • 索引超出範圍、對 nil map 寫入、走到了「照理說不可能」的 switch 分支，代表程式本身寫錯了，繼續執行只會產生更難追的錯誤，這時候 panic。Go 執行時期自己發出的 panic 都屬於這一類。

Must 模式

func mustPrice(name string) int {
	p, err := price(name)
	if err != nil {
		panic(fmt.Sprintf("mustPrice(%q)：%v", name, err))
	}
	return p
}

var comboPrice = mustPrice("排骨飯") + 25

func mustDemo() {
	fmt.Println(comboPrice)

	defer func() {
		fmt.Println("panic:", recover())
	}()
	fmt.Println(mustPrice("珍奶"))
}

輸出

110
panic: mustPrice("珍奶")：菜單上沒有

有些值是寫死在程式裡的，例如套餐的價格建立在「排骨飯」這個品名上。如果查不到，那是寫程式的人打錯字，不是執行時的意外。這時候可以提供一個 mustX 版本：成功就直接回傳值，失敗就 panic。搭配 package 層級的變數使用，打錯字時程式一啟動就會當掉，不會等到客人點餐才發現。標準庫的 regexp.MustCompile、template.Must 都是這個模式。

在邊界 recover

不要用 recover 來處理一般的錯誤。它真正的用途是在邊界保護整個程式：例如 HTTP 伺服器處理每一個請求時，net/http 會 recover 那個請求裡發生的 panic，記錄下來，然後繼續服務其他請求，一個有 bug 的請求不會讓整個伺服器停掉。自己寫的程式很少需要 recover；需要時，也只在這種最外層的地方使用。

8. 分層處理錯誤

func statusFor(err error) int {
	switch {
	case err == nil:
		return http.StatusOK
	case errors.Is(err, ErrNotOnMenu):
		return http.StatusNotFound
	case errors.Is(err, ErrSoldOut):
		return http.StatusConflict
	}
	if _, ok := errors.AsType[*StockError](err); ok {
		return http.StatusConflict
	}
	return http.StatusInternalServerError
}

func layersDemo() {
	errs := []error{
		nil,
		fmt.Errorf("訂單 19：%w", ErrNotOnMenu),
		&OrderError{No: 20, Err: reserve("排骨飯", 5)},
		errors.New("資料庫連不上"),
	}
	for _, err := range errs {
		fmt.Println(statusFor(err), err)
	}
}

輸出

200 <nil>
404 訂單 19：菜單上沒有
409 訂單 20：排骨飯 只剩 3 份
500 資料庫連不上

真實的程式通常分好幾層：存取資料的、處理商業邏輯的、對外提供 HTTP 介面的。錯誤在各層之間流動時，有幾條原則：

  • 每一層只補自己知道的事，用 %w 往上傳。quote 知道品名，placeOrder 知道訂單號碼，它們都不知道最後會怎麼回應使用者，也不需要知道。
  • 只處理一次。「處理」是指記 log、重試、改用預設值、回應使用者這類動作。中間層如果記了 log 又把錯誤往上傳，上一層再記一次，同一個錯誤就會在 log 裡出現好幾次，反而更難追。要嘛處理，要嘛回傳，不要兩個都做。
  • 在邊界翻譯。只有最外層知道「這是 HTTP」或「這是命令列」，所以只有它把錯誤翻譯成 404、409、500 或程式的結束碼。statusFor 用 errors.Is 和 errors.AsType 判斷種類，不管錯誤被包了幾層。
  • 給客人看的和給開發者看的分開。500 的時候，log 要記下完整的錯誤鏈；回應給客人的只要「系統忙碌，請稍後再試」，不要把「資料庫連不上」這種內部細節送出去。
  • 不要比對 Error() 的文字。訊息是給人看的，隨時可能改寫；而且不同的錯誤可能剛好寫著一樣的字。練習 6 就是這個 bug。

HTTP 伺服器怎麼把這些接起來，會在 HTTP 服務那一章看到；log 的寫法在「日誌」那一章。

常見錯誤

1. 拿到 error 卻不檢查

n, _ := strconv.Atoi(s) 把錯誤丟掉，輸入不對時 n 是 0，程式卻繼續往下跑（04 章）。真的確定不會失敗才這樣寫，而且最好加一行註解說明為什麼。

2. 比對 Error() 的文字

err.Error() == "賣完了"：包裝過就比不到，別的錯誤剛好寫著一樣的字又會誤判，err 是 nil 時還會 panic。用 errors.Is（第 8 節、練習 6）。

3. 該用 %w 的地方用了 %v

印出來一樣，錯誤鏈卻斷了，上層的 errors.Is 永遠是 false（3.1 節）。要讓上層判斷就用 %w；故意隱藏內部細節時才用 %v。

4. 記了 log 又回傳

同一個錯誤在 log 裡出現好幾次，每一次的前後文還不太一樣，追查時更混亂。只在最外層處理一次（第 8 節）。

5. errors.As 的第二個參數不是指標

package main

import (
	"errors"
	"fmt"
)

type StockError struct {
	Item string
	Left int
}

func (e *StockError) Error() string {
	return fmt.Sprintf("%s 只剩 %d 份", e.Item, e.Left)
}

func main() {
	var err error = &StockError{Item: "排骨飯", Left: 3}
	var se *StockError
	if errors.As(err, se) {
		fmt.Println(se.Item, se.Left)
	}
}

go vet

main.go:20:5: second argument to errors.As must be a non-nil pointer to either a type that implements error, or to any interface type

這支程式編譯得過，執行時 errors.As 卻會 panic。要傳 &se，也就是「指向 *StockError 的指標」。go vet 抓得到這個錯誤；改用 errors.AsType[*StockError](err) 則從根本上避開它。

6. 回傳裝著 nil 指標的 error

先宣告 var e *StockError，最後 return e，呼叫的人看到的 err 永遠不是 nil（10 章）。沒有錯誤就直接 return nil。

7. 寫入之後丟掉 Close 的錯誤

defer w.Close() 用在寫入的檔案上，磁碟滿了也不會知道（第 6 節、練習 7）。用具名回傳值加 errors.Join。

8. 用 panic 處理預期中的錯誤

使用者輸入錯誤就 panic，呼叫的人只能用 recover 接，程式變得難以理解（04 章）。預期中的失敗一律回傳 error（第 7 節）。

重點回顧

  • error 是只有 Error() string 的 interface，放在回傳值的最後一個；nil 代表成功。
  • 呼叫完立刻檢查 if err != nil；失敗時不要使用其他回傳值。
  • sentinel error 是 package 層級的 ErrX 變數，讓呼叫的人分辨種類。
  • 用 fmt.Errorf("…：%w", err) 補上這一層的資訊再往上傳；%v 會切斷錯誤鏈。
  • 比對用 errors.Is，取出型別用 errors.AsType（舊寫法 errors.As），不要比對文字。
  • 自己的錯誤型別寫了 Unwrap 方法，就能參與錯誤鏈。
  • 大部分錯誤不必匯出；需要分辨時才匯出 sentinel，需要細節時才匯出型別。
  • errors.Join 一次回報多個錯誤，全部是 nil 時回傳 nil。
  • 寫入之後，用具名回傳值和 defer 把 Close 的錯誤也收進來。
  • 外界造成的失敗回傳 error；程式自己寫錯才 panic；recover 只放在邊界。
  • 錯誤在中間層只包裝，在最外層處理一次、翻譯成狀態碼或結束碼。
