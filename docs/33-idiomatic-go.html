本章你會學到

  • 從呼叫端的角度取名字：package 名稱、匯出名稱、縮寫、getter、receiver。
  • 寫出 go doc 和 pkg.go.dev 能好好呈現的 doc comment，包括標題、連結和 Deprecated。

1. 命名

Go 的命名規則不多，但社群幾乎都照著做，所以違反時特別顯眼。這一章的主角是 ticket 這個 package，一台排隊叫號機。先從外面看它長什麼樣子：

go doc ./chapters/33-idiomatic-go/ticket Machine

輸出

package ticket // import "github.com/xinqilin/GO-Playground/chapters/33-idiomatic-go/ticket"

type Machine struct {
	// Has unexported fields.
}
    Machine 是一台叫號機。零值是一台還沒有人取號的叫號機。Machine 開始使用後不能再複製。

func (m *Machine) Call() (int, error)
func (m *Machine) Called() []int
func (m *Machine) Remaining() int
func (m *Machine) Take() int
func (m *Machine) Waiting() int

呼叫端寫出來是 var m ticket.Machine、m.Take()、m.Waiting()，讀起來像一句話。幾條規則：

  • package 名稱：短、全小寫、一個單字，不用底線也不用 MixedCaps，例如 ticket、parking、strconv。它是名稱的一部分：呼叫端看到的是 ticket.Machine，所以型別不必再叫 TicketMachine（練習 1）。避免 util、common、helpers 這種什麼都能放的名字，它說明不了裡面有什麼。
  • MixedCaps：多個字的名稱用大小寫分開，不用底線：orderCount、OrderCount。開頭的大小寫決定是否匯出（29 章）。
  • 縮寫整個大寫或整個小寫：UserID、ParseURL、HTTPServer、未匯出時 apiKey，不寫成 UserId、ParseUrl（練習 5）。
  • getter 不加 Get：讀取用 Waiting()，不是 GetWaiting()；設定才用 SetX。
  • 單一方法的 interface 用 -er 結尾：Reader、Writer、Stringer，以及本章的 waiter。
  • receiver 名稱：一兩個字母，取型別名稱的開頭，同一個型別的每個方法都用同一個：func (m *Machine)。不要用 this、self。
  • 錯誤：sentinel error 叫 ErrXxx，錯誤型別叫 XxxError（11 章）。

這本手冊的識別字一律用英文，註解和字串用中文。Go 允許中文識別字，但中文沒有大小寫，沒辦法表達「匯出」，混用也會讓搜尋和 code review 變得困難。

2. doc comment

每個匯出的名稱都要有 doc comment：緊接在宣告前面、中間不空行，第一句以名稱開頭，說明它「做什麼」，而不是「怎麼做」。package 本身的說明寫在 package 子句前面，以「Package 名稱」開頭。整個 ticket package：

// Package ticket 是排隊叫號機：取號、叫號，以及查詢還有幾個人在等。
//
// [Machine] 的零值就可以直接使用，也可以同時被多個 goroutine 使用：
//
//	var m ticket.Machine
//	n := m.Take()
//
// # 號碼
//
// 號碼從 1 開始依序發出，叫號的順序和取號的順序相同。叫過的號碼可以用 [Machine.Called] 查詢。
package ticket

import (
	"errors"
	"slices"
	"sync"
)

// ErrNoOneWaiting 表示目前沒有人在等，叫不到號。
var ErrNoOneWaiting = errors.New("ticket: 沒有人在等")

// Machine 是一台叫號機。零值是一台還沒有人取號的叫號機。Machine 開始使用後不能再複製。
type Machine struct {
	mu     sync.Mutex
	issued int
	called []int
}

// Take 取一張號碼牌，回傳它的號碼。
func (m *Machine) Take() int {
	m.mu.Lock()
	defer m.mu.Unlock()
	m.issued++
	return m.issued
}

// Call 叫下一號並回傳號碼。沒有人在等時回傳 [ErrNoOneWaiting]。
func (m *Machine) Call() (int, error) {
	m.mu.Lock()
	defer m.mu.Unlock()
	if len(m.called) == m.issued {
		return 0, ErrNoOneWaiting
	}
	n := len(m.called) + 1
	m.called = append(m.called, n)
	return n, nil
}

// Waiting 回傳還在等的人數。
func (m *Machine) Waiting() int {
	m.mu.Lock()
	defer m.mu.Unlock()
	return m.issued - len(m.called)
}

// Called 回傳叫過的號碼，依叫號的順序。回傳的是複本，修改它不會影響 m。
func (m *Machine) Called() []int {
	m.mu.Lock()
	defer m.mu.Unlock()
	return slices.Clone(m.called)
}

// Remaining 回傳還在等的人數。
//
// Deprecated: 改用 [Machine.Waiting]。
func (m *Machine) Remaining() int {
	return m.Waiting()
}

# 號碼

號碼從 1 開始依序發出，叫號的順序和取號的順序相同。叫過的號碼可以用 Machine.Called 查詢。

type Machine struct{ ... }
  • 格式（Go 1.19 起）：以 # 開頭的一行是標題；縮排的行是程式碼；[Machine.Called] 這種方括號是連到其他名稱的連結，在 pkg.go.dev 上可以點；以 - 開頭的行是清單。gofmt 會自動調整 doc comment 的格式。
  • Deprecated：以 Deprecated: 開頭的段落表示不要再用，並說明改用什麼。Remaining 就是一個例子。有些工具會在你呼叫它時提醒，pkg.go.dev 預設會把它的說明收起來。
  • 中文的段落寫在同一行：go doc 會把段落裡的換行換成空白，中文句子之間就多了一個空格（32 章的 go doc 輸出就是這樣）。一個段落寫成一行，輸出才會整齊。
  • Example 也是文件：ticket_test.go 的 ExampleMachine 會出現在 pkg.go.dev 上，而且 go test 會驗證它的輸出，永遠不會過期（30 章）。
  • 寫給呼叫的人看：參數的限制、錯誤什麼時候發生、能不能同時被多個 goroutine 使用、零值能不能用。內部的實作細節寫在函式裡面的註解。

3. 零值就能用

標準庫裡很多型別的零值都能直接用。這是 Go 刻意的設計，你自己的型別也應該盡量做到：

func zeroDemo() {
	var m ticket.Machine
	m.Take()
	m.Take()
	fmt.Printf("叫號機：%d 人在等\n", m.Waiting())

	var b strings.Builder
	b.WriteString("排骨飯")
	b.WriteString(" x2")
	fmt.Printf("strings.Builder：%s\n", b.String())

	var mu sync.Mutex
	mu.Lock()
	mu.Unlock()
	fmt.Println("sync.Mutex：零值是沒有上鎖的鎖")

	var orders []string
	orders = append(orders, "滷肉飯")
	fmt.Printf("nil slice 也能 append：%v\n", orders)

	var prices map[string]int
	fmt.Printf("nil map 可以讀：%d，寫入會 panic\n", prices["排骨飯"])
}
叫號機：2 人在等
strings.Builder：排骨飯 x2
sync.Mutex：零值是沒有上鎖的鎖
nil slice 也能 append：[滷肉飯]
nil map 可以讀：0，寫入會 panic
  • map 是例外：nil map 可以讀，寫入會 panic（07 章）。需要 map 的型別，在第一次寫入時才建立，讀取時不用特別處理。練習 3 的 Tally 就是這樣。
  • 零值不合理時才寫 New：例如一定要給資料庫連線、一定要有的設定。New 回傳 *T，而且讓呼叫端不可能拿到一半初始化的物件。
  • 選項很多時，有兩種常見的寫法：傳一個 Config struct（零值欄位代表預設值），或用 functional options：New(WithPrefix("B"), WithWidth(2))，每個選項是一個修改設定的函式，沒給的就用預設值。練習 4 實作後者。兩種都比十個參數的 New 好讀。
  • 文件要寫清楚零值能不能用，ticket 的 package 說明和 Machine 的說明都寫了。

4. 接受 interface，回傳具體型別

看板只需要知道每個櫃台有幾個人在等。它不依賴 *ticket.Machine，而是定義一個只有 Waiting 方法的 interface：

type waiter interface {
	Waiting() int
}

func busiest(counters map[string]waiter) string {
	best, most := "", -1
	for _, name := range slices.Sorted(maps.Keys(counters)) {
		if n := counters[name].Waiting(); n > most {
			best, most = name, n
		}
	}
	return best
}

func printBoard(w io.Writer, counters map[string]waiter) error {
	for _, name := range slices.Sorted(maps.Keys(counters)) {
		if _, err := fmt.Fprintf(w, "%s櫃台：%d 人在等\n", name, counters[name].Waiting()); err != nil {
			return err
		}
	}
	return nil
}

func interfaceDemo() {
	var pay, pickup ticket.Machine
	for range 3 {
		pay.Take()
	}
	pickup.Take()
	counters := map[string]waiter{"結帳": &pay, "取餐": &pickup}
	printBoard(os.Stdout, counters)
	fmt.Printf("最忙的是：%s\n", busiest(counters))
}
取餐櫃台：1 人在等
結帳櫃台：3 人在等
最忙的是：結帳

測試時不用真的取號，給一個假的就好：

type fakeWaiter int

func (f fakeWaiter) Waiting() int { return int(f) }

func TestBusiest(t *testing.T) {
	tests := []struct {
		name     string
		counters map[string]waiter
		want     string
	}{
		{"最多的", map[string]waiter{"結帳": fakeWaiter(2), "取餐": fakeWaiter(5)}, "取餐"},
		{"一樣多取名稱在前的", map[string]waiter{"結帳": fakeWaiter(3), "取餐": fakeWaiter(3)}, "取餐"},
		{"都沒有人", map[string]waiter{"結帳": fakeWaiter(0)}, "結帳"},
		{"沒有櫃台", nil, ""},
	}
	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			if got := busiest(tt.counters); got != tt.want {
				t.Errorf("busiest = %q，想要 %q", got, tt.want)
			}
		})
	}
}
  • 接受 interface：printBoard 收 io.Writer，所以能寫到終端機、檔案、HTTP 回應，TestPrintBoard 還用一個每次都失敗的 Writer 測試錯誤的處理。參數用你需要的最小 interface。
  • 回傳具體型別：ticket 回傳 *Machine，不是某個 interface。呼叫端能用它所有的方法，之後加新方法也不會破壞任何人；需要抽象時，呼叫端自己定義 interface。例外是 error，以及刻意隱藏多種實作的情況。
  • 不要為了「以後可能會換」先寫 interface。只有一個實作的 interface 只是多一層跳轉。真的出現第二個實作，或測試需要替換時再加，Go 的隱式滿足讓這件事很便宜。
  • interface 越小越好用：io.Reader 只有一個方法，所以幾乎什麼都能當 Reader。

5. 正常流程靠左

兩個函式做的事完全一樣，main_test.go 的 TestServeSame 在各種情況下比對它們的結果：

func serveNested(m *ticket.Machine, counter string) (string, error) {
	if counter != "" {
		n, err := m.Call()
		if err == nil {
			msg := fmt.Sprintf("請 %d 號到%s櫃台", n, counter)
			if w := m.Waiting(); w >= 3 {
				msg += fmt.Sprintf("，後面還有 %d 位", w)
			}
			return msg, nil
		} else {
			return "", fmt.Errorf("%s櫃台：%w", counter, err)
		}
	} else {
		return "", errNoCounter
	}
}

func serve(m *ticket.Machine, counter string) (string, error) {
	if counter == "" {
		return "", errNoCounter
	}
	n, err := m.Call()
	if err != nil {
		return "", fmt.Errorf("%s櫃台：%w", counter, err)
	}
	msg := fmt.Sprintf("請 %d 號到%s櫃台", n, counter)
	if w := m.Waiting(); w >= 3 {
		msg += fmt.Sprintf("，後面還有 %d 位", w)
	}
	return msg, nil
}
func flowDemo() {
	var m ticket.Machine
	for range 4 {
		m.Take()
	}
	for _, counter := range []string{"結帳", "結帳", "", "取餐", "取餐", "取餐"} {
		msg, err := serve(&m, counter)
		switch {
		case errors.Is(err, ticket.ErrNoOneWaiting):
			fmt.Printf("沒有人在等：%v\n", err)
		case err != nil:
			fmt.Printf("錯誤：%v\n", err)
		default:
			fmt.Println(msg)
		}
	}
}

  • 先處理例外，然後 return。if 的區塊以 return 結束時，不要再寫 else；正常的流程留在最外層。
  • 錯誤加上脈絡再往上傳：fmt.Errorf("%s櫃台：%w", counter, err) 告訴讀錯誤訊息的人是哪個櫃台，%w 讓上層仍然能用 errors.Is 判斷（輸出的最後一行）。
  • 錯誤只處理一次：要嘛往上傳，要嘛在這裡處理（記 log、重試、換預設值），不要記了 log 又往上傳，同一個錯誤會在 log 裡出現好幾次。
  • 錯誤訊息的寫法：會被串在別的訊息後面，所以英文的錯誤訊息開頭不大寫、結尾不加標點。標準庫的錯誤常以 package 名稱開頭，例如 bufio.ErrBufferFull 的訊息是 bufio: buffer full，ticket 也照這個習慣。
  • panic 只用在「程式本身有 bug」的情況，不用來處理可以預期的錯誤（11 章）。

6. 在邊界上複製

ticket 的 Called 回傳 slices.Clone(m.called)。呼叫端改了拿到的 slice，叫號機裡的紀錄不受影響：

func calledDemo() {
	var m ticket.Machine
	for range 3 {
		m.Take()
	}
	m.Call()
	m.Call()
	got := m.Called()
	got[0] = 99
	fmt.Printf("改過的複本：%v\n", got)
	fmt.Printf("叫號機裡的：%v\n", m.Called())
}
改過的複本：[99 2]
叫號機裡的：[1 2]
  • 兩個方向都要注意：把收到的 slice 存起來（例如建構函式的參數）也一樣，呼叫端之後改了它，你的內部狀態就跟著變。練習 6 的兩個 bug 剛好是這兩個方向。
  • 不是每次都要複製。複製有成本，只在「資料離開或進入你的控制範圍、而且之後還會被改」的地方做，並在文件寫清楚（Called 的說明寫了「回傳的是複本」）。
  • 鎖不要外露：Machine 用具名欄位 mu sync.Mutex，而不是直接嵌入 sync.Mutex。嵌入的話 Lock、Unlock 會變成 Machine 公開的方法，任何人都能從外面鎖住它（17 章）。
  • 讓呼叫端決定要不要並行：Take、Call 都是同步的函式，呼叫端想用 goroutine 自己開。函式庫自己開 goroutine 時，要提供停止它的方法（例如接受 context），不然很容易洩漏（18 章）。
  • 需要 context 的函式，ctx 放第一個參數，不要存在 struct 裡。

7. 專案的目錄結構

Go 沒有規定目錄結構，go 指令只在乎 module 和 package。官方的建議很簡單：從最小的結構開始，需要時才分。

  • 一支小程式：go.mod 加上幾個 .go 檔，全部是 package main，放在根目錄。這本手冊的每一章就是這樣。
  • 程式變大：把邏輯分到 internal/ 底下的 package，main 只負責讀參數、組裝、啟動。internal 底下的 package 只有這個 module 能 import，你可以隨時改它的 API（29 章）。
  • 好幾支程式：每支程式一個 cmd/名稱/ 目錄。go install example.com/kiosk/cmd/kiosk@latest 裝出來的執行檔就叫 kiosk。
  • 要給別人 import 的函式庫：package 放在根目錄或有意義的子目錄。沒有必要多一層 pkg/。
  • 依職責分 package，不是依種類：queue、display 各自負責一件事。不要開 models、utils、interfaces 這種依「是什麼東西」分類的 package，它們會互相 import，最後變成 import cycle。

kiosk 是 testdata 裡一個完整的 module：

review 的重點是「這段程式明年的同事讀得懂、改得動嗎」，而不是挑出所有和自己習慣不同的地方。工具能統一的（格式、import 順序）不要花時間討論；真正值得討論的是命名、邊界和錯誤處理。

常見錯誤

1. 名稱重複了 package 名稱

ticket.TicketMachine、user.UserService。呼叫端已經寫了 package 名稱，型別名稱只要說剩下的部分（第 1 節，練習 1）。

2. 照 Java 的習慣寫 getter 和 setter

每個欄位都配一對 GetX、SetX。讀取的方法直接叫 X；不需要從外面改的欄位，就不要提供 SetX。很多時候直接匯出欄位就好。

3. 在提供功能的 package 裡先宣告 interface

寫了 Machine 又寫一個 MachineInterface，然後所有地方都用 interface。interface 交給使用端定義（第 4 節）。

4. 零值不能用，又沒有說

型別裡有 map，使用者 var t Tally 之後第一次 Add 就 panic。讓零值能用，或者提供 New 並在文件寫清楚（第 3 節，練習 3）。

5. if 以 return 結束，後面還接 else

正常流程被推到右邊，錯誤處理離條件越來越遠（第 5 節）。

6. 把內部的 slice、map 直接交出去或存起來

呼叫端一改，你的內部狀態就壞了，而且很難追（第 6 節，練習 6）。

7. 在匯出的 struct 裡嵌入 sync.Mutex

Lock、Unlock 變成公開的 API。用不匯出的具名欄位 mu sync.Mutex（第 6 節）。

8. 開一個 utils package 放所有東西

名稱說明不了內容，所有 package 都 import 它，最後誰都不敢改。依職責取名，或乾脆放回用它的那個 package（第 1、7 節）。

從 Java 轉過來最常見的「口音」，是把 Java 的設計模式原樣搬過來：每個類別配一個 interface、工廠和 Builder、很深的 package 階層、到處都是 getter。這些在 Java 有它的理由（例如框架需要 interface 來產生代理），在 Go 通常只是多出來的程式碼。先寫最直接的版本，等真的需要時再加抽象。

  1. 入門練習 1：名稱有沒有重複 package

    第 1 節的規則寫成程式。注意 time.Time 這種同名的情況不算。

    func Stutters(pkg, name string) bool {
	// TODO: 實作
	return false
}

    測試：TestStutters。

    提示

    strings.EqualFold 不分大小寫比較。package 名稱都是 ASCII，可以直接切 name[:len(pkg)]，但要先確認 name 比 pkg 長。後面那個字用 unicode.IsUpper 判斷。

  2. 入門練習 2：檢查 doc comment

    第 2 節的規則：以名稱開頭、是完整的句子。

    func DocProblems(name, doc string) []string {
	// TODO: 實作
	return nil
}

    測試：TestDocProblems。

    提示

    先 TrimSpace。「以名稱開頭」要連空白一起比，不然 FeeTable 也會被當成以 Fee 開頭。「。」是多個 byte 的字元，用 strings.HasSuffix 比較就不用管這件事。

  3. 進階練習 3：零值就能用的 Tally

    第 3 節：map 在第一次寫入時才建立。

    func (t *Tally) Add(dish string, n int) {
	// TODO: 實作
}

func (t *Tally) Count(dish string) int {
	// TODO: 實作
	return 0
}

func (t *Tally) Top(n int) []string {
	// TODO: 實作
	return nil
}

    測試：TestTally。

    提示

    Add 裡 if t.counts == nil { t.counts = make(…) }；Count 不用檢查，nil map 可以讀。Top 用 slices.SortedFunc(maps.Keys(t.counts), …)，比較函式用 cmp.Or 先比份數、再比菜名，最後用 min 決定要切幾個。

  4. 進階練習 4：functional options

    第 3 節提到的寫法：沒給的選項用預設值，後給的蓋過先給的。

    func WithPrefix(p string) Option {
	// TODO: 實作
	return func(*Machine) {}
}

func WithStart(n int) Option {
	// TODO: 實作
	return func(*Machine) {}
}

func WithWidth(w int) Option {
	// TODO: 實作
	return func(*Machine) {}
}

func New(opts ...Option) *Machine {
	// TODO: 實作
	return &Machine{}
}

func (m *Machine) Next() string {
	// TODO: 實作
	return ""
}

    測試：TestOptions。

    提示

    每個 WithX 回傳一個閉包：func(m *Machine) { m.prefix = p }。New 先建立有預設值的 Machine，再依序呼叫每個 opt。補零可以用 fmt.Sprintf("%0*d", width, n)：* 表示寬度從參數來。

  5. 挑戰練習 5：snake_case 轉 MixedCaps

    把資料庫欄位名稱轉成 Go 的欄位名稱時用得到，縮寫的規則是重點。

    func MixedCaps(snake string, exported bool) string {
	// TODO: 實作
	return ""
}

    測試：TestMixedCaps。

    提示

    strings.FieldsFunc(snake, func(r rune) bool { return r == '_' }) 會順便忽略連續和前後的底線。對每一段：是第一段而且不匯出就原樣寫入；在 Initialisms 裡就整個大寫；否則第一個字母大寫。

  6. 找錯練習 6：隊伍被外面改掉了

    第 6 節的兩個方向：收進來的 slice、交出去的 slice。

    func QueueOf(nums []int) *Queue {
	return &Queue{waiting: nums}
}

func (q *Queue) Join(n int) {
	q.waiting = append(q.waiting, n)
}

func (q *Queue) Waiting() []int {
	return q.waiting
}

    測試：TestQueueCopies。

    提示

    QueueOf 和 Waiting 都要用 slices.Clone。只修 Waiting 的話，呼叫端改了傳進來的 nums，或者 Join 時 append 寫進了呼叫端陣列裡多餘的容量，測試還是會失敗。

參考解答：先自己寫完再看。測試通過的寫法都是對的。

重點回顧

  • 名稱從呼叫端讀：package 名稱短而具體、不重複、縮寫一致、getter 不加 Get。
  • 每個匯出的名稱都有以名稱開頭的 doc comment；# 標題、[連結]、Deprecated: 段落。
  • 設計型別時先讓零值有意義；需要設定時用 Config struct 或 functional options。
  • 參數接受最小的 interface，回傳具體型別；interface 由使用端定義。
  • 先處理例外再 return，正常流程靠左；錯誤加上脈絡、只處理一次。
  • slice、map 跨過 API 邊界時複製；鎖不外露；讓呼叫端決定要不要並行。
  • 從一個 package 開始；多支程式用 cmd/，共用的放 internal/，依職責分 package。
  • review 前先跑 gofmt、vet、test -race；討論時把時間花在命名、邊界和錯誤處理。
