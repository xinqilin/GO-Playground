package 與 module

1. package 與 import

同一個 package 裡的檔案彼此看得到所有的名稱，不分大小寫；其他 package 只看得到大寫開頭的名稱。Go 沒有 public、private 關鍵字，這一條規則就是全部。這一章的 bento 是一個小 package，給 main 使用：

// Package bento 管理便當店的菜單。
//
// 對這一章的 main 來說，它是「別人寫的 package」：main 只能用這裡大寫開頭的名稱。
package bento

import (
	"errors"
	"maps"
	"slices"
)

// ErrBadPrice 表示價格不合理。
var ErrBadPrice = errors.New("價格要大於 0")

// Menu 是一份菜單。欄位沒有匯出，外面只能透過方法讀寫，所以價格不可能被改成負的。
type Menu struct {
	prices map[string]int
}

// New 建立一份空的菜單。
func New() *Menu {
	return &Menu{prices: make(map[string]int)}
}

// Add 加入一道菜；價格要大於 0。
func (m *Menu) Add(dish string, price int) error {
	if !valid(price) {
		return ErrBadPrice
	}
	m.prices[dish] = price
	return nil
}

// Price 回傳 dish 的價格；菜單上沒有時 ok 是 false。
func (m *Menu) Price(dish string) (price int, ok bool) {
	price, ok = m.prices[dish]
	return price, ok
}

// Dishes 回傳排序好的菜名。
func (m *Menu) Dishes() []string {
	return slices.Sorted(maps.Keys(m.prices))
}

// valid 沒有匯出：它是 bento 自己的實作細節，以後要改規則也不會影響別人。
func valid(price int) bool {
	return price > 0
}
func exportDemo() {
	m := bento.New()
	fmt.Println(m.Add("排骨飯", 90), m.Add("滷肉飯", 50))
	fmt.Println(m.Add("空氣便當", 0))
	// m.prices["排骨飯"] = -1 // 編譯錯誤：prices 沒有匯出
	// bento.valid(-1)        // 編譯錯誤：valid 沒有匯出

	price, ok := m.Price("排骨飯")
	fmt.Println(price, ok, m.Dishes())

	fmt.Print(receipt.Format([]receipt.Line{
		{Dish: "排骨飯", Qty: 2, Price: price},
		{Dish: "滷肉飯", Qty: 1, Price: 50},
	}))
}
<nil> <nil>
價格要大於 0
90 true [排骨飯 滷肉飯]
排骨飯 x2 180
滷肉飯 x1 50
合計 230

Menu 的 prices 欄位沒有匯出，main 不可能把價格改成負的，所有的修改都要經過會檢查的 Add。在別的 package 碰沒有匯出的名稱是編譯錯誤，連標準庫也一樣：

package main

import "strings"

func main() {
	var b strings.Builder
	b.buf = append(b.buf, 0)
}

編譯錯誤

./main.go:7:19: b.buf undefined (cannot refer to unexported field buf)

程式裡用的是 package 名稱，不是 import 路徑。兩個 package 名稱一樣時，其中一個要取別名：

func aliasDemo() {
	const note = "備註：<b>不要辣</b>\n"
	text := template.Must(template.New("t").Parse("{{.}}"))
	html := htmltemplate.Must(htmltemplate.New("h").Parse("{{.}}"))
	text.Execute(os.Stdout, note)
	html.Execute(os.Stdout, note)
}
備註：<b>不要辣</b>
備註：&lt;b&gt;不要辣&lt;/b&gt;
  • text/template 和 html/template 的 package 名稱都是 template。別名取在比較少用的那個上面。
  • 路徑的最後一段是版本時，package 名稱是前一段：math/rand/v2 的名稱是 rand，encoding/json/v2 的名稱是 json。
  • _ 別名只執行那個 package 的 init，不用它的任何名稱，例如 28 章註冊 SQLite driver。
  • . 別名讓那個 package 的名稱不用加前綴就能用。讀程式的人看不出名稱從哪裡來，不要用。
  • import 了沒用到是編譯錯誤，存檔時讓編輯器（gopls）自動整理 import。

2. 初始化的順序

套件層級的變數不是單純由上往下初始化：一個變數用到的其他變數，一定先初始化。internal/steps 記下每一步的順序：

var Log []string

func Record(name string, v int) int {
	Log = append(Log, name)
	return v
}

func init() {
	Record("steps 的 init", 0)
}
var total = steps.Record("total", price*qty)

var price = steps.Record("price", 90)

var qty = steps.Record("qty", 2)

func init() {
	steps.Record("main 的 init", 0)
}

func initOrderDemo() {
	fmt.Println(strings.Join(steps.Log, " → "))
	fmt.Println("total =", total)
}
steps 的 init → price → qty → total → main 的 init
total = 180
  • total 寫在最上面，卻最後才初始化，因為它要等 price 和 qty。變數之間形成循環（a 用到 b、b 用到 a）是編譯錯誤。
  • steps 被 main import，所以它的 init 最先執行。同一個 package 被好幾個地方 import，也只初始化一次。
  • init 不能被呼叫，也沒有參數和回傳值。一個檔案可以有好幾個 init，依照出現的順序執行。

init 很方便，但要節制：它在每一次程式啟動、每一次測試時都會執行，而且失敗了只能 panic。讀設定檔、連資料庫、呼叫網路這些可能失敗的事，放在 main 裡明確地呼叫，失敗時回傳錯誤（21 章的 run 函式就是這樣）。init 適合做的是註冊（像 driver）和計算固定的表格。

3. internal 與 package 的設計

本章的 internal/receipt 和 internal/steps 只有 chapters/29-packages-modules 底下的程式碼能用。internal 的規則由 go 指令檢查，不是慣例。testdata/internalerr 是一個專門用來示範的小 module：

// Package counter 在 kitchen 外面，不能 import kitchen/internal 底下的東西。
package counter

import "example.com/shop/kitchen/internal/recipe"

// Peek 想偷看廚房的食譜。
func Peek(dish string) int { return recipe.Steps(dish) }
cd chapters/29-packages-modules/testdata/internalerr
go build ./...

輸出

package example.com/shop/counter
	counter/counter.go:4:8: use of internal package example.com/shop/kitchen/internal/recipe not allowed

package 怎麼切、怎麼命名，決定了程式好不好讀、好不好改：

  • 依照提供的功能切，不是依照型別的種類。bento、receipt、steps 各自說得出「我負責什麼」；models、utils、common、helpers 說不出來，最後什麼都往裡面丟。
  • 名稱短、小寫、一個字，不要底線或大小寫混合。名稱會出現在每一個呼叫的地方，所以 package 裡的名稱不要重複它：bento.Menu 而不是 bento.BentoMenu。
  • 匯出的越少越好。每一個大寫的名稱都是承諾，改了就會弄壞別人。先不匯出，真的有人需要再開放。
  • 每個 package 有一段 package 說明，寫在 // Package bento … 開頭的註解裡。go doc 和 pkg.go.dev 都從原始碼的註解產生文件：
cd chapters/29-packages-modules
go doc ./bento
go doc ./bento Menu.Price

輸出

package bento // import "github.com/xinqilin/GO-Playground/chapters/29-packages-modules/bento"

Package bento 管理便當店的菜單。

對這一章的 main 來說，它是「別人寫的 package」：main 只能用這裡大寫開頭的名稱。

type Menu struct{ ... }
    func New() *Menu

兩個 package 不能互相 import。訂單要通知廚房、廚房做好又要更新訂單，寫成兩個 package 互相呼叫，就會編譯失敗：

cd chapters/29-packages-modules/testdata/cycle
go build ./...

輸出

	imports example.com/cycle/order from kitchen.go
	imports example.com/cycle/kitchen from order.go: import cycle not allowed
  • 常見的解法：讓其中一邊定義一個小 interface，另一邊實作它（10 章）；或把兩邊都需要的型別移到第三個 package；或兩個合成一個。循環常常表示切錯了：兩個 package 其實是同一件事。
  • 這幾個示範用的 module 都放在 testdata 底下：go 指令的 ./... 會略過名叫 testdata 的目錄，它們不會影響 repo 本身的建置。module_test.go 會實際執行上面的指令，確認輸出沒有變。

4. go.mod 與 go.sum

這個 repo 只用標準庫，go.mod 只有兩行：

module github.com/xinqilin/GO-Playground

go 1.27

28 章用了 SQLite driver，它的 go.mod 就多了 require：

module github.com/xinqilin/GO-Playground/chapters/28-database

go 1.27

require modernc.org/sqlite v1.62.0

require (
	github.com/dustin/go-humanize v1.1.0 // indirect
	github.com/google/uuid v1.6.0 // indirect
	github.com/mattn/go-isatty v0.0.24 // indirect
	github.com/ncruces/go-strftime v1.1.0 // indirect
	github.com/remyoudompheng/bigfft v0.0.0-20230129092748-24d4a6f8daec // indirect
	golang.org/x/sys v0.49.0 // indirect
	modernc.org/libc v1.80.1 // indirect
	modernc.org/mathutil v1.7.1 // indirect
	modernc.org/memory v1.12.1 // indirect
)
  • module：module 路徑，也是 import 路徑的開頭。要發佈的話，它就是程式碼的位置（例如 GitHub 上的 repo）。
  • go：至少需要的 Go 版本，也決定語言的行為（00 章）。
  • require：直接用到的 module，以及建置需要的間接 module（標著 // indirect）。第一個區塊是程式碼直接 import 的 modernc.org/sqlite，第二個區塊是它需要的。
  • 其他指令：replace（換成別的版本或本機的目錄，第 6 節）、exclude（排除某個版本）、retract（作者宣告自己某一版不要用，第 7 節）、tool（Go 1.24 起，記錄專案用到的命令列工具，工具鏈那一章）。

go.sum 每個版本有兩行，一行是整個 module 內容的雜湊，一行只有它的 go.mod：

modernc.org/sqlite v1.62.0 h1:gMaCjSM1qpl+iOjiWhR1LYP3zqrYDI+5GYLGt6veP2g=
modernc.org/sqlite v1.62.0/go.mod h1:Jzjh1mt4s0HuQ0KvtB1LIuHiGRmU2D5pgj8dUhW7/SE=

想知道某個 module 為什麼會在清單裡，用 go mod why -m，它印出從你的 module 到它的一條 import 路線：

cd chapters/28-database
go mod why -m github.com/google/uuid

輸出

# github.com/google/uuid
github.com/xinqilin/GO-Playground/chapters/28-database
modernc.org/sqlite
modernc.org/libc
github.com/google/uuid

平常會用到的指令：

go get modernc.org/sqlite@latest   # 加入或升級一個相依，更新 go.mod 和 go.sum
go get modernc.org/sqlite@v1.61.0  # 指定版本（也可以降版）
go get -u ./...                    # 把所有相依升到同一個主版本裡的最新版
go mod tidy                        # 依照程式碼實際的 import，補上缺的、移除沒用到的
go list -m -u all                  # 列出所有 module，以及有沒有新版
go mod graph                       # 誰 require 誰，一行一筆
  • 改了 import 之後跑 go mod tidy，再一起 commit go.mod 和 go.sum。CI 可以檢查 tidy 之後有沒有差異，抓出忘了更新的情況。
  • go.mod 可以手動改，但改完要 tidy；require 的版本和 go.sum 對不上時，go 指令會拒絕建置，並提示要跑哪個指令。

5. 版本與最小版本選擇

module 的版本是語意化版本：v主版本.次版本.修訂。修 bug 加修訂號，加功能但不弄壞舊程式加次版本號，會弄壞舊程式（改名、刪除、改變行為）才加主版本號。v0 表示還在開發，任何一版都可能不相容。

好幾個 module 需要同一個 module 的不同版本時，Go 用最小版本選擇（Minimal Version Selection，MVS）：把所有 go.mod 裡要求過的版本都找出來，每個 module 選其中最大的。不是「網路上最新的」，是「有人明確要求過的最小那個能滿足所有人的版本」。練習 5 會自己實作它。

go.mod 的 go 那一行也是一種版本，標準庫的 go/version 用來比較這種寫法：

func goVersionDemo() {
	pairs := [][2]string{
		{"go1.21.0", "go1.22rc1"},
		{"go1.22rc1", "go1.22.0"},
		{"go1.9", "go1.10"},
	}
	for _, p := range pairs {
		fmt.Printf("%s 比 %s：%d\n", p[0], p[1], version.Compare(p[0], p[1]))
	}
	fmt.Println(version.Lang("go1.27.4"), version.IsValid("1.27"), version.IsValid("go1.27"))
}
go1.21.0 比 go1.22rc1：-1
go1.22rc1 比 go1.22.0：-1
go1.9 比 go1.10：-1
go1.27 false true
  • 版本號要比數字，不是比字串：go1.9 比 go1.10 舊，v1.9.0 比 v1.10.0 舊（練習 2）。rc 這種預發行版比正式版舊。
  • v2 以後要改 module 路徑：不相容的新版，module 路徑要加上 /v2，例如 example.com/bento/v2。對 Go 來說它是另一個 module，同一個程式可以同時用 v1 和 v2，舊的使用者不會因為 go get -u 突然被升到不相容的版本。標準庫的 math/rand/v2、encoding/json/v2 也是同樣的做法。
  • pseudo-version：相依的 module 沒有打版本標籤時，go 指令用 commit 的時間和雜湊組出一個版本，例如 28 章 go.mod 裡的 v0.0.0-20230129092748-24d4a6f8daec。

6. 本機開發：replace 與 go.work

同時修改兩個 module 時（例如函式庫和使用它的服務），每改一次就要發佈新版，太慢了。go.work 讓 go 指令把幾個本機的 module 當成一起建置。testdata/workspace 有兩個 module：

go 1.27

use (
	./price
	./shop
)
// Package price 是另一個 module：放在同一個 workspace 裡，改了馬上就能在 shop 看到效果。
package price

// Of 回傳一道菜的價格，不認得的菜回傳 0。
func Of(dish string) int {
	switch dish {
	case "排骨飯":
		return 90
	case "滷肉飯":
		return 50
	}
	return 0
}
// shop 用到 example.com/price。這個 module 沒有發佈到任何地方，是 go.work 讓 go 找得到它。
package main

import (
	"fmt"

	"example.com/price"
)

func main() {
	for _, dish := range []string{"排骨飯", "滷肉飯"} {
		fmt.Printf("%s %d 元\n", dish, price.Of(dish))
	}
}
cd chapters/29-packages-modules/testdata/workspace
go run ./shop

輸出

排骨飯 90 元
滷肉飯 50 元
  • 建立 workspace：go work init ./price ./shop，之後用 go work use ./其他目錄 加入。
  • shop 的 go.mod 完全沒有提到 price：example.com/price 根本不存在於網路上，是 go.work 讓 go 指令找得到它。
  • 暫時不想用 workspace：GOWORK=off go build ./...，確認只靠 go.mod 也建置得過，這是發佈之前該做的檢查。

另一個做法是在 go.mod 寫 replace，把某個 module 換成本機的目錄或另一個 fork。testdata/replace 沒有 go.work，同一個 price 改由 replace 找到：

module example.com/shop

go 1.27

require example.com/price v0.0.0

// example.com/price 沒有發佈過；replace 把它換成本機的目錄。
replace example.com/price => ../workspace/price
cd chapters/29-packages-modules/testdata/replace
go run .

輸出

排骨飯 90 元
  • replace 寫在 go.mod 裡，會跟著 commit。它只對主 module 有效：別人 require 你的 module 時，你的 replace 會被忽略。
  • 適合「在上游修好之前，暫時用自己 fork 的版本」。只是本機開發的話用 go.work，不要讓 replace 留在 go.mod 裡被發佈出去。

7. 發佈、私有 module 與 vendor

發佈不需要上傳到任何地方：module 路徑就是程式碼的位置，在 repo 打上 v1.2.0 這種 git 標籤就是一個版本。第一次有人 go get 時，proxy.golang.org 抓下來並快取，pkg.go.dev 也會產生文件。

  • 已經發佈的版本不能改。發現某一版有嚴重的問題，發一個新版，並在 go.mod 用 retract v1.2.0 宣告不要用它：go get 不會再選它，已經在用的人也會在 go list -m -u 看到提醒。
  • module 在子目錄時（例如這個 repo 的 chapters/28-database），標籤要加上目錄當前綴：chapters/28-database/v1.0.0。

私有 module（公司內部的 repo）不能經過公開的 proxy，雜湊也不該送到公開的 checksum database。設定 GOPRIVATE，符合的路徑就直接從 repo 抓：

go env -w GOPRIVATE='git.example.com/*'   # 寫進 go 的設定檔，之後每次都有效
go env GOPROXY GOSUMDB                    # 看目前的設定

輸出（預設值）

https://proxy.golang.org,direct
sum.golang.org
  • 存取私有 repo 的帳號密碼由 git 處理（SSH 金鑰、credential helper），go 指令只是呼叫 git。
  • 公司也可以架自己的 proxy，用 GOPROXY 指定，同時快取公開和私有的 module。

vendor：go mod vendor 把所有相依的原始碼複製到 vendor 目錄，go 指令看到它就改用裡面的程式碼，建置時完全不需要網路。代價是 repo 多了大量第三方程式碼，每次升級都是很大的 diff。大部分專案用 proxy 加 go.sum 就足夠了，只有完全不能連外的建置環境才需要 vendor。

常見錯誤

1. utils、common、models 這種 package

名稱說不出它負責什麼，最後什麼都往裡面丟，而且每個 package 都 import 它。依照功能切，名稱就是它做的事（第 3 節）。

2. 名稱重複 package 名稱

呼叫的地方會寫成 bento.BentoMenu。package 名稱已經是前綴了：bento.Menu（第 3 節）。

3. 什麼都匯出

每一個大寫的名稱都可能被別人用到，以後就改不了。先不匯出，只在自己的 module 裡共用的放 internal（第 1、3 節）。

4. 在 init 裡做會失敗的事

init 不能回傳錯誤，失敗只能 panic，測試也會跟著執行。讀設定、連資料庫放在 main 裡明確地呼叫（第 2 節）。

5. 兩個 package 互相 import

編譯失敗。用 interface 反轉其中一邊的依賴，或把共用的部分移到第三個 package（第 3 節）。

6. 不 commit go.sum，或手改 go.mod 不 tidy

別人建置時沒有雜湊可以比對，或 go.mod 和程式碼對不上。改了 import 就 go mod tidy，兩個檔案一起 commit（第 4 節）。

7. 不相容的改版沒有改成 /v2

使用者 go get -u 之後程式就壞了。主版本號從 2 開始，module 路徑要加 /v2（第 5 節）。

8. 本機的 replace 留在 go.mod 裡

別人 clone 之後沒有那個目錄，建置失敗。本機開發用 go.work，並且不要 commit 它（第 6 節）。

重點回顧

  • 一個目錄一個 package；import 路徑是 module 路徑加目錄；程式裡用 package 名稱。
  • 大寫開頭才匯出。匯出的越少，以後越好改。
  • 被 import 的 package 先初始化；變數依相依關係初始化，然後 init，最後 main。
  • init 只做註冊、固定的表格；會失敗的事放在 main。
  • internal 只給上一層目錄底下的程式碼用；package 依照功能切，名稱短而且不重複。
  • import 循環是編譯錯誤，用 interface 或第三個 package 解開。
  • go.mod 決定版本，go.sum 驗證內容，兩個都要 commit；改了 import 就 go mod tidy。
  • MVS 選被要求過的最大版本；不相容的新版要改成 /v2 路徑。
  • 本機同時改好幾個 module 用 go.work；私有 module 設 GOPRIVATE。
