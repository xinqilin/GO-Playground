並行模式

尖峰時段的便當店：固定幾個廚師輪流接單，外送平台的連線只有幾條，菜一站一站往下傳，有一家分店缺貨就整筆取消，簡訊一封一封隔著發。這一章把前面幾章的零件組成這些固定的做法。

本章你會學到

  • worker pool：固定人數，從同一個 channel 拿工作。
  • semaphore：每件事各開一個 goroutine，但限制同時執行的數量。
  • 每一站都聽 ctx 的管線，下游不要了，整條線都停得下來。
  • 並行處理之後，怎麼讓結果維持原本的順序。
  • 自己做一個 Group：第一個錯誤就取消其他工作，並等大家都停下來。
  • 用 time.Ticker 限制呼叫的速率，並用 synctest 精確測試時間。
  • 遇到一個並行問題，該選哪一個模式。

1. worker pool

14 章說過 goroutine 很便宜，每件事開一個通常沒問題。但工作量很大、或每件事都要用到有限的資源（CPU、資料庫連線、對方 API 的配額）時，就要限制同時在做的數量。最常見的做法是 worker pool：固定開幾個 worker，讓它們從同一個 channel 拿工作：

func cookAll(ctx context.Context, orders []string, cooks int, cook func(string) string) []string {
	jobs := make(chan int)
	out := make([]string, len(orders))
	var wg sync.WaitGroup
	for range cooks {
		wg.Go(func() {
			for i := range jobs {
				out[i] = cook(orders[i])
			}
		})
	}

feed:
	for i := range orders {
		select {
		case jobs <- i:
		case <-ctx.Done():
			break feed
		}
	}
	close(jobs)
	wg.Wait()
	return out
}

func poolDemo() {
	orders := []string{"排骨飯", "雞腿飯", "魚排飯", "滷肉飯", "控肉飯"}
	done := cookAll(context.Background(), orders, 2, func(o string) string {
		return o + " 好了"
	})
	for _, d := range done {
		fmt.Println(d)
	}
}

輸出

排骨飯 好了
雞腿飯 好了
魚排飯 好了
滷肉飯 好了
控肉飯 好了
  • jobs 裡送的是索引，不是單子本身。worker 做好就寫進 out[i]，每個人寫不同的格子，不用鎖，結果的順序也自然和 orders 一樣（14 章的做法）。
  • 一個 channel 可以有好幾個人同時收，每個值只會被其中一個人收到：這就是「誰有空誰拿」。
  • 派完工一定要 close(jobs)，worker 的 for range jobs 才會結束，wg.Wait 才等得到。
  • 派工的 select 也等 ctx.Done()：取消之後不再派新的單，已經拿到單的 worker 做完手上這張就收工。break 後面加上標籤 feed，才會跳出 for，而不是只跳出 select。
  • worker 數量怎麼定：CPU 密集的計算用 runtime.NumCPU() 左右；等待外部服務的工作，看對方能承受多少。

2. semaphore

有時候每件事開一個 goroutine 最自然，只是不能同時太多，例如對方的 API 一次只接受兩條連線。buffered channel 就是現成的 semaphore（號碼牌）：容量是牌的數量，送進去是拿牌，拿出來是還牌，牌被拿光時送的人自然會等：

func fetchAll(branches []string, limit int, fetch func(string) int) []int {
	sem := make(chan struct{}, limit)
	out := make([]int, len(branches))
	var wg sync.WaitGroup
	for i, b := range branches {
		wg.Go(func() {
			sem <- struct{}{}
			defer func() { <-sem }()
			out[i] = fetch(b)
		})
	}
	wg.Wait()
	return out
}

func semaphoreDemo() {
	stock := map[string]int{"東區": 12, "西區": 0, "南區": 7, "北區": 30, "中區": 5, "內湖": 18, "板橋": 9}
	branches := []string{"東區", "西區", "南區", "北區", "中區", "內湖", "板橋"}
	var g gauge
	got := fetchAll(branches, 2, func(b string) int {
		g.enter()
		defer g.leave()
		return stock[b]
	})
	fmt.Println(got)
	fmt.Printf("同時在查的分店沒有超過 2 家：%t\n", g.peak.Load() <= 2)
}

輸出

[12 0 7 30 5 18 9]
同時在查的分店沒有超過 2 家：true

gauge 用 17 章的 CompareAndSwap 記錄最多同時幾個。在 Example 裡只能檢查「沒有超過 2」，因為真實執行時，幾個 goroutine 會不會剛好同時在查，每次都不一樣。用 synctest 的假時間就能精確測試：每家查 1 秒、7 家、同時 2 家，剛好要 4 秒，同時最多剛好 2 家：

func TestFetchAllLimit(t *testing.T) {
	synctest.Test(t, func(t *testing.T) {
		var g gauge
		start := time.Now()
		fetchAll(make([]string, 7), 2, func(string) int {
			g.enter()
			defer g.leave()
			time.Sleep(time.Second)
			return 0
		})
		if d, p := time.Since(start), g.peak.Load(); d != 4*time.Second || p != 2 {
			t.Errorf("花了 %v、同時最多 %d 個；want 4s、2 個", d, p)
		}
	})
}

worker pool 和 semaphore 都能限制同時的數量，差別在 goroutine 的數量：

worker poolsemaphore
goroutine 數量固定 n 個，重複使用每件事一個，同時執行的最多 n 個
適合工作量很大、源源不絕，或工作從 channel 來一批數量已知的工作，寫法最短
要注意要記得 close(jobs)一萬件事就有一萬個 goroutine 在等牌

semaphore 的缺點可以改善：在開 goroutine 之前就拿牌（把 sem <- struct{}{} 移到 wg.Go 前面），迴圈會停在拿牌的地方，同時存在的 goroutine 也不會超過 n 個（練習 1）。

3. 可以取消的管線

15 章的管線一定要把所有東西跑完；有了 ctx，下游可以隨時說「不要了」。把每一站寫成同一個樣子，就能自由組合：

func emit[T any](ctx context.Context, items ...T) <-chan T {
	out := make(chan T)
	go func() {
		defer close(out)
		for _, it := range items {
			select {
			case out <- it:
			case <-ctx.Done():
				return
			}
		}
	}()
	return out
}

func stage[In, Out any](ctx context.Context, in <-chan In, f func(In) Out) <-chan Out {
	out := make(chan Out)
	go func() {
		defer close(out)
		for v := range in {
			select {
			case out <- f(v):
			case <-ctx.Done():
				return
			}
		}
	}()
	return out
}

每一站只有三條規則：自己開的 channel 自己 close（defer）；送的時候 select ctx；收的時候直接 range 上一站。收的地方不需要聽 ctx，因為上一站也照同樣的規則寫，被取消時會 close，range 就結束了。用它算一疊發票的含稅合計，遇到看不懂的發票就停：

type amount struct {
	v   int
	err error
}

func parse(s string) amount {
	v, err := strconv.Atoi(s)
	if err != nil {
		return amount{err: fmt.Errorf("發票金額「%s」不是數字", s)}
	}
	return amount{v: v}
}

func addTax(a amount) amount {
	if a.err != nil {
		return a
	}
	return amount{v: a.v * 105 / 100}
}

func pipelineDemo() {
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	raw := emit(ctx, "120", "85", "九十", "300")
	taxed := stage(ctx, stage(ctx, raw, parse), addTax)

	total := 0
	for a := range taxed {
		if a.err != nil {
			fmt.Println("停下來：", a.err)
			break
		}
		total += a.v
	}
	fmt.Println("含稅合計", total)
}

輸出

停下來： 發票金額「九十」不是數字
含稅合計 215
  • 錯誤當成值沿著管線往下傳（amount 的 err 欄位），由最後的消費者決定怎麼處理。另一種做法是在發生錯誤的那一站用 WithCancelCause 取消整條線（第 5 節）。
  • 消費者 break 之後，defer 的 cancel 讓 emit、parse、addTax 各自在送的地方選到 Done 結束，第四張發票根本不會被處理。測試裡用 synctest 檢查「提早離開之後，泡泡裡沒有留下任何 goroutine」，寫法和 18 章一樣。
  • 某一站特別慢，可以讓它自己開好幾個 worker（第 1 節），再把它們的輸出匯成一條（15 章的 fan-in）；但順序就亂了，見下一節。

4. 結果的順序

好幾個 worker 同時做，完成的順序每次都不一樣。需要原本的順序時，有三種做法：

  • 全部做完再排序：結果帶著編號，收齊之後 slices.SortFunc。最直覺，但要等全部做完。
  • 寫進對應的格子：事先開好 slice，每份結果寫進自己的索引（第 1 節）。不用排序、不用鎖，同樣要等全部做完。工作數量事先知道時，這是首選。
  • 邊做邊照順序送出：結果是串流，不能等全部做完時，用一個暫存區重新排序：
type finished struct {
	seq  int
	dish string
}

func inOrder(in <-chan finished) <-chan string {
	out := make(chan string)
	go func() {
		defer close(out)
		pending := make(map[int]string)
		next := 0
		for f := range in {
			pending[f.seq] = f.dish
			for {
				dish, ok := pending[next]
				if !ok {
					break
				}
				out <- dish
				delete(pending, next)
				next++
			}
		}
	}()
	return out
}

func orderDemo() {
	in := make(chan finished, 4)
	in <- finished{2, "魚排飯"}
	in <- finished{0, "排骨飯"}
	in <- finished{3, "滷肉飯"}
	in <- finished{1, "雞腿飯"}
	close(in)

	for dish := range inOrder(in) {
		fmt.Println(dish)
	}
}

輸出

排骨飯
雞腿飯
魚排飯
滷肉飯

每收到一份，就檢查「下一個該送的」是不是已經在 pending 裡，是就連續送出，直到斷掉為止。代價是排在前面的那一份特別慢時，後面做好的全部卡在 pending 裡等它，記憶體也跟著變大。能用格子就用格子；真的需要串流，再用這一招，並限制同時在做的數量，讓 pending 不會無限長大。

5. 第一個錯誤就全部取消

一張訂單要三家分店都備好料才算成功，任何一家失敗，其他家再做下去也沒用。這是非常常見的需求：同時做好幾件事、等全部完成、第一個錯誤就取消其他的。把 WaitGroup、Once 和 WithCancelCause 組起來：

type Group struct {
	wg     sync.WaitGroup
	cancel context.CancelCauseFunc
	once   sync.Once
	err    error
}

func NewGroup(ctx context.Context) (*Group, context.Context) {
	ctx, cancel := context.WithCancelCause(ctx)
	return &Group{cancel: cancel}, ctx
}

func (g *Group) Go(f func() error) {
	g.wg.Go(func() {
		if err := f(); err != nil {
			g.once.Do(func() {
				g.err = err
				g.cancel(err)
			})
		}
	})
}

func (g *Group) Wait() error {
	g.wg.Wait()
	g.cancel(g.err)
	return g.err
}

func groupDemo() {
	g, ctx := NewGroup(context.Background())
	branches := []string{"東區", "西區", "北區"}
	status := make([]string, len(branches))
	for i, b := range branches {
		g.Go(func() error {
			if b == "西區" {
				status[i] = "缺貨"
				return errors.New("西區 排骨缺貨")
			}
			<-ctx.Done() // 模擬一件很久的工作，只會因為取消而停下來
			status[i] = "停下來：" + ctx.Err().Error()
			return ctx.Err()
		})
	}

	fmt.Println("錯誤：", g.Wait())
	for i, b := range branches {
		fmt.Println(b, status[i])
	}
}

輸出

錯誤： 西區 排骨缺貨
東區 停下來：context canceled
西區 缺貨
北區 停下來：context canceled
  • Once 保證只記下第一個錯誤。被取消的東區、北區也回傳了錯誤（ctx.Err()），但那時 Once 已經做過，不會蓋掉真正的原因。
  • 用 WithCancelCause 取消，工作裡用 context.Cause(ctx) 就能看到「西區 排骨缺貨」，而不只是 context canceled。
  • Wait 先等所有工作結束，才回傳。即使有人失敗，也不會留下還在跑的 goroutine。Wait 最後也取消 ctx，釋放它的資源。
  • 工作一定要聽 ctx（這裡是 <-ctx.Done()），否則取消了它也照樣做完，Wait 就得等它。

這個模式太常用了，Go 團隊維護的 golang.org/x/sync/errgroup 提供了幾乎一樣的 API：errgroup.WithContext(ctx) 回傳 Group 和 ctx，再用 Go、Wait；還多了 SetLimit(n) 限制同時的數量（練習 4 就是自己做出它）。它不在標準庫，要用 go get 加進專案（「package 與 module」那一章）。這本手冊只用標準庫，所以自己寫，順便看清楚它裡面在做什麼。

6. 限制速率

限制同時的數量（第 1、2 節）和限制速率是兩回事：簡訊商可能規定「每秒最多一封」，就算你只有一條連線，也不能連續狂送。time.NewTicker(d) 每隔 d 往 t.C 送一次時間，每次做事前先收一個 tick：

func notifyAll(ctx context.Context, phones []string, every time.Duration, send func(string)) error {
	t := time.NewTicker(every)
	defer t.Stop()
	for _, p := range phones {
		select {
		case <-t.C:
			send(p)
		case <-ctx.Done():
			return ctx.Err()
		}
	}
	return nil
}

func tickerDemo() {
	phones := []string{"0912-000-111", "0922-000-222", "0933-000-333"}
	err := notifyAll(context.Background(), phones, time.Millisecond, func(p string) {
		fmt.Println("已通知", p)
	})
	fmt.Println("錯誤：", err)
}

輸出

已通知 0912-000-111
已通知 0922-000-222
已通知 0933-000-333
錯誤： <nil>

Example 只看得到順序；時間對不對，用 synctest 的假時間檢查，連「1.5 秒逾時，只來得及通知一位」都能精確測試：

func TestNotifyAllPacing(t *testing.T) {
	synctest.Test(t, func(t *testing.T) {
		start := time.Now()
		var at []time.Duration
		send := func(string) { at = append(at, time.Since(start)) }
		if err := notifyAll(t.Context(), []string{"a", "b", "c"}, time.Second, send); err != nil {
			t.Fatal(err)
		}
		if want := []time.Duration{time.Second, 2 * time.Second, 3 * time.Second}; !slices.Equal(at, want) {
			t.Errorf("通知的時間 = %v, want %v", at, want)
		}

		ctx, cancel := context.WithTimeout(t.Context(), 1500*time.Millisecond)
		defer cancel()
		at, start = nil, time.Now()
		err := notifyAll(ctx, []string{"a", "b", "c"}, time.Second, send)
		if !errors.Is(err, context.DeadlineExceeded) || len(at) != 1 {
			t.Errorf("1.5 秒逾時：錯誤 = %v、通知了 %d 位；want DeadlineExceeded、1 位", err, len(at))
		}
	})
}
  • 第一個 tick 在一個間隔之後才來，不是馬上。要第一件立刻做，就先做一次再進迴圈。
  • 收的一方太慢時，Ticker 會丟掉跟不上的 tick，不會累積一堆，之後一口氣放行。
  • defer t.Stop()：Go 1.23 起沒有 Stop 的 Ticker 也會被回收，但不用了就停掉，意圖比較清楚。只需要 channel 的話，time.Tick(d) 在 Go 1.23 之後也可以放心用。
  • 需要「平常每秒一個，但允許偶爾一次衝幾個」這種 token bucket 的限速，可以用 Go 團隊維護的 golang.org/x/time/rate：rate.NewLimiter(r, b)，每次做事前呼叫 lim.Wait(ctx)。

7. 怎麼選

這些模式背後是同一組原則，比記住每個模式更重要：

  • 每個 goroutine 都要有人負責等它結束。開 goroutine 的函式，回傳之前就要等它們結束（WaitGroup、Group），或是把「怎麼讓它結束」交給呼叫的人（ctx、close channel）。這樣函式回傳之後，就不會有它開的 goroutine 還在背景亂跑。
  • 輸入沒有上限時，並行就要有上限。工作來自使用者、檔案、網路，數量就不受你控制；用 worker pool 或 semaphore 把同時的數量固定下來。
  • 會等待的地方都要能被取消：送、收、睡、呼叫外部服務，都放進有 ctx.Done() 的 select，或用收 ctx 的 API。
  • 誰送誰 close，而且只 close 一次（15 章）。
  • 先寫循序的版本。並行有成本：程式變複雜、測試變難、goroutine 和 channel 本身也要時間。先確認慢在哪裡（等外部服務？算太多？），量測之後再並行，而且只並行慢的那一段。

常見錯誤

1. 先 Wait 再收結果

結果 channel 沒有緩衝，worker 送結果時要有人收；收的那一方卻卡在 wg.Wait 等 worker 結束，兩邊互等，永遠結束不了（練習 5）。把「等 worker 結束再 close 結果」放到另一個 goroutine，或改用寫格子的做法。

2. 忘了 close(jobs)

worker 的 for range jobs 永遠等下一個工作，wg.Wait 永遠等不到。派工的一方送完一定要 close（第 1 節）。

3. 輸入有多少就開多少 goroutine 去打外部服務

一萬筆資料就同時開一萬條連線，對方會把你擋掉，你自己的檔案描述元也可能用完。用 semaphore 或 worker pool 限制數量（第 2 節）。

4. 管線的某一站送的時候不聽 ctx

下游不收了，這一站就永遠卡在送，前面每一站跟著卡住，全部洩漏。每一站送的時候都要 select ctx（第 3 節）。

5. Group 裡的工作不聽 ctx

第一個錯誤發生了、ctx 也取消了，其他工作卻照樣做完，Wait 只能等它們。工作內部會等待的地方都要聽 ctx（第 5 節）。

6. 依賴完成的順序

並行的結果「在我電腦上每次順序都一樣」只是巧合。需要順序就用格子或重新排序（第 4 節）；測試裡比較結果前先排序，或用 synctest 控制時間。

Java 的 ExecutorService 是一個要記得 shutdown 的物件；Go 的 worker pool 只是幾個 goroutine 和一個 channel，close(jobs) 就是 shutdown，wg.Wait 就是 awaitTermination。

練習

    worker pool 查每道菜的價格，結果一道菜都查不回來。

    func Prices(workers int, dishes []string, lookup func(string) int) map[string]int {
	type priced struct {
		dish  string
		price int
	}
	jobs := make(chan string)
	results := make(chan priced)

	var wg sync.WaitGroup
	for range workers {
		wg.Go(func() {
			for d := range jobs {
				results <- priced{d, lookup(d)}
			}
		})
	}
	go func() {
		defer close(jobs)
		for _, d := range dishes {
			jobs <- d
		}
	}()

	wg.Wait()
	close(results)
	out := make(map[string]int)
	for r := range results {
		out[r.dish] = r.price
	}
	return out
}

重點回顧

  • worker pool：固定 n 個 goroutine 從同一個 channel 拿工作，派完要 close。
  • semaphore：容量 n 的 channel 當號碼牌；在開 goroutine 之前拿牌，連 goroutine 數量都有上限。
  • 管線的每一站：自己 close 輸出、送的時候 select ctx、收的時候 range 上一站。
  • 結果要有順序：能寫格子就寫格子；串流才用重新排序，並限制同時的數量。
  • Group（errgroup）：第一個錯誤用 Once 記下並取消 ctx，Wait 等所有工作結束才回傳。
  • 限制速率用 time.Ticker，每做一件事先收一個 tick；需要突發額度用 x/time/rate。
  • 每個 goroutine 都要有人負責等它結束；會等待的地方都要能被取消。
  • 並行程式的時間行為，用 synctest 的假時間精確測試。
  • 先寫循序的版本，量測之後只並行慢的那一段。
