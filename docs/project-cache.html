TTL＋LRU 快取

分店的收銀機每結一次帳，就要問總店一次便當的價格，每次等 300ms。價格一天才改一兩次，大可以記在分店：但記多少？記多久？中午十個客人同時點排骨飯，要問總店十次嗎？這個專題寫一個回答這三個問題的快取。

這個專題做什麼

快取最多記 3 種便當，每筆 10 分鐘後過期。依序查 8 次，方括號裡是查完之後快取裡的內容，由最近用過排到最久沒用：

總共花了 1.8s（問總店 6 次，每次 300ms）
  • 第 3 行：排骨飯已經在快取裡，不用等，而且它變成「最近用過的」，排到最前面。
  • 第 5 行：控肉飯進來時已經有 3 筆，最久沒用的雞腿飯被擠掉。
  • 第 6 行：所以再查雞腿飯，又要問總店一次，這次擠掉的是排骨飯。
  • 炒泡麵：總店回傳錯誤，錯誤不存進快取，下次還會再問。

程式分成兩個檔案：cache.go 是通用的快取，main.go 是總店的模擬和上面的示範。測試在 cache_test.go 和 bench_test.go。先備：07 章 map、12 章泛型、17 章 Mutex、22 章單調時鐘、30 章 synctest、31 章效能。

1. 上限和期限

  • 只用 map 的快取：每查一種新的東西就多一筆，永遠不會變小。查詢的 key 來自使用者（網址、搜尋字）時，記憶體會一直長下去，最後程式被系統砍掉。這是很常見的記憶體洩漏。
  • LRU（least recently used）：滿了丟掉最久沒用的。它假設「最近用過的，等一下也很可能再用」，這對大部分的查詢都成立。
  • TTL（time to live）：總店改了價格，分店最晚 10 分鐘後就會知道。期限越短資料越新，問總店的次數也越多。
  • 同時沒找到：中午十個人同時點一種剛過期的便當，十個人都去問總店，總店一下子收到十倍的請求。第 6 節處理這件事。

2. 泛型的快取型別

type Cache[K comparable, V any] struct {
	mu      sync.Mutex
	size    int
	ttl     time.Duration
	order   *list.List          // 最近用過的在最前面；每個元素的 Value 是 *entry[K, V]
	items   map[K]*list.Element // key → order 裡的元素
	loading map[K]*call[V]      // 正在載入的 key
	stats   Stats
}

type entry[K comparable, V any] struct {
	key     K // 從串列尾端丟掉一筆時，要用它刪掉 map 裡的 key
	val     V
	expires time.Time // 零值表示不會過期
}

type call[V any] struct {
	done chan struct{}
	val  V
	err  error
}

type Stats struct {
	Hits        int // 有找到
	Misses      int // 沒找到，包括過期的
	Loads       int // GetOrLoad 呼叫 load 的次數
	Evictions   int // 滿了被丟掉的筆數
	Expirations int // 過期被丟掉的筆數
}

func New[K comparable, V any](size int, ttl time.Duration) *Cache[K, V] {
	if size < 1 {
		panic("cache: size 必須大於 0")
	}
	return &Cache[K, V]{
		size:    size,
		ttl:     ttl,
		order:   list.New(),
		items:   map[K]*list.Element{},
		loading: map[K]*call[V]{},
	}
}
  • K comparable：key 要放進 map，所以必須能用 == 比較（12 章）。V 沒有限制，用 any。
  • New[string, int](3, 10*time.Minute)：K 和 V 只出現在回傳值，不在參數裡，編譯器推論不出來，呼叫時要明確寫出型別（12 章）。
  • size 小於 1 就 panic：容量是 0 的快取什麼都存不了，一定是呼叫的人寫錯了，就像 make 的長度是負數也會 panic。這和「總店查不到」這種執行時會發生的錯誤不同，不用回傳 error。
  • ttl 的零值有意義：0 表示不會過期，只當 LRU 用。entry.expires 的零值也表示不會過期，不需要另外一個 bool。
  • Stats 是一般的 struct：Stats() 回傳它的複本，呼叫的人拿去讀、拿去比較都不用擔心被改到。

3. LRU：map 加雙向串列

func (c *Cache[K, V]) getLocked(key K) (V, bool) {
	el, ok := c.items[key]
	if !ok {
		c.stats.Misses++
		var zero V
		return zero, false
	}
	e := el.Value.(*entry[K, V])
	if !e.expires.IsZero() && !time.Now().Before(e.expires) {
		c.removeLocked(el) // 過期的資料用到時才丟掉
		c.stats.Expirations++
		c.stats.Misses++
		var zero V
		return zero, false
	}
	c.order.MoveToFront(el)
	c.stats.Hits++
	return e.val, true
}

func (c *Cache[K, V]) setLocked(key K, val V) {
	var expires time.Time
	if c.ttl > 0 {
		expires = time.Now().Add(c.ttl)
	}
	if el, ok := c.items[key]; ok {
		e := el.Value.(*entry[K, V])
		e.val, e.expires = val, expires
		c.order.MoveToFront(el)
		return
	}
	c.items[key] = c.order.PushFront(&entry[K, V]{key: key, val: val, expires: expires})
	if c.order.Len() > c.size {
		c.removeLocked(c.order.Back())
		c.stats.Evictions++
	}
}

func (c *Cache[K, V]) removeLocked(el *list.Element) {
	e := c.order.Remove(el).(*entry[K, V])
	delete(c.items, e.key)
}
  • 為什麼不用 slice 排順序：把中間的一筆移到最前面，要搬動它前面的每一個元素，是 O(n)。雙向串列只要改幾個指標。
  • entry 裡也存 key：從串列尾端丟掉一筆時，只拿得到節點，要靠它的 key 才能從 map 刪掉。少了這一步，map 會留著指向已經不在串列裡的節點。
  • container/list 不是泛型的：它在泛型出現之前就有了，Value 的型別是 any，取出來要用型別斷言 el.Value.(*entry[K, V])。斷言不會失敗，因為放進去的一定是這個型別；延伸挑戰 6 讓你寫一個不需要斷言的版本。
  • 更新也算使用：Set 一個已經存在的 key，會更新值、重新計時，並移到最前面。

4. TTL：過期的資料

func TestTTL(t *testing.T) {
	synctest.Test(t, func(t *testing.T) {
		c := New[string, int](10, 10*time.Minute)
		c.Set("排骨飯", 100)

		time.Sleep(5 * time.Minute)
		if _, ok := c.Get("排骨飯"); !ok {
			t.Fatal("5 分鐘時應該還在")
		}
		time.Sleep(5*time.Minute - time.Nanosecond)
		if _, ok := c.Get("排骨飯"); !ok {
			t.Fatal("差 1 奈秒滿 10 分鐘時應該還在")
		}
		time.Sleep(time.Nanosecond)
		if _, ok := c.Get("排骨飯"); ok {
			t.Fatal("滿 10 分鐘時應該過期了")
		}

		c.Set("排骨飯", 105) // 重新存入，重新計時
		time.Sleep(9 * time.Minute)
		if v, ok := c.Get("排骨飯"); !ok || v != 105 {
			t.Errorf("重新存入 9 分鐘後 = %d, %v，想要 105, true", v, ok)
		}
		if s := c.Stats(); s.Expirations != 1 || s.Hits != 3 || s.Misses != 1 {
			t.Errorf("Stats() = %+v", s)
		}
	})
}
  • 用到時才丟（lazy）：不需要背景的 goroutine 定時掃描，程式簡單，也沒有要關閉的東西。代價是過期但沒人查的資料會繼續佔著位置，Len 和 Keys 也算它們；有 LRU 的上限，它們最後還是會被擠掉。延伸挑戰 3 加上背景清理。
  • !time.Now().Before(expires)：「現在不早於期限」，也就是剛好滿 10 分鐘就算過期。TestTTL 測了差 1 奈秒和剛好滿兩個邊界。
  • 單調時鐘：time.Now() 帶著單調時鐘的讀數，Before 會用它比較。有人把系統時間往回調一小時，快取的期限也不會亂掉（22 章）。
  • 不用注入時鐘：程式直接呼叫 time.Now()。在 synctest 的泡泡裡，time.Now 和 time.Sleep 都是假的，十分鐘一瞬間就過了，而且精確到奈秒。專題 4 注入 now 函式，是因為輸出要印出固定的日期；這裡只在乎經過多久，用 synctest 就夠了。

5. 一把鎖，而且不能是 RLock

func (c *Cache[K, V]) Get(key K) (V, bool) {
	c.mu.Lock()
	defer c.mu.Unlock()
	return c.getLocked(key)
}

func (c *Cache[K, V]) Set(key K, val V) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.setLocked(key, val)
}

func (c *Cache[K, V]) Keys() []K {
	c.mu.Lock()
	defer c.mu.Unlock()
	keys := make([]K, 0, c.order.Len())
	for el := c.order.Front(); el != nil; el = el.Next() {
		keys = append(keys, el.Value.(*entry[K, V]).key)
	}
	return keys
}
  • Mutex，不是 RWMutex：RWMutex 適合「讀很多、寫很少，而且讀真的不改任何東西」的情況（17 章）。LRU 的每一次 Get 都會寫，用讀鎖就是 data race，go test -race 會在 TestConcurrent 裡抓到。
  • 公開方法加鎖，Locked 方法不加：GetOrLoad 要在同一把鎖裡先找、找不到再登記「我要載入」，所以需要一個不加鎖的 getLocked 給它用。
  • Keys 回傳新的 slice：不把內部的串列交出去。呼叫的人在鎖外面走訪內部的串列，就又是 data race。
  • 統計也在同一把鎖裡：Hits、Misses 和串列一起改，Stats() 拿到的永遠是某一個時間點一致的數字。

6. 同時沒找到：只載入一次

func (c *Cache[K, V]) GetOrLoad(ctx context.Context, key K, load func(context.Context, K) (V, error)) (V, error) {
	c.mu.Lock()
	if v, ok := c.getLocked(key); ok {
		c.mu.Unlock()
		return v, nil
	}
	if cl, ok := c.loading[key]; ok { // 已經有人在載入了：等他
		c.mu.Unlock()
		select {
		case <-cl.done:
			return cl.val, cl.err
		case <-ctx.Done():
			var zero V
			return zero, ctx.Err()
		}
	}
	cl := &call[V]{done: make(chan struct{}), err: errPanicked} // load 沒有正常回傳時，err 就留在 errPanicked
	c.loading[key] = cl
	c.stats.Loads++
	c.mu.Unlock() // load 可能很慢，不能拿著鎖等

	defer func() { // load panic 時也會執行，等待的人不會永遠卡住
		c.mu.Lock()
		delete(c.loading, key)
		if cl.err == nil {
			c.setLocked(key, cl.val)
		}
		c.mu.Unlock()
		close(cl.done)
	}()
	cl.val, cl.err = load(ctx, key)
	return cl.val, cl.err
}
  • 不拿著鎖等：load 要 300ms。拿著鎖等的話，這 300ms 內所有人的 Get，連查別種便當的都要排隊。所以先在 loading 登記，放開鎖再呼叫 load，完成之後再拿鎖存結果。
  • done channel 傳結果：call 的 val 和 err 由載入的人寫入，寫完才 close(done)；等待的人在 <-done 之後才讀。channel 的關閉保證讀的人一定看得到寫好的值（17 章）。
  • err 的初始值是 errPanicked：load 正常回傳時，這個值會被蓋掉；load panic 的話，賦值根本沒有發生，err 就留在 errPanicked。defer 照樣會執行：清掉 loading、不存結果、關閉 done。panic 繼續傳給第一個人，等待的人拿到錯誤，而不是永遠卡住。
  • 等待的人可以放棄：select 同時等 done 和自己的 ctx。TestWaiterGivesUp 確認放棄的人 100ms 就回傳，載入的人不受影響，結果照樣存進快取。
  • 錯誤不存：總店暫時連不上，不應該讓分店接下來 10 分鐘都以為「查不到」。代價是不存在的品項每次都會問總店，延伸挑戰 2 處理這件事。
func TestGetOrLoadOnce(t *testing.T) {
	synctest.Test(t, func(t *testing.T) {
		h := &headOffice{delay: 300 * time.Millisecond}
		c := New[string, int](3, time.Minute)
		start := time.Now()
		var wg sync.WaitGroup
		for range 10 {
			wg.Go(func() {
				p, err := c.GetOrLoad(context.Background(), "雞腿飯", h.price)
				if p != 110 || err != nil {
					t.Errorf("GetOrLoad = %d, %v", p, err)
				}
			})
		}
		wg.Wait()
		if h.calls != 1 {
			t.Errorf("問了總店 %d 次，想要 1 次", h.calls)
		}
		if d := time.Since(start); d != 300*time.Millisecond {
			t.Errorf("花了 %v，想要 300ms", d)
		}
	})
}
  • 剛好 300ms：synctest 的假時間讓「十個人一起等、總共只花一次的時間」可以精確地驗證；用真的時間只能寫「小於 600ms」這種模糊的條件。
  • 還沒解決的兩件事：load 用的是第一個人的 ctx，他放棄的話，其他人也一起拿到取消的錯誤；載入期間有人呼叫 Delete（例如總店剛改價），載入完成時還是會把舊的價格存進去。golang.org/x/sync/singleflight 是常用的去重套件，但後面這個問題要靠快取自己處理（延伸挑戰 4）。

7. 量一量：一把鎖的極限

func BenchmarkGetParallel(b *testing.B) {
	c := New[string, int](len(keys), 0)
	for i, k := range keys {
		c.Set(k, i)
	}
	b.RunParallel(func(pb *testing.PB) {
		i := 0
		for pb.Next() {
			c.Get(keys[i%len(keys)])
			i++
		}
	})
}

func BenchmarkMapParallel(b *testing.B) {
	var mu sync.Mutex
	m := map[string]int{}
	for i, k := range keys {
		m[k] = i
	}
	b.RunParallel(func(pb *testing.PB) {
		i := 0
		for pb.Next() {
			mu.Lock()
			_ = m[keys[i%len(keys)]]
			mu.Unlock()
			i++
		}
	})
}

  • SetEvict 每次配置兩次：一個 entry、一個 list.Element，合計 96 bytes。用 -memprofile 和 pprof 看，配置確實來自 setLocked 和 container/list 的 insertValue（31 章）。

  • 不是 LRU 的錯：對照組只有 map 加一把鎖，沒有串列、沒有期限，也要 140ns。瓶頸是那一把鎖本身。
  • 要不要改：一次 167ns，每秒還是能處理幾百萬次 Get，比問總店的 300ms 快了一百多萬倍。真的成為瓶頸時，常見的做法是分片：把 key 分到好幾個各有一把鎖的小快取（延伸挑戰 5）。改之前，先確認真實的負載真的卡在這裡（31 章）。

延伸挑戰

這些題目沒有附測試。先寫測試描述你要的行為，跟時間有關的用 synctest。

  1. 入門挑戰 1：Peek

    加一個 Peek(key)：回傳值，但不移到最前面、不算進統計。過期的資料 Peek 回傳沒找到，但不丟掉它。

    提示

    Peek 不改任何東西，看起來可以用讀鎖；但其他方法都用 Mutex，混用兩種鎖沒有意義。直接用同一把 Mutex。

  2. 進階挑戰 2：記住「查不到」

    總店回傳 errNoItem 時，把這個結果記 1 分鐘，這段時間內再查同一個品項直接回傳錯誤，不問總店；其他錯誤（例如逾時）還是不記。

    提示

    可以把 V 包成 struct{ val V; err error }，或在 GetOrLoad 多一個參數決定哪些錯誤要記。想想兩種期限（10 分鐘、1 分鐘）要怎麼放進同一個 entry。

  3. 進階挑戰 3：背景清理

    加一個 Run(ctx, every) 方法：每隔 every 掃描一次，丟掉所有過期的資料，ctx 取消時結束。用 synctest 測試：過了期限加一個 every 之後，Len() 變成 0。

    提示

    用 time.Ticker 和 select（16 章）。掃描時要拿鎖，一次掃完整個串列的時間和筆數成正比；筆數很多時可以一次只掃一部分。

  4. 進階挑戰 4：載入期間的刪除

    先寫一個會失敗的測試：GetOrLoad 正在載入時呼叫 Delete，載入完成後 Get 應該找不到。再修改程式讓它通過。

    提示

    Delete 時如果這個 key 正在載入，在它的 call 上做個記號；載入完成時看到記號就不存。用 synctest.Wait 讓「載入中」這個時間點可以精確地控制。

  5. 挑戰挑戰 5：分片

    寫一個 Sharded[K, V]，裡面有 16 個 Cache，用 maphash.Comparable 算出 key 屬於哪一個。比較它和原本的 BenchmarkGetParallel。

    提示

    maphash.Comparable（Go 1.24 起）可以對任何 comparable 的值算雜湊，不用自己把 key 轉成字串。分片之後，LRU 變成「每一片各自的 LRU」，整體丟掉的不一定是全域最久沒用的；這是分片的代價。

  6. 挑戰挑戰 6：泛型的雙向串列

    不用 container/list，自己寫一個 node[K, V] 帶 prev、next 指標的雙向串列，拿掉所有型別斷言。用 BenchmarkSetEvict 比較配置次數。

    提示

    把 key、val、expires 直接放在節點裡，一個節點只要配置一次。用一個不存資料的哨兵節點，頭尾相連，插入和刪除就不用處理 nil 的特殊情況。

重點回顧

  • 快取要有上限和期限：上限控制記憶體，期限控制資料多舊。只用 map 的快取會一直長大。
  • LRU = map（找到節點）加雙向串列（記住順序），每個動作都是 O(1)；entry 要存 key，丟掉尾端時才刪得掉 map。
  • 泛型型別的型別參數只出現在回傳值時，呼叫要寫明 New[K, V]；container/list 不是泛型的，取值要型別斷言。
  • 用到時才檢查過期，程式簡單；過期的資料會佔位置到被擠掉。time.Now 帶單調時鐘，不怕系統時間被調整。
  • Get 會移動節點、改統計，所以用 Mutex，不是 RWMutex 的讀鎖。
  • 同一個 key 同時沒找到，只讓一個人載入，其他人等 done channel；載入時不拿著鎖，panic 時用 defer 收尾。
  • synctest 讓 TTL 和「等了多久」都能精確到奈秒地測試，不用注入假的時鐘。
  • 一把鎖在大量平行存取時會成為瓶頸；先量，再決定要不要分片。
