TCP 聊天室

十一點半，辦公室的人開始討論中午訂哪一家。這個專題寫那個聊天室的伺服器：任何人用 nc 連進來，取一個暱稱就能說話。難的不是收發訊息，而是那些「萬一」：有人連上就不說話、有人的網路很慢、有人送來一大串亂碼、伺服器要重開時大家怎麼辦。

這個專題做什麼

啟動伺服器，再開幾個終端機用 nc 連進來：

go run ./projects/chat

  • 暱稱：重複的、有空白的都會被擋下來，請他再輸入一次。
  • 廣播：一個人說的話，其他人都會收到，自己不會再收到一次（nc 的畫面上已經有自己打的字）。
  • 指令：/who、/nick、/quit、/help；不認得的指令只告訴打錯的那個人。
  • 關機：伺服器關閉時，已經進來的人會收到道別訊息；還在輸入暱稱的 C 直接斷線。

程式分成三個檔案：main.go（旗標和監聽）、server.go（每個連線的讀寫）、room.go（線上名單和廣播）。測試在 listener_test.go 和 chat_test.go。先備：14 章 goroutine、15 章 channel、17 章 Mutex、18 章 context、30 章 synctest。

1. 監聽與接受連線

func run(ctx context.Context, addr string, logger *slog.Logger) error {
	ln, err := net.Listen("tcp", addr)
	if err != nil {
		return err
	}
	logger.Info("聊天室開張", "addr", ln.Addr().String())
	return NewServer(logger).Serve(ctx, ln)
}
func (s *Server) Serve(ctx context.Context, ln net.Listener) error {
	stop := context.AfterFunc(ctx, func() { ln.Close() }) // 讓卡在 Accept 的迴圈醒來
	defer stop()
	var wg sync.WaitGroup
	defer wg.Wait()
	for {
		conn, err := ln.Accept()
		if err != nil {
			s.room.Close("* 伺服器要關了，再見。")
			if ctx.Err() != nil {
				return nil
			}
			return err
		}
		wg.Go(func() { s.handle(ctx, conn) })
	}
}
  • localhost:9000 和 :9000：寫 :9000 會監聽所有網路介面，同一個網路裡的其他電腦也連得進來；localhost:9000 只接受本機的連線。預設用比較保守的那個，要開放時用 -addr 改。
  • Accept 不收 context：它會一直等到有人連進來。要讓它醒來，只能關掉 Listener，所以用 context.AfterFunc 在 ctx 取消時呼叫 ln.Close()（18 章）。關掉之後 Accept 回傳錯誤，迴圈就結束了。
  • wg.Go 和 defer wg.Wait()：Serve 回傳之前，一定等所有連線都處理完。呼叫 Serve 的人可以放心地認為「回傳了就全部結束了」，測試也靠這一點確認沒有 goroutine 漏掉。
  • Accept 的其他錯誤：例如檔案描述元用完了，這種錯誤過一下可能就好了。net/http 的伺服器會從 5ms 開始等，每次加倍，最多等 1 秒再試；這裡直接結束，留給延伸挑戰。

2. 一行一行讀，加上期限

func readLine(conn net.Conn, sc *bufio.Scanner) (string, error) {
	conn.SetReadDeadline(time.Now().Add(idleTimeout))
	if sc.Scan() {
		return sc.Text(), nil
	}
	return "", cmp.Or(sc.Err(), io.EOF) // Err 在讀到結尾時是 nil
}

func writeLine(conn net.Conn, line string) error {
	conn.SetWriteDeadline(time.Now().Add(writeTimeout))
	_, err := io.WriteString(conn, line+"\n")
	return err
}
  • SetReadDeadline：時間到了還沒讀到東西，Read 回傳的錯誤包著 os.ErrDeadlineExceeded，用 errors.Is 判斷。不設期限的話，連上就不說話的人會永遠佔著一個連線和兩個 goroutine。
  • 寫也要有期限：對方不讀的時候，Write 會一直等下去。writeTimeout 是 10 秒，超過就當作他跟不上（第 5 節）。
  • Scanner 的上限：sc.Buffer(…, maxLine) 讓一行連同換行最多 512 bytes，大約 170 個中文字。超過時 Scan 回傳 false、Err 是 bufio.ErrTooLong。預設的上限是 64KB，聊天用不到那麼長；設小一點，有人送來一大串不換行的資料時，很快就會被擋下來（02 章）。TestLineLimit 確認 511 bytes 可以送、512 bytes 會被請出去。
  • Scanner 停了就不能再用：Scan 回傳 false 之後，不管是哪一種錯誤，都不會再讀。所以逾時、太長都直接結束這個連線，不試著「跳過這一行」。
  • \r\n：telnet 和 Windows 的工具送 \r\n，ScanLines 會把行尾的 \r 一起拿掉，不用自己處理。
  • cmp.Or(sc.Err(), io.EOF)：讀到結尾時 Err 是 nil，這時回傳 io.EOF，呼叫的人就不用分兩種情況。

3. 暱稱與輸入檢查

連進來的第一件事是問暱稱。這時還沒有 writeLoop，所以直接寫給對方：

func (s *Server) join(conn net.Conn, sc *bufio.Scanner) (*member, error) {
	prompt := "歡迎來到午餐聊天室！請輸入暱稱："
	for range maxTries {
		if err := writeLine(conn, prompt); err != nil {
			return nil, err
		}
		line, err := readLine(conn, sc)
		if err != nil {
			return nil, err
		}
		m, err := s.room.Join(strings.TrimSpace(line))
		if err == nil || errors.Is(err, errClosed) {
			return m, err
		}
		prompt = "* " + err.Error() + "，請再輸入一次："
	}
	writeLine(conn, "* 試太多次了，再見。")
	return nil, errors.New("暱稱試太多次")
}
func checkNick(nick string) error {
	switch n := utf8.RuneCountInString(nick); {
	case n == 0:
		return errors.New("暱稱不能是空的")
	case n > maxNick:
		return fmt.Errorf("暱稱最多 %d 個字", maxNick)
	}
	for _, c := range nick {
		if !unicode.IsLetter(c) && !unicode.IsDigit(c) {
			return fmt.Errorf("暱稱只能用文字和數字，不能有 %q", c)
		}
	}
	return nil
}
  • 檢查放在 Room 裡：Join 和 Rename 都呼叫 checkNick。規則只寫在一個地方，不管從哪裡改名都擋得住。
  • 最多試 3 次：不然有人可以一直送錯的暱稱，佔著連線不走。
  • 用字數，不用 byte 數：utf8.RuneCountInString 算出的才是「12 個字」；len 的話一個中文字算 3（08 章）。
  • %q 顯示看不見的字元：錯誤訊息裡的空白顯示成 ' '，控制字元顯示成 '\x1b'，使用者才知道哪裡不對。

聊天的內容也要清理。終端機看到 ESC 開頭的字元會當成控制碼，而不是文字：

func clean(s string) string {
	return strings.Map(func(c rune) rune {
		if unicode.IsControl(c) {
			return -1
		}
		return c
	}, strings.ToValidUTF8(s, "�"))
}
func Example_clean() {
	for _, s := range []string{
		"\x1b[2J\x1b[31m大家好\x1b[0m", // 清掉畫面、改成紅字
		"便當\a\a\a到了",                // 響鈴
		"排骨\xff飯",                   // 不合法的 UTF-8
	} {
		fmt.Printf("%q\n", clean(s))
	}
	// Output:
	// "[2J[31m大家好[0m"
	// "便當到了"
	// "排骨�飯"
}

"便當到了"

  • 不要相信輸入：伺服器把一個人送來的 byte 原封不動轉給其他人，等於讓任何人都能控制其他人的終端機。拿掉控制字元之後，剩下的 [2J 只是普通的文字。
  • ToValidUTF8：不合法的 UTF-8 換成 U+FFFD（顯示成 �）。轉給其他人的一定是合法的 UTF-8，他們的終端機不用猜那些 byte 要怎麼顯示。

4. 聊天室：一把鎖保護名單

type Room struct {
	mu      sync.Mutex
	members map[string]*member // 暱稱 → 成員
	closed  bool               // 伺服器要關了，不再讓人進來
}

type member struct {
	nick string
	out  chan string
}

func (r *Room) Say(m *member, text string) {
	r.mu.Lock()
	defer r.mu.Unlock()
	if r.hasLocked(m) {
		r.broadcastLocked(m, m.nick+"："+text)
	}
}

func (r *Room) broadcastLocked(from *member, line string) {
	var slow []*member
	for _, m := range r.members {
		if m != from && !offer(m, line) {
			slow = append(slow, m)
		}
	}
	// map 的順序是隨機的；排序之後，好幾個人同時跟不上時，公告的順序也固定。
	slices.SortFunc(slow, func(a, b *member) int { return strings.Compare(a.nick, b.nick) })
	for _, m := range slow {
		r.leaveLocked(m, "跟不上，斷線了")
	}
}

func offer(m *member, line string) bool {
	select {
	case m.out <- line:
		return true
	default:
		return false
	}
}
  • 持有鎖時不做 I/O：如果 broadcast 直接寫到每個人的連線，一個人卡住 10 秒，所有想說話、想進來的人都要跟著等 10 秒。這是聊天室最容易犯的錯（17 章）。
  • buffered channel 當待送區：容量是 outboxSize（16）。offer 用 select 加 default，放不下就馬上回傳 false，絕不等待（15 章）。
  • Locked 結尾的方法：表示呼叫的人必須已經持有 mu。公開的 Say、Tell 負責加鎖，再呼叫這些方法；Locked 方法互相呼叫時不能再加鎖，因為 Go 的 Mutex 不能重複鎖（17 章）。
  • 誰關閉 out：只有 Room，而且在持有鎖的時候。所有送進 out 的動作也都在鎖裡面，所以不會送進已經關閉的 channel（那會 panic），也不會關兩次（15 章）。
  • hasLocked：一個人被請出去之後，他的 handler 可能還沒發現，還在呼叫 Tell。先確認他還在名單上，才碰他的 out。
  • 另一種寫法：讓一個 goroutine 擁有名單，其他人用 channel 送請求給它，就不需要鎖。這兩種都是常見的寫法；這裡選鎖，是因為 Join、Rename 要回傳錯誤，用 channel 的話每個請求都要附一個回覆用的 channel，程式比較長。延伸挑戰 5 讓你寫寫看另一種。

5. 跟不上的人

func (s *Server) writeLoop(m *member, conn net.Conn) {
	defer conn.Close()
	for line := range m.out {
		if err := writeLine(conn, line); err != nil {
			why := "離開了"
			if errors.Is(err, os.ErrDeadlineExceeded) {
				why = "跟不上，斷線了"
			}
			s.room.Leave(m, why)
			return
		}
	}
}
func (r *Room) leaveLocked(m *member, why string) {
	if !r.hasLocked(m) {
		return
	}
	delete(r.members, m.nick)
	close(m.out) // 他的 writeLoop 會把剩下的寫完，再關掉連線
	if why != "" {
		r.broadcastLocked(nil, "* "+m.nick+" "+why)
	}
}
  • 為什麼請他離開，而不是丟掉訊息：丟掉的話，他會漏看幾句話卻不知道，聊天的上下文就斷了。斷線至少是明確的，他重新連進來就好。也有系統選擇丟掉最舊的訊息，例如即時的股價，只有最新的值有意義。
  • 不能讓一個人拖累所有人：如果 broadcast 用阻塞的 m.out <- line，阿明的待送區一滿，持有鎖的 broadcast 就會停住，整個聊天室跟著停住。
  • 先寫完再關：leaveLocked 只關閉 out。writeLoop 的 range 會先把 channel 裡剩下的訊息拿完才結束，所以「太久沒說話，先斷線了。」這種最後一句話送得到。
  • 真的 TCP 比較寬容：作業系統在兩端都有緩衝區，對方不讀時，Write 要等緩衝區滿了才會卡住，所以真的被請出去的時間比測試晚。測試用的 net.Pipe 沒有緩衝，每次 Write 都要等對方讀，TestSlowUser 才能精確地在第 18 行看到他被請出去。

6. 指令

func (s *Server) chat(m *member, conn net.Conn, sc *bufio.Scanner) error {
	for {
		line, err := readLine(conn, sc)
		if err != nil {
			return err
		}
		line = strings.TrimSpace(clean(line))
		if line == "" {
			continue
		}
		if !strings.HasPrefix(line, "/") {
			s.room.Say(m, line)
			continue
		}
		cmd, arg, _ := strings.Cut(line, " ")
		switch cmd {
		case "/quit":
			return nil
		case "/who":
			s.room.Who(m)
		case "/nick":
			if err := s.room.Rename(m, strings.TrimSpace(arg)); err != nil {
				s.room.Tell(m, "* "+err.Error())
			}
		case "/help":
			s.room.Tell(m, "* 指令：/who 看誰在線上、/nick 新暱稱 改名、/quit 離開")
		default:
			s.room.Tell(m, "* 沒有 "+cmd+" 這個指令，輸入 /help 看指令")
		}
	}
}
  • strings.Cut：把「/nick 明哥」切成指令和參數。沒有空白時，arg 是空字串，交給 Rename 的 checkNick 回報「暱稱不能是空的」。
  • 先 clean 再判斷：控制字元先拿掉，指令和一般的話都用清理過的內容。
  • 錯誤只告訴一個人：打錯指令、改名失敗都用 Tell，不會吵到其他人。
  • /quit 回傳 nil：和對方直接關掉 nc（讀到 io.EOF）一樣，都算「離開了」；只有逾時和太長兩種錯誤會換成其他說法。
func (r *Room) Rename(m *member, nick string) error {
	if err := checkNick(nick); err != nil {
		return err
	}
	r.mu.Lock()
	defer r.mu.Unlock()
	if !r.hasLocked(m) {
		return nil
	}
	if r.members[nick] != nil {
		return errNickTaken
	}
	old := m.nick
	delete(r.members, old)
	m.nick = nick
	r.members[nick] = m
	r.broadcastLocked(nil, "* "+old+" 改名為 "+nick)
	return nil
}
  • 改名要在一把鎖裡完成：檢查新名字有沒有人用、刪掉舊的 key、加上新的 key，三步之間不能讓別人插進來，不然兩個人可能同時改成同一個名字。
  • m.nick 只在鎖裡改：其他 goroutine 在廣播時會讀到它，也都在鎖裡面。go test -race 會檢查這件事。

7. 一個連線的一生與關機

func (s *Server) handle(ctx context.Context, conn net.Conn) {
	addr := conn.RemoteAddr().String()
	s.log.Info("連線", "addr", addr)
	sc := bufio.NewScanner(conn)
	sc.Buffer(make([]byte, 0, maxLine), maxLine)

	// 還在輸入暱稱時伺服器要關了：直接斷線。進了聊天室之後改由 Room.Close 道別。
	stop := context.AfterFunc(ctx, func() { conn.Close() })
	m, err := s.join(conn, sc)
	stop()
	if err != nil {
		conn.Close()
		s.log.Info("離線", "addr", addr, "err", err)
		return
	}

	done := make(chan struct{})
	go func() {
		defer close(done)
		s.writeLoop(m, conn)
	}()

	err = s.chat(m, conn, sc)
	why := "離開了"
	switch {
	case errors.Is(err, os.ErrDeadlineExceeded):
		s.room.Tell(m, "* 太久沒說話，先斷線了。")
		why = "太久沒說話，斷線了"
	case errors.Is(err, bufio.ErrTooLong):
		s.room.Tell(m, "* 一行太長了，先斷線了。")
		why = "送了太長的訊息，斷線了"
	}
	s.room.Leave(m, why) // 已經被請出去的話什麼都不做
	<-done               // writeLoop 寫完剩下的訊息、關掉連線之後才算結束
	s.log.Info("離線", "addr", addr, "err", err)
}
  • 兩個階段：還在輸入暱稱時，伺服器要關了就直接關掉連線（AfterFunc）；進了聊天室之後，改由 Room.Close 道別。stop() 取消前一個階段的 AfterFunc。
  • <-done：handle 等 writeLoop 結束才回傳。Serve 的 wg 只追蹤 handle，這樣也就間接等到了 writeLoop，不會留下還在寫的 goroutine。
  • Leave 可以重複呼叫：被請出去的人、伺服器關閉時的每一個人，handler 最後都還會呼叫一次 Leave；已經不在名單上就什麼都不做。
func (r *Room) Close(notice string) {
	r.mu.Lock()
	defer r.mu.Unlock()
	r.closed = true
	r.broadcastLocked(nil, notice)
	for _, m := range r.members {
		r.leaveLocked(m, "")
	}
}
func main() {
	addr := flag.String("addr", "localhost:9000", "監聽的位址")
	flag.Parse()
	logger := slog.New(slog.NewTextHandler(os.Stderr, nil))

	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt)
	context.AfterFunc(ctx, stop) // 第一次 Ctrl-C 之後恢復預設行為：道別卡住時，再按一次就直接結束
	err := run(ctx, *addr, logger)
	stop()
	if err != nil {
		logger.Error("聊天室停止", "err", err)
		os.Exit(1)
	}
}
  • closed：關機的時候剛好有人輸入完暱稱，Join 會回傳 errClosed，而不是讓他進來之後馬上又被關掉。
  • 最久等多久：一個完全不讀的人，writeLoop 要等 writeTimeout 才放棄。所以按下 Ctrl-C 之後最多大約 10 秒，程式一定會結束。
  • Ctrl-C 按第二次：NotifyContext 在 stop() 之前會一直攔下訊號，第二次 Ctrl-C 等於沒按。context.AfterFunc(ctx, stop) 在第一次訊號、ctx 取消時就呼叫 stop()，恢復預設行為，不想等的人再按一次就能直接結束（21 章）。

8. 不開 port 的測試

type pipeListener struct {
	conns chan net.Conn
	done  chan struct{}
	once  sync.Once
}

func (l *pipeListener) Accept() (net.Conn, error) {
	select {
	case c := <-l.conns:
		return c, nil
	case <-l.done:
		return nil, net.ErrClosed
	}
}

func (l *pipeListener) Close() error {
	l.once.Do(func() { close(l.done) })
	return nil
}

func (l *pipeListener) dial() net.Conn {
	server, client := net.Pipe()
	l.conns <- server
	return client
}
  • 為什麼不用真的 TCP：真的網路要開 port，可能和別的程式衝突；更重要的是，卡在網路 I/O 上的 goroutine，synctest 不認為它「durably blocked」，假時間就不會前進。net.Pipe 是用 channel 做的，在泡泡裡建立就沒有這個問題。
  • Accept 的語意：關閉之後回傳 net.ErrClosed，和真的 Listener 一樣，Serve 才會走到「ctx 取消了，正常結束」那一條路。sync.Once 讓 Close 可以呼叫很多次。
func (ct *chatTest) settle() {
	synctest.Wait()
	for _, u := range ct.users {
		for _, line := range u.take() {
			ct.note(u.name + " 收到：" + line)
		}
	}
}
  • synctest.Wait：等泡泡裡的每個 goroutine 都停下來，也就是訊息都送到了、每個人都在等下一行。這時再收集每個人讀到的東西，逐字稿每次都一樣，不需要 time.Sleep 碰運氣（30 章）。
func TestIdle(t *testing.T) {
	synctest.Test(t, func(t *testing.T) {
		ct := start()
		a := ct.connect("A", 0)
		ct.send(a, "小美")
		b := ct.connect("B", 0)
		ct.send(b, "阿明")
		ct.log.Reset()

		time.Sleep(idleTimeout - time.Second)
		ct.send(a, "還有人在嗎？")    // 小美重新計時，阿明沒有
		time.Sleep(time.Second) // 阿明剛好滿 5 分鐘
		ct.settle()
		time.Sleep(idleTimeout - time.Second) // 小美也滿 5 分鐘
		ct.settle()
		ct.shutdown(t)

		want := `A 送出：還有人在嗎？
B 收到：小美：還有人在嗎？
A 收到：* 阿明 太久沒說話，斷線了
B 收到：* 太久沒說話，先斷線了。
B 收到：（連線結束）
A 收到：* 太久沒說話，先斷線了。
A 收到：（連線結束）
伺服器關閉
`
		if got := ct.log.String(); got != want {
			t.Errorf("逐字稿：\n%s\n想要：\n%s", got, want)
		}
	})
}
  • 5 分鐘一瞬間跑完：泡泡裡的 time.Sleep 不會真的等。小美在第 4 分 59 秒說了話，所以阿明先被請出去，小美再過 4 分 59 秒才輪到。
  • 邊界都測到：TestWriteTimeout 確認 writeLoop 在 10 秒前一奈秒還沒放棄、剛好 10 秒時放棄；TestSlowUser 確認第 17 行還放得下、第 18 行放不下。
  • 並行的測試：TestConcurrentSay 讓五個人同時各說三句，檢查每個人都收到其他人的 12 句，而且同一個人說的話順序不變。用 go test -race 跑，鎖漏了任何一個地方都會被抓到。

延伸挑戰

這些題目沒有附測試。先用 chatTest 寫一段描述需求的逐字稿，再改程式。

  1. 入門挑戰 1：私訊

    加一個指令 /msg 暱稱 內容，只有那個人收到「（私訊）小美：內容」。對方不在時，告訴送出的人。

    提示

    在 Room 加一個 Whisper 方法，在鎖裡找到對方，用 tellLocked 送出。內容要用 strings.Cut 再切一次。

  2. 入門挑戰 2：最近的 10 句話

    新進來的人在歡迎訊息之後，先看到最近的 10 句話，才不會不知道大家在聊什麼。

    提示

    Room 多一個長度最多 10 的 []string，Say 時加到最後、超過就去掉最前面的。注意 10 句加上歡迎訊息不能超過待送區的容量。

  3. 進階挑戰 3：團購統計

    加上 /order 排骨飯 登記自己要的便當（再登記一次會覆蓋），/orders 列出每一種的數量和誰訂的。改名之後，訂單要跟著新名字。

    提示

    訂單是 map[*member]string，用 member 當 key，改名就不用搬資料；列出時再依暱稱排序。想想有人離開之後，他的訂單要不要留著。

  4. 進階挑戰 4：限制發言速度

    每個人每 10 秒最多說 5 句，超過的話告訴他「說太快了」，那一句不送出。用 synctest 測試第 6 句被擋下、等 10 秒之後又可以說。

    提示

    每個人記住最近 5 句的時間，第 6 句的時間和第 1 句相差不到 10 秒就擋下。這個狀態只有他自己的 handler 會用，放在 chat 函式的區域變數裡就好，不需要鎖。

  5. 挑戰挑戰 5：沒有鎖的聊天室

    改寫 Room：由一個 goroutine 擁有名單，Join、Say、Leave 都改成送請求到 channel。所有現有的測試都要通過，再比較兩個版本的程式碼量，以及哪一個比較容易看出正確性。

    提示

    需要回傳結果的請求（Join、Rename）附一個 reply channel。關機時這個 goroutine 也要結束，不然 synctest 會發現它還卡在那裡（19 章）。

重點回顧

  • net.Listen、Accept 的迴圈、每個連線一個 goroutine；Accept 不收 context，取消時關掉 Listener 讓它醒來。
  • 讀和寫用兩個 goroutine，一個人寫不出去，不會影響讀他說的話。
  • deadline 是時間點，每次讀寫之前重新設定；逾時的錯誤用 errors.Is(err, os.ErrDeadlineExceeded) 判斷。
  • Scanner 一定要設上限；使用者送來的內容要拿掉控制字元、修正不合法的 UTF-8。
  • 持有鎖的時候不做 I/O。廣播只把訊息放進待送區，放不下就請他離開，不讓一個人拖累所有人。
  • channel 由送的那一方關閉；所有送和關都在同一把鎖裡，就不會送進已經關閉的 channel。
  • 關機要照順序：停止接受、道別、寫完、關連線、等所有 goroutine 結束才回傳。
  • 伺服器只依賴 net.Listener 這個 interface，測試就能用 net.Pipe 和 synctest，不開 port、不真的等待。
