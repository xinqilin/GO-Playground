工具鏈

便當店的廚房不用到處借工具：刀、砧板、蒸籠、打包機都在同一面牆上。go 指令也是這樣，排版、檢查、測試、編譯、交叉編譯、產生程式碼、查文件，都是同一個指令的子命令，不用另外裝外掛或寫設定檔。這一章帶你把牆上每一樣工具拿下來用一次。

1. 一個指令，一整箱工具

Java 專案要先選 Maven 或 Gradle、寫設定檔、裝外掛；Go 的工具都在 go 指令裡，而且行為由 go.mod 和原始碼本身決定，沒有另外的建置腳本。這一章的程式是一支小小的「便當店點餐機」，重點不在程式本身，而在怎麼用 go 指令建置它。

先認識兩個查詢用的指令。go env 印出目前的設定：

go env GOOS GOARCH GOVERSION

arm64

2. go vet：編得過，但幾乎一定錯

下面這支程式編得過、也跑得起來，但 JSON 的欄位名稱不是你想的那樣：

package main

import (
	"encoding/json"
	"fmt"
)

type Dish struct {
	Name  string `json:"name"`
	Price int    `json:price`
}

func main() {
	b, _ := json.Marshal(Dish{Name: "排骨飯", Price: 90})
	fmt.Println(string(b))
}

go vet

main.go:10:2: struct field tag `json:price` not compatible with reflect.StructTag.Get: bad syntax for struct tag value

tag 的值少了雙引號，encoding/json 讀不到它，只好用欄位名稱，輸出變成 {"name":"排骨飯","Price":90}。編譯器不檢查 tag 的內容，執行也不會出錯，只有 vet 會發現。前面幾章出現過的 vet 檢查還有：

  • printf：Printf 的動詞和參數型別不合（02 章）。
  • copylocks：值 receiver 或傳值時複製了 Mutex、WaitGroup（09 章）。
  • lostcancel：context.WithTimeout 回傳的 cancel 沒有呼叫（18 章）。
  • errorsas、stringintconv、waitgroup：errors.As 的第二個參數不是指標、string(65) 這種轉換、在新的 goroutine 裡才呼叫 wg.Add。

全部的分析器用 go tool vet help 列出來。go test 在編譯測試時會自動跑其中最可靠的一部分（atomic、bools、buildtag、directive、errorsas、ifaceassert、nilfunc、printf、stdversion、stringintconv、tests），其中有問題就不跑測試。copylocks 不在裡面，所以「測試都過了」不代表 vet 也會過：

// Package vetsubset 的 Next 方法用了值 receiver，複製了整把鎖。
// go test 會通過，go vet 才抓得到。
package vetsubset

import "sync"

// Queue 是排隊叫號機。
type Queue struct {
	mu   sync.Mutex
	next int
}

// Next 回傳下一個號碼。
func (q Queue) Next() int {
	q.mu.Lock()
	defer q.mu.Unlock()
	q.next++
	return q.next
}
go -C chapters/32-toolchain/testdata/vetsubset test -count=1 .
go -C chapters/32-toolchain/testdata/vetsubset vet .

輸出

ok  	example.com/vetsubset	0.378s
queue.go:14:9: Next passes lock by value: example.com/vetsubset.Queue contains sync.Mutex

Next 每次都在複本上加一，叫號機永遠只叫得出 1 號。測試只檢查了第一個號碼，剛好通過。所以 CI 要同時跑 go vet 和 go test，這個 repo 的 CI 就是這樣做的。本章的 toolchain_test.go 會實際執行這兩個指令，確認結果和頁面一致。

3. go fix：換成新寫法

Go 每一版都會加入新的語法和標準庫函式，舊程式還是能編譯，只是寫法比較囉嗦。下面這個 module 故意用了舊寫法，它的 go.mod 寫的是 go 1.27：

// Package oldstyle 用比較舊的寫法整理菜單，用來看 go fix 會建議怎麼改。
package oldstyle

import (
	"sort"
	"strings"
	"sync"
)

// Lookup 在 menu 裡找菜名，找不到回傳 nil。
func Lookup(menu map[string]interface{}, name string) interface{} {
	return menu[name]
}

// Sorted 回傳排序好的價格。
func Sorted(prices []int) []int {
	sort.Slice(prices, func(i, j int) bool { return prices[i] < prices[j] })
	return prices
}

// HasDish 回傳 menu 裡有沒有 name。
func HasDish(menu []string, name string) bool {
	for _, d := range menu {
		if d == name {
			return true
		}
	}
	return false
}

// Note 取出「備註：」後面的文字。
func Note(line string) string {
	if strings.HasPrefix(line, "備註：") {
		return strings.TrimPrefix(line, "備註：")
	}
	return ""
}

// CookAll 同時處理每一張單。
func CookAll(orders []string, cook func(string)) {
	var wg sync.WaitGroup
	for _, o := range orders {
		wg.Add(1)
		go func() {
			defer wg.Done()
			cook(o)
		}()
	}
	wg.Wait()
}
go -C chapters/32-toolchain/testdata/oldstyle fix -diff ./...

  • -diff 只印出建議、不改檔案；拿掉它，go fix ./... 就直接改寫。改完用 git diff 看一遍再 commit。
  • 五個改寫：interface{} 換成 any（Go 1.18 起）；sort.Slice 換成 slices.Sort（Go 1.21 起），連 import 都一起改；手寫的搜尋迴圈換成 slices.Contains；HasPrefix 加 TrimPrefix 換成 strings.CutPrefix（Go 1.20 起）；wg.Add 加 go func 換成 wg.Go（Go 1.25 起，14 章）。
  • go fix 只會用 go.mod 的 go 版本允許的功能。同一個檔案，go.mod 改成 go 1.21 再跑一次，就只剩前四個建議：wg.Go 要 Go 1.25 才有。
  • 函式庫的作者可以在要淘汰的函式上加 //go:fix inline，使用者執行 go fix 時，呼叫的地方會自動換成新的寫法。
  • 這本手冊有幾章故意保留舊寫法做對照（例如 03 章的三段式 for、14 章的 wg.Add），go fix 會對它們提出建議，這是預期中的。

4. build tag 與檔名

點餐機有免費版和專業版，差別只在一個常數。兩個檔案各自宣告 edition，用 build tag 決定編哪一個：

//go:build !pro

package main

// edition 在沒有加 -tags pro 時使用這個檔案。
const edition = "免費版"
//go:build pro

package main

// edition 在加上 -tags pro 時使用這個檔案。
const edition = "專業版"

//go:build 必須在 package 子句之前，後面空一行。條件可以用 &&、||、! 和括號組合，例如 //go:build (linux || darwin) && !cgo。滿足的標籤有：目標的 GOOS 和 GOARCH、unix（類 Unix 系統）、cgo（cgo 啟用時）、go1.1 到目前版本的 go1.N，以及 -tags 給的自訂標籤。

只跟作業系統有關時，連 //go:build 都不用寫，用檔名就好：open_darwin.go 只在 GOOS=darwin 時編譯。其他系統沒有對應的檔名，open_other.go 就用 build tag 排除這兩個：

package main

// 檔名以 _darwin.go 結尾：只有 GOOS=darwin（macOS）時才會被編譯，不需要寫 //go:build。

// openCommand 回傳在這個作業系統上用預設瀏覽器打開網址的指令。
func openCommand() []string {
	return []string{"open"}
}
//go:build !darwin && !windows

package main

// 其他系統（Linux、各種 BSD…）沒有對應的檔名，用 build 條件排除 darwin 和 windows。

// openCommand 回傳在這個作業系統上用預設瀏覽器打開網址的指令。
func openCommand() []string {
	return []string{"xdg-open"}
}

go list 可以直接看到某種建置下用了哪些檔案（GoFiles）、略過了哪些（IgnoredGoFiles）：

go list -f '{{.GoFiles}} {{.IgnoredGoFiles}}' ./chapters/32-toolchain
GOOS=windows go list -f '{{.GoFiles}} {{.IgnoredGoFiles}}' ./chapters/32-toolchain
GOOS=linux go list -tags pro -f '{{.GoFiles}} {{.IgnoredGoFiles}}' ./chapters/32-toolchain

[edition_free.go main.go menu.go menu_gen.go open_windows.go] [edition_pro.go open_darwin.go open_other.go]

  • 檔名規則的細節（_test 怎麼處理、第一個底線前面不算、linux.go 為什麼不算）是練習 3 的主題。
  • 這個 repo 的練習題就是 build tag 的應用：exercises.go 是 //go:build !solution，solution.go 是 //go:build solution，go test -tags solution 換成參考解答。
  • 看到 // +build 這種寫法，是 Go 1.17 以前的舊語法，新程式只寫 //go:build。

5. 交叉編譯

GOOS=linux GOARCH=amd64 go build -o app ./chapters/32-toolchain       # Linux 伺服器
GOOS=windows GOARCH=amd64 go build -o app.exe ./chapters/32-toolchain # Windows
go tool dist list                                                     # 所有支援的 GOOS/GOARCH 組合
go tool dist list | wc -l

最後一行的輸出（Go 1.27.4）

      47
  • Linux 常見的組合是 amd64 和 arm64（雲端的 ARM 主機、樹莓派）。Windows 和 macOS 也各有 amd64、arm64。
  • cgo：用到 C 程式庫的 package 需要目標平台的 C 編譯器，交叉編譯時 cgo 預設是關的。只用標準庫的程式不受影響。明確設定 CGO_ENABLED=0 會得到不依賴系統 C 函式庫的執行檔，適合放進極簡的容器映像。
  • 編出來的檔案不能在 Mac 上直接執行，但 go version app.exe 讀得到它的建置資訊（下一節）。toolchain_test.go 用檔案開頭的幾個 byte 確認 Linux 版是 ELF、Windows 版是 PE（開頭是 MZ）。
  • 編譯產物不要 commit。這個 repo 早期放過 .exe 檔，後來從 git 移除了；要發佈執行檔，用 GitHub Releases 這類地方。

6. 版本與建置資訊

var version = "dev"

func describe() string {
	return fmt.Sprintf("版本 %s，%s", version, edition)
}

func buildInfoDemo() {
	info, ok := debug.ReadBuildInfo()
	if !ok {
		fmt.Println("沒有建置資訊")
		return
	}
	fmt.Printf("Go 版本：%s\n", info.GoVersion)
	fmt.Printf("module 版本：%s\n", info.Main.Version)
	for _, s := range info.Settings {
		switch s.Key {
		case "-tags", "-ldflags", "GOOS", "GOARCH", "vcs.revision", "vcs.modified":
			fmt.Printf("%s = %s\n", s.Key, s.Value)
		}
	}
}

  • -X 的規則：只能改 package 層級的 string 變數，不能改常數；變數的初始值必須是常數字串或沒有初始值，初始值呼叫了函式就沒有效果，而且不會報錯。不在 main 的變數要寫完整的 import path，例如 -X github.com/xinqilin/GO-Playground/internal/build.Version=1.2.3。

  • 程式裡用 runtime/debug.ReadBuildInfo 讀同樣的資訊，也就是 buildInfoDemo 做的事。練習 4 用它決定程式要顯示的版本。
  • module 版本：Go 1.24 起，go build 會依 git 的 tag 和 commit 填入 main module 的版本，有未 commit 的改動時加上 +dirty，上面的 v0.0.0-20261120175533-e29293b9197c+dirty 就是這樣來的。go run 不寫入版本控制的資訊，所以 go run ./chapters/32-toolchain 看到的是 (devel)。
  • -ldflags "-s" 去掉符號表和除錯資訊，執行檔變小，但 Delve 這類除錯器就沒辦法用了。

7. go generate

菜單常常改，每次手動改 Go 程式容易出錯。把菜單放在 CSV，讓程式產生 Go 原始碼：

菜名,價格
排骨飯,90
雞腿飯,100
滷肉飯,50
魚排飯,95
素食便當,80
package main

import "fmt"

// 改了 menu.csv 之後，在這個目錄執行 go generate，menu_gen.go 就會重新產生。
//go:generate go run ./genmenu -in menu.csv -out menu_gen.go

// dish 是菜單上的一道菜。menu 這個變數在 menu_gen.go，由 genmenu 產生。
type dish struct {
	name  string
	price int
}

// menuDemo 印出產生出來的菜單。
func menuDemo() {
	for _, d := range menu {
		fmt.Printf("%s %d 元\n", d.name, d.price)
	}
}

//go:generate 後面就是要執行的指令，工作目錄是這個檔案所在的目錄。產生器是同一個 repo 裡的一支小程式，用 23 章的 encoding/csv 讀資料，最後交給 go/format 排版：

func generate(r io.Reader, source string) ([]byte, error) {
	rows, err := csv.NewReader(r).ReadAll()
	if err != nil {
		return nil, err
	}
	if len(rows) < 2 {
		return nil, errors.New("菜單是空的")
	}
	var b bytes.Buffer
	fmt.Fprintf(&b, "// Code generated by genmenu from %s; DO NOT EDIT.\n\n", source)
	b.WriteString("package main\n\nvar menu = []dish{\n")
	for i, row := range rows[1:] {
		price, err := strconv.Atoi(row[1])
		if err != nil {
			return nil, fmt.Errorf("第 %d 行的價格：%w", i+2, err)
		}
		fmt.Fprintf(&b, "{%q, %d},\n", row[0], price)
	}
	b.WriteString("}\n")
	return format.Source(b.Bytes())
}
go generate -x ./chapters/32-toolchain   # -x 印出執行的指令

  • 產生的檔案要 commit：使用者 go install 你的程式時不會執行 go generate，產生器需要的工具也不一定裝了。
  • 用測試確認沒有過期：genmenu/main_test.go 的 TestMenuUpToDate 讀 menu.csv 重新產生一次，和 commit 的 menu_gen.go 比較。改了 CSV 卻忘了 go generate，CI 就會失敗。
  • Go 團隊維護的 stringer（golang.org/x/tools/cmd/stringer）是最常見的產生器：替一組常數產生 String 方法。協定、資料庫存取的程式碼也常用產生器。
  • //go:generate 的參數規則（引號、tab）是練習 5 的主題。

8. 專案用到的工具

這個 repo 只用標準庫，下面的指令沒有實際加進來；在你自己的專案裡執行它們，go.mod 就會多出 tool 和 require：

go get -tool golang.org/x/vuln/cmd/govulncheck   # 加進 go.mod 的 tool 指令
go tool govulncheck ./...                       # 檢查用到的依賴有沒有已知的漏洞
go get tool                                     # 把所有工具升到最新版
  • govulncheck 是 Go 官方的漏洞檢查工具，比對 Go 的漏洞資料庫。它會分析呼叫關係，只報告程式真的呼叫到的有漏洞的函式，所以雜訊很少。適合放進 CI。
  • Delve（dlv）是 Go 最常用的除錯器：設中斷點、一步一步執行、看變數和 goroutine。dlv debug ./chapters/32-toolchain 除錯程式，dlv test ./exercises/32-toolchain 除錯測試。VS Code 和 GoLand 的除錯功能背後用的就是它。GDB 也能用，但官方文件建議 Delve。
  • 只想試用一次的工具，可以不加進 go.mod，直接 go run golang.org/x/vuln/cmd/govulncheck@latest ./...。

深入：第一次讀可以先跳過

GOTOOLCHAIN 與 go env -w

go.mod 的 go 1.27 是這個 module 至少需要的 Go 版本。你的 go 比它舊時，預設的 GOTOOLCHAIN=auto 會自動下載夠新的工具鏈來用（00 章）。go.mod 還可以加一行 toolchain go1.27.4，指定「建議」使用的版本。GOTOOLCHAIN=local 則是只用目前安裝的版本，不自動下載。

go env -w GOFLAGS=-mod=mod 這類指令把設定寫進使用者的設定檔（go env GOENV 印出它的位置），之後每次執行 go 都會套用。很方便，但也容易忘記：別人用同樣的指令得到不同的結果時，先比對 go env 的輸出。要取消用 go env -u GOFLAGS。

常見錯誤

1. 只跑 go test，不跑 go vet

go test 只跑 vet 的一小部分，複製鎖這類問題要 go vet 才抓得到。CI 兩個都要跑（第 2 節）。

2. //go:build 的位置不對

寫在 package 子句後面，或和 package 說明的註解黏在一起，它就只是普通的註解，條件不會生效。放在檔案最前面，後面空一行。

3. 只在自己的平台上編譯

用了 _windows.go 檔案，卻從來沒有用 GOOS=windows 編譯過，某個函式漏了 Windows 版也不知道。CI 裡至少對每個支援的平台跑一次 go vet（第 4 節）。

4. -X 改不了版本

把 version 寫成常數，或初始值呼叫了函式，-X 都會默默沒有效果。用 package 層級的 string 變數，初始值寫常數字串；路徑要寫完整的 import path（第 6 節）。

5. 改了資料，忘了 go generate

go build 不會幫你執行 go generate，程式用的還是舊的產生結果。寫一個比對的測試（第 7 節）。

6. 手動修改產生的檔案

下次 go generate 就被蓋掉了。要改的是資料或產生器。

7. 把執行檔 commit 進 git

執行檔很大、每次建置都不同，而且只適用一個平台。加進 .gitignore，用 Releases 發佈（第 5 節）。

8. go fix 改完不看就 commit

改寫不應該改變行為，但還是要看過 diff、跑過測試。一次只套一種改寫，review 起來比較容易（第 3 節）。

  1. 入門練習 1：交叉編譯的檔名

    一次編好幾個平台時，每個執行檔要有不同的名字。

    func BinaryName(name, goos, goarch string) string {
	// TODO: 實作
	return ""
}

    測試：TestBinaryName。

    提示

    字串相加就好，只有 goos 是 "windows" 時多加 .exe。

  2. 入門練習 2：判斷 build 條件

    不用自己寫 parser：標準庫有現成的 package。

    func Matches(expr string, tags []string) (bool, error) {
	// TODO: 實作
	return false, nil
}

    測試：TestMatches。

    提示

    constraint.Parse("//go:build " + expr)（go/build/constraint）回傳一個 Expr，它的 Eval(func(tag string) bool) 會對每個標籤呼叫你給的函式。

  3. 進階練習 3：檔名規則

    第 4 節的檔名規則。測試除了列出答案，還會和 go/build 的 MatchFile 比對。

    func FileMatches(name, goos, goarch string) bool {
	// TODO: 實作
	return false
}

    測試：TestFileMatches、TestFileMatchesTable。

    提示

    依序處理：strings.Cut 切掉第一個 . 之後、TrimSuffix 去掉 _test、strings.Cut 取第一個 _ 之後、strings.Split 以 _ 分段。注意 tools_unix.go：unix 不在 KnownOS 裡，所以檔名不算條件。

  4. 進階練習 4：要顯示哪個版本

    結合第 6 節的兩個來源：-X 注入的字串和建置資訊。

    func Version(info *debug.BuildInfo, injected string) string {
	// TODO: 實作
	return ""
}

    測試：TestVersion。

    提示

    info.Settings 是 []debug.BuildSetting，每一個有 Key 和 Value。先處理 info 是 nil 的情況。

  5. 挑戰練習 5：解析 //go:generate

    go generate 怎麼把一行註解切成指令和參數。

    func GenerateArgs(line string) ([]string, error) {
	// TODO: 實作
	return nil, nil
}

    測試：TestGenerateArgs。

    提示

    每一圈先去掉開頭的空白和 tab。不是雙引號開頭的參數，到下一個空白或 tab 為止；雙引號開頭的，往後找右引號，遇到反斜線就多跳過一個字元，找到後整段交給 strconv.Unquote。

  6. 找錯練習 6：誰是產生的檔案

    只要檔案裡出現 DO NOT EDIT 就當成產生的檔案，結果一支檢查工具把自己也跳過了。

    func IsGenerated(src []byte) bool {
	return bytes.Contains(src, []byte("DO NOT EDIT"))
}

    測試：TestIsGenerated。

    提示

    用 go/parser 的 ParseFile 加上 parser.PackageClauseOnly|parser.ParseComments 只解析到 package 子句，再交給 ast.IsGenerated（Go 1.21 起）。或者自己逐行檢查 package 之前的註解。

重點回顧

  • go 指令就是工具箱：go help 主題、go env 看設定、go doc 查文件、go list 看 package 的細節。
  • go vet 抓編得過但幾乎一定錯的寫法；go test 只跑其中一部分，CI 兩個都要跑。
  • go fix 依 go.mod 的版本把舊寫法換成新的，先用 -diff 看，改完 review。
  • //go:build 放在 package 之前、後面空一行；檔名 _GOOS、_GOARCH 也是條件。
  • GOOS/GOARCH 交叉編譯；每個支援的平台都要編譯檢查。
  • -ldflags -X 改 package 層級的 string 變數；go version -m、debug.ReadBuildInfo 讀建置資訊。
  • go generate 要手動執行，產生的檔案要有 Code generated 標頭、要 commit、要有測試確認沒過期。
  • go.mod 的 tool 指令管理工具版本；govulncheck 檢查漏洞，Delve 除錯。
