1. 送與收：無緩衝的 channel

channel 是一條有型別的管道：一個 goroutine 送值進去，另一個 goroutine 從另一端收。用 make(chan T) 建立，用 <- 送和收：

  • ch <- v：把 v 送進 ch。箭頭指向 channel。
  • v := <-ch：從 ch 收一個值。箭頭從 channel 指出來。
func handoffDemo() {
	window := make(chan string)
	go func() {
		window <- "排骨飯"
		window <- "雞腿飯"
	}()
	fmt.Println("拿到", <-window)
	fmt.Println("拿到", <-window)
}

輸出

拿到 排骨飯
拿到 雞腿飯

make(chan string) 建立的是無緩衝（unbuffered）的 channel，裡面沒有任何存放空間。廚房送出排骨飯時，如果 main 還沒來收，廚房就停在那一行等；main 收的時候，如果還沒有人送，main 也停著等。兩邊都到了，值才交出去，雙方再各自往下走。所以無緩衝的 channel 不只傳值，也是一個同步點。

利用這一點，channel 可以取代 WaitGroup，等一個 goroutine 做完：

func doneDemo() {
	done := make(chan struct{})
	var receipt string
	go func() {
		receipt = "排骨飯 x2，NT$170"
		close(done)
	}()
	<-done
	fmt.Println(receipt)
}

輸出

排骨飯 x2，NT$170
  • chan struct{} 的元素型別是空的 struct，不佔記憶體，表示「這個 channel 只用來通知，不傳任何資料」。
  • goroutine 寫好 receipt 之後 close(done)；main 的 <-done 一直等到 done 被 close 才返回（下一節會講 close）。
  • Go 的記憶體模型保證：close 之前寫的東西，在「因為 close 而返回的收」之後一定看得到。送也一樣：送之前寫的，收到之後看得到。所以 main 讀 receipt 是安全的，不是 data race。

2. 有緩衝的 channel

make 的第二個參數是容量：make(chan int, 3) 是一個可以先放三個值的 channel，像一個有三格的號碼牌架：

func bufferDemo() {
	tickets := make(chan int, 3)
	tickets <- 17
	tickets <- 18
	tickets <- 19
	fmt.Println(len(tickets), cap(tickets))

	fmt.Println("叫號", <-tickets)
	tickets <- 20
	fmt.Println(len(tickets), cap(tickets))

	fmt.Println("叫號", <-tickets, <-tickets, <-tickets)
	fmt.Println(len(tickets), cap(tickets))
}

輸出

3 3
叫號 17
3 3
叫號 18 19 20
0 3
  • 連放三個都沒有卡住，因為還有空格。整個示範都在同一個 goroutine 裡，這在無緩衝的 channel 上是做不到的。
  • 值是先進先出：先放的 17 先被拿走。
  • len(ch) 是目前放了幾個，cap(ch) 是容量。無緩衝的 channel 兩個都是 0。
  • 放滿了再送，送的一方就要等，等到有人拿走一個；空了再收，收的一方就要等。

容量要多大？大部分時候用無緩衝就好，它的行為最好推理：送出去了，就代表對方已經收到。只有在你說得出理由時才加緩衝，例如「一共會有 n 個結果，讓 n 個 goroutine 都能放下結果就結束，不必等人來收」（練習 5），或是吸收短暫的流量高峰。把緩衝加大來「修好」卡住的程式，通常只是把問題延後（常見錯誤 6）。

不要用 len 來判斷「現在能不能收」：你檢查完到真的去收之間，別的 goroutine 可能已經把值拿走了。len 和 cap 只適合拿來觀察和除錯。

3. close 與 range

收的一方怎麼知道沒有更多的值了？靠送的一方 close(ch)。for v := range ch 會一直收，直到 channel 被 close、而且裡面的值都收完：

func orders(items ...string) <-chan string {
	out := make(chan string)
	go func() {
		defer close(out)
		for _, it := range items {
			out <- it
		}
	}()
	return out
}

func rangeDemo() {
	for o := range orders("排骨飯", "雞腿飯", "魚排飯") {
		fmt.Println("出餐", o)
	}
}

輸出

出餐 排骨飯
出餐 雞腿飯
出餐 魚排飯

orders 是很常見的寫法：函式裡建立 channel，開一個 goroutine 去送，把 channel 回傳給呼叫的人。goroutine 用 defer close(out)，送完就 close。如果忘了 close，range 會在收完三份之後永遠等下去（練習 6）。

不用 range 時，可以用和 map 一樣的 comma-ok 寫法，分辨「收到一個零值」和「channel 已經 close 了」：

func closedDemo() {
	c := make(chan int, 2)
	c <- 17
	c <- 18
	close(c)
	for range 4 {
		v, ok := <-c
		fmt.Println(v, ok)
	}
}

輸出

17 true
18 true
0 false
0 false

close 不會丟掉已經在緩衝裡的值，17 和 18 照樣收得到，ok 是 true。收完之後，每一次收都立刻返回零值和 false，不會卡住。這也是為什麼 close 可以當「廣播」用：所有在等這個 channel 的 goroutine 會同時被叫醒；而一次送出只會叫醒一個收的人。

close 有三條規則，違反了就 panic：

func try(f func()) {
	defer func() {
		fmt.Println("panic:", recover())
	}()
	f()
}

func closePanicDemo() {
	c := make(chan int, 1)
	close(c)
	try(func() { c <- 1 })
	try(func() { close(c) })
	var never chan int
	try(func() { close(never) })
}

輸出

panic: send on closed channel
panic: close of closed channel
panic: close of nil channel

所以有一條簡單的規則：由送的一方 close，而且只 close 一次。收的一方不知道還有沒有人要送，它 close 了，送的一方一送就 panic。有好幾個送的 goroutine 時，誰都不該自己 close，要等全部送完再由一個人 close（第 6 節的 kitchen）。也不是每個 channel 都要 close：沒有人在 range 它、也沒有人在等「結束」的訊號時，不 close 也沒關係，channel 會跟其他值一樣被垃圾回收。

不同狀態的 channel，三種操作的結果整理如下：

操作nil channel開著的 channel已 close 的 channel
送 ch <- v永遠卡住有人收、或還有空格時完成panic
收 <-ch永遠卡住有值時完成先收完剩下的值，之後立刻得到零值和 false
close(ch)panic成功panic

深入：第一次讀可以先跳過

3.1 nil channel

channel 的零值是 nil：var ch chan int 沒有 make，就是 nil channel。對它送或收都會永遠卡住，這通常是 bug，例如 struct 裡有一個 channel 欄位卻忘了在建構函式裡 make。

但「永遠卡住」也有用處：在下一章的 select 裡，把某個 channel 變數設成 nil，就等於關掉那一個分支，select 再也不會選它。這是 select 常用的技巧。

4. 方向

channel 型別可以加上方向：chan<- T 只能送，<-chan T 只能收。把函式參數或回傳值寫成有方向的型別，誰送誰收就寫在簽名裡，用錯了編譯器會擋：

func announce(nums []int, out chan<- int) {
	for _, n := range nums {
		out <- n
	}
	close(out)
}

func display(in <-chan int) {
	for n := range in {
		fmt.Println("請", n, "號")
	}
}

func directionDemo() {
	ch := make(chan int)
	go announce([]int{17, 18, 19}, ch)
	display(ch)
}

輸出

請 17 號
請 18 號
請 19 號

main 裡 make 出來的 ch 是雙向的 chan int，傳給 announce 時自動轉成 chan<- int，傳給 display 時自動轉成 <-chan int。第 3 節的 orders 回傳 <-chan string 也是一樣的道理：呼叫的人只能收，不能送，也不能 close，close 的責任留在 orders 裡面。

在只能送的 channel 上收、或 close 一個只能收的 channel，都是編譯錯誤：

package main

import "fmt"

func announce(nums []int, out chan<- int) {
	for _, n := range nums {
		out <- n
	}
	fmt.Println("還有剩嗎？", <-out)
}

func display(in <-chan int) {
	for n := range in {
		fmt.Println("請", n, "號")
	}
	close(in)
}

func main() {
	ch := make(chan int)
	go announce([]int{17, 18, 19}, ch)
	display(ch)
}

編譯錯誤

./main.go:9:35: invalid operation: cannot receive from send-only channel chan<- int out (variable of type chan<- int)
./main.go:16:8: invalid operation: cannot close receive-only channel in (variable of type <-chan int)

「只能收的一方不能 close」由編譯器強制，正好對上第 3 節「由送的一方 close」的規則。回傳 channel 的函式，回傳型別幾乎都應該寫成 <-chan T。

5. 管線

每一站都是「收一個 channel、回傳一個 channel」的函式，就能一站接一站串起來：

func cook(in <-chan string) <-chan string {
	out := make(chan string)
	go func() {
		defer close(out)
		for o := range in {
			out <- o + "（熱）"
		}
	}()
	return out
}

func pack(in <-chan string) <-chan string {
	out := make(chan string)
	go func() {
		defer close(out)
		for m := range in {
			out <- "外帶袋[" + m + "]"
		}
	}()
	return out
}

func pipelineDemo() {
	for bag := range pack(cook(orders("排骨飯", "雞腿飯"))) {
		fmt.Println(bag)
	}
}

輸出

外帶袋[排骨飯（熱）]
外帶袋[雞腿飯（熱）]
  • 每一站都用同一個形狀：建立自己的 out，開 goroutine，for v := range in 處理每個值，defer close(out)。
  • close 會一路往下傳：orders 送完 close，cook 的 range 結束，cook 也 close，pack 跟著結束，最後 main 的 range 結束。每一站只 close 自己的輸出，不碰別人的。
  • 三站同時在跑：pack 在裝第一份排骨飯的時候，cook 已經在做第二份雞腿飯了。

這和 13 章用疊代器串的管線看起來很像，差別在於疊代器的管線全部在同一個 goroutine 裡，一次只做一件事；channel 的管線每一站是一個 goroutine，真的同時執行，但每傳一個值都要同步一次，成本比函式呼叫高得多。每一站做的是很快的計算時，用疊代器或一個普通的迴圈；某一站要等網路、等磁碟，或計算量大到值得分給好幾個核心時，channel 的管線才划得來。

6. fan-out 與 fan-in

某一站特別慢時，可以開好幾個 goroutine 一起做那一站：

  • fan-out：好幾個 goroutine 從同一個 channel 收。每個值只會被其中一個收走，工作自然就分攤了。
  • fan-in：好幾個 goroutine 送到同一個 channel，讓下游只需要收一個地方。
func kitchen(in <-chan string, cooks int) <-chan string {
	out := make(chan string)
	var wg sync.WaitGroup
	for range cooks {
		wg.Go(func() {
			for o := range in {
				out <- o + "好了"
			}
		})
	}
	go func() {
		wg.Wait()
		close(out)
	}()
	return out
}

func fanDemo() {
	var done []string
	for m := range kitchen(orders("排骨飯", "雞腿飯", "魚排飯", "滷肉飯", "控肉飯"), 3) {
		done = append(done, m)
	}
	slices.Sort(done)
	fmt.Println(len(done), done)
}

輸出

5 [排骨飯好了 控肉飯好了 滷肉飯好了 雞腿飯好了 魚排飯好了]

難的是 out 要由誰、在什麼時候 close：

  • 不能讓每位廚師做完就 close：第一位 close 之後，第二位一送就 panic。
  • 不能在 kitchen 裡 wg.Wait() 完才回傳：out 是無緩衝的，在有人收之前廚師全都卡在送出，Wait 永遠等不到，這就是死結。
  • 所以另外開一個 goroutine，專門等所有廚師結束再 close。kitchen 馬上回傳 out，呼叫的人開始收，廚師才送得出去。

哪位廚師做哪一份、哪一份先好，每次執行都不一樣，順序沒有保證。需要固定順序時，要嘛像這裡收完再排序，要嘛像 14 章那樣讓每個值帶著自己的索引，寫進對應的格子。限制同時有幾位廚師、讓整條管線可以中途取消，是「並行模式」那一章的主題。

7. 死結與洩漏

channel 的兩大問題都來自同一件事：送的一方等不到收的一方，或反過來。最直接的情況是在同一個 goroutine 裡對無緩衝的 channel 送值：

func main() {
	window := make(chan string)
	window <- "排骨飯" // 沒有其他 goroutine 會來收：main 永遠卡在這一行
	fmt.Println(<-window)
}

輸出（go run ./chapters/15-channels/deadlock，後面的 stack trace 省略）

fatal error: all goroutines are asleep - deadlock!

goroutine 1 [chan send]:
main.main()

main 在送出那一行等人來收，可是程式裡沒有其他 goroutine，永遠不會有人來。runtime 發現所有 goroutine 都卡住了，就以 fatal error 結束程式，訊息會告訴你卡在哪裡（chan send）。這不是 panic，recover 接不到。要注意 runtime 只在所有 goroutine 都卡住時才看得出來；伺服器程式裡總有其他 goroutine 在跑，同樣的錯誤只會讓那一部分安靜地停住。

比較隱蔽的是洩漏：收的一方提早不收了，送的一方就卡在下一次送出，永遠不會結束：

錯：找到就 return，orders 裡的 goroutine 卡在送下一份

func findLeaky(items []string, want string) int {
	i := 0
	for o := range orders(items...) {
		if o == want {
			return i
		}
		i++
	}
	return -1
}

對：return 之前由 defer 把剩下的收完，送的一方才能送完、close、結束

func find(items []string, want string) int {
	ch := orders(items...)
	defer func() {
		for range ch {
		}
	}()
	i := 0
	for o := range ch {
		if o == want {
			return i
		}
		i++
	}
	return -1
}

輸出（find）

1

findLeaky 的回傳值完全正確，測試只看結果的話永遠抓不到這個 bug。Go 1.25 起，標準庫的 testing/synctest 可以在測試裡抓洩漏：synctest.Test 把測試放進一個「泡泡」，裡面開的 goroutine 都屬於這個泡泡；測試函式結束時，如果泡泡裡還有 goroutine 卡著、而且泡泡裡沒有人能叫醒它，測試就失敗：

func TestFindNoLeak(t *testing.T) {
	synctest.Test(t, func(t *testing.T) {
		if got := find([]string{"排骨飯", "雞腿飯", "魚排飯"}, "雞腿飯"); got != 1 {
			t.Errorf("find = %d, want 1", got)
		}
	})
}

這個測試對 find 會通過。把裡面的 find 換成 findLeaky 再跑一次，輸出如下（stack trace 省略）：

--- FAIL: TestFindNoLeak (0.00s)
panic: deadlock: main bubble goroutine has exited but blocked goroutines remain [recovered, repanicked]
…
goroutine 38 [chan send (durable), synctest bubble 1]:
github.com/xinqilin/GO-Playground/chapters/15-channels.orders.func1()

訊息直接指出卡住的 goroutine 是 orders 裡開的那一個，停在 chan send。synctest 還能控制時間，寫有 time.Sleep 的測試也不必真的等，詳見「測試」那一章。

修好洩漏有三種方向：

  • 收的一方收完：像 find 一樣把剩下的收掉。簡單，但送的一方產生剩下的值都白做了。
  • 讓送的一方不會卡住：已知一共會送幾個時，給 channel 足夠的緩衝，每個人都能放下就走（練習 5）。
  • 通知送的一方停下來：送的一方同時等「有人收」和「不用送了」兩件事，這要用下一章的 select，或「context」那一章的取消。

另外，像 find 這種「在同一個流程裡一個一個看、可能提早停」的需求，其實用 疊代器更合適：break 就會通知產生值的一方停下來，不需要額外的 goroutine。

常見錯誤

1. 送了卻沒有人收

在同一個 goroutine 裡對無緩衝的 channel 送值，或所有收的 goroutine 都已經結束，送的一方就永遠卡住（第 7 節）。送之前想清楚：誰會來收？

2. 收的一方 close，或 close 兩次

送的一方一送就 panic，close 兩次也 panic（第 3 節）。規則：由送的一方 close，只 close 一次；好幾個送的 goroutine 時，等全部送完再由一個人 close。

3. 忘了 close

range 收完所有的值之後會永遠等下去。在送值的 goroutine 裡第一行就寫 defer close(out)。

4. 不收了，送的 goroutine 就洩漏了

提早 return、只要第一個結果，剩下的送出就沒有人收（第 7 節）。用 synctest 寫測試抓出來，再選一種修法。

5. 忘了 make

var ch chan int 是 nil channel，送和收都永遠卡住，close 會 panic。struct 裡的 channel 欄位，要在建構函式裡 make。

6. 把緩衝加大來「修」卡住的程式

容量 10 的時候卡住，改成 100 就不卡了，直到某天進來 101 個。先找出為什麼沒有人收，緩衝只在你說得出容量的理由時才用。

7. 用 len 判斷能不能收

檢查和收之間，別的 goroutine 可能已經把值拿走了，收的時候還是會卡住。要「有就收、沒有就算了」，用下一章 select 的 default。

go test ./exercises/15-channels/                      # 跑全部練習
go test ./exercises/15-channels/ -run TestTickets     # 只跑一題
go test -race ./exercises/15-channels/                # 檢查 data race
go test -tags solution ./exercises/15-channels/       # 跑參考解答

  1. 入門練習 1：發號碼牌

    在另一個 goroutine 裡從 from 發到 to，發完就 close。

    func Tickets(from, to int) <-chan int {
	// TODO: 實作
	return closed[int]()
}

    測試：TestTickets。

    提示

    照第 3 節的 orders：make、開 goroutine、第一行 defer close(out)、迴圈送值，最後回傳 out。

  2. 入門練習 2：全部收下來

    收到 channel 被 close 為止，回傳收到的所有值。

    func Collect[T any](ch <-chan T) []T {
	// TODO: 實作
	return nil
}

    測試：TestCollect。

    提示

    一個 range 迴圈，每收到一個就 append。

  3. 進階練習 3：管線的一站

    寫一個通用的管線站：收一個值、處理、往下送。

    func Stage[T, U any](in <-chan T, f func(T) U) <-chan U {
	// TODO: 實作
	return closed[U]()
}

    測試：TestStage。

    提示

    和第 5 節的 cook 一模一樣，只是處理的部分換成 f，型別換成型別參數。

  4. 進階練習 4：兩家分店的訂單匯到總店

    把好幾個 channel 的值匯到同一個 channel。

    func FanIn[T any](chs ...<-chan T) <-chan T {
	// TODO: 實作
	return closed[T]()
}

    測試：TestFanIn。

    提示

    每個輸入一個 goroutine，把收到的值轉送到 out。什麼時候 close out？和第 6 節的 kitchen 一樣：另外一個 goroutine 等 WaitGroup，再 close。沒有輸入時，Wait 立刻返回，out 馬上被 close。

  5. 挑戰練習 5：哪家外送先接單

    同時問好幾家外送平台，用第一家成功的；全部失敗就把錯誤依序合起來。不可以留下卡住的 goroutine。

    func FirstOK(tries ...func() (string, error)) (string, error) {
	// TODO: 實作
	return "", nil
}

    測試用 synctest 的假時間決定誰先完成，並檢查洩漏。測試：TestFirstOK。

    提示

    結果 channel 的容量設成 len(tries)：FirstOK 拿到第一個成功就回傳，之後沒有人收，但每個 goroutine 都還放得下自己的結果，不會卡住（第 7 節）。送進 channel 的值要帶著索引，錯誤才能放回 errs[i]，最後 errors.Join。

  6. 找錯練習 6：永遠等不到最後一份

    值都收得到，但 range 這個 channel 的人永遠等不到結束。

    func Receipts(amounts []int) <-chan string {
	out := make(chan string)
	go func() {
		for _, a := range amounts {
			out <- fmt.Sprintf("NT$%d", a)
		}
	}()
	return out
}

    測試：TestReceipts。

    提示

    常見錯誤 3。

參考解答：先自己寫完再看。測試通過、而且 -race 沒有警告的寫法都是對的。

重點回顧

  • ch <- v 送、<-ch 收；無緩衝的 channel 要雙方都到才交接，也是同步點。
  • 送之前寫的東西，收到之後一定看得到；chan struct{} 加上 close 可以用來等一件事完成。
  • make(chan T, n) 有 n 個格子，滿了送要等、空了收要等；沒有理由就用無緩衝。
  • 由送的一方 close，只 close 一次；range 收完剩下的值就結束，comma-ok 可以分辨 close。
  • 對已 close 的 channel 送、close 兩次、close nil channel 都會 panic；nil channel 的送收永遠卡住。
  • 參數和回傳值寫成 chan<- T、<-chan T，讓編譯器檢查誰送誰收。
  • 管線的每一站收一個 channel、回傳一個 channel，close 一路往下傳。
  • fan-out 讓好幾個 goroutine 搶同一個 channel；fan-in 時用 WaitGroup 等全部送完，再由另一個 goroutine close。
  • 所有 goroutine 都卡住是死結；只有一部分卡住是洩漏，用 testing/synctest 在測試裡抓出來。
