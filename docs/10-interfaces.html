1. interface 是一份方法清單

interface 型別列出一組方法簽名。任何型別只要擁有這些方法（名稱、參數、回傳值都一樣），就滿足（satisfy）這個 interface，可以放進這個型別的變數、當成這個型別的參數傳進去。不需要任何宣告，這叫隱式實作：

type Notifier interface {
	Notify(msg string)
}

type SMS struct {
	Phone string
}

func (s SMS) Notify(msg string) {
	fmt.Printf("簡訊 %s：%s\n", s.Phone, msg)
}

type Email struct {
	Addr string
}

func (e Email) Notify(msg string) {
	fmt.Printf("Email %s：%s\n", e.Addr, msg)
}

func callNumber(n Notifier, no int) {
	n.Notify(fmt.Sprintf("%d 號的餐點好了", no))
}

func implicitDemo() {
	callNumber(SMS{Phone: "0912-345-678"}, 17)
	callNumber(Email{Addr: "amei@example.com"}, 18)

	list := []Notifier{SMS{Phone: "0987-654-321"}, Email{Addr: "kuo@example.com"}}
	for _, n := range list {
		n.Notify("明天公休")
	}
}

輸出

簡訊 0912-345-678：17 號的餐點好了
Email amei@example.com：18 號的餐點好了
簡訊 0987-654-321：明天公休
Email kuo@example.com：明天公休
  • callNumber 的參數型別是 Notifier，它只能呼叫 Notify，也只需要 Notify。傳進來的是簡訊還是 Email，它不知道也不在乎。
  • []Notifier 可以裝不同型別的值，只要每一個都滿足 Notifier。
  • SMS 和 Email 的原始碼裡沒有出現 Notifier 這個字。在別的 package 寫的型別，甚至在 Notifier 被寫出來之前就存在的型別，只要方法對得上，就能拿來用。

方法差一點就不算。參數多了一個、回傳值型別不同、名稱拼錯，編譯器都會拒絕，而且會把「有的」和「要的」並排列出來：

package main

import "fmt"

type Notifier interface {
	Notify(msg string)
}

type Email struct {
	Addr string
}

func (e Email) Notify(msg string, urgent bool) {
	fmt.Println(e.Addr, msg, urgent)
}

func main() {
	var n Notifier = Email{Addr: "amei@example.com"}
	n.Notify("餐點好了")
}

編譯錯誤

./main.go:18:19: cannot use Email{…} (value of struct type Email) as Notifier value in variable declaration: Email does not implement Notifier (wrong type for method Notify)
		have Notify(string, bool)
		want Notify(string)

既然不用宣告，要怎麼確定某個型別真的滿足某個 interface？只要有地方把它當成那個 interface 用，編譯器就會檢查。如果程式裡暫時還沒有這樣的地方，可以寫一段專門給編譯器看的宣告：

var (
	_ Notifier = SMS{}
	_ Notifier = Email{}
)

把 SMS 指定給一個 Notifier 型別的變數，變數名稱是 _，表示不會用到它，也不會佔用任何執行時間。哪天有人改了 Notify 的簽名，這幾行就會編譯失敗，錯誤訊息和上面的一樣。

2. interface 值

func interfaceValue() {
	var n Notifier
	fmt.Println(n == nil)
	fmt.Printf("%T\n", n)

	n = SMS{Phone: "0912-345-678"}
	fmt.Printf("%T %v\n", n, n)

	n = Email{Addr: "amei@example.com"}
	fmt.Printf("%T %v\n", n, n)
	fmt.Println(n == nil)
}

輸出

true
<nil>
main.SMS {0912-345-678}
main.Email {amei@example.com}
false

interface 型別的變數裡面記著兩件事：現在裝的是哪個型別（dynamic type），以及那個值（dynamic value）。零值是兩格都空的 nil，%T 印出 <nil>。放進 SMS 之後，%T 印出的是裡面那個值的型別 main.SMS，不是 Notifier；同一個變數之後也可以換裝 Email。呼叫 n.Notify(…) 時，Go 依照型別那一格找到要執行的方法，這個「執行時才決定呼叫誰」的動作叫做動態分派（dynamic dispatch）。

放進指標

type Buzzer struct {
	No    int
	count int
}

func (b *Buzzer) Notify(msg string) {
	b.count++
	fmt.Printf("呼叫器 %d 號響了（第 %d 次）：%s\n", b.No, b.count, msg)
}

func pointerInInterface() {
	b := Buzzer{No: 5}
	var n Notifier = &b
	n.Notify("餐點好了")
	n.Notify("請到櫃台取餐")
	fmt.Println(b.count)
}

輸出

呼叫器 5 號響了（第 1 次）：餐點好了
呼叫器 5 號響了（第 2 次）：請到櫃台取餐
2

取餐呼叫器要記得自己響了幾次，Notify 必須修改 count，所以用指標 receiver（09 章）。放進 interface 的是 &b，透過 n 呼叫兩次，改到的就是 b 本身，最後印出 2。

那可以放 b 本身嗎？不行。09 章的 method set 規則在這裡發揮作用：Notify 掛在 *Buzzer 上，Buzzer 這個型別沒有 Notify 方法，所以只有 *Buzzer 滿足 Notifier：

package main

import "fmt"

type Notifier interface {
	Notify(msg string)
}

type Buzzer struct {
	No    int
	count int
}

func (b *Buzzer) Notify(msg string) {
	b.count++
	fmt.Println(b.No, msg)
}

func main() {
	b := Buzzer{No: 5}
	var n Notifier = b
	n.Notify("餐點好了")
}

編譯錯誤

./main.go:21:19: cannot use b (variable of struct type Buzzer) as Notifier value in variable declaration: Buzzer does not implement Notifier (method Notify has pointer receiver)

這條規則保護了你：如果允許放 b，interface 裡裝的是 b 的複本，Notify 改到的會是那個看不到的複本，count 永遠不會增加。看到 “method has pointer receiver”，就把 b 改成 &b。

深入：第一次讀可以先跳過

2.1 比較兩個 interface

func compareInterfaces() {
	var a, b Notifier = SMS{Phone: "0912"}, SMS{Phone: "0912"}
	var c Notifier = Email{Addr: "0912"}
	fmt.Println(a == b, a == c)

	defer func() {
		fmt.Println("panic:", recover())
	}()
	var x, y any = []string{"排骨"}, []string{"排骨"}
	fmt.Println(x == y)
}

輸出

true false
panic: runtime error: comparing uncomparable type []string

interface 可以用 == 比較：先比型別那一格，型別相同再比值。a 和 b 都是 SMS 而且內容一樣，所以相等；a 和 c 裡面的字串一樣，型別卻不同，所以不相等。

麻煩在於值那一格可能是不能比較的型別，例如 slice。[]string == []string 在編譯期就會被擋下（06 章），但包在 any 裡面時，編譯器不知道裡面裝什麼，只能放行，結果在執行期 panic。用 any 當 map 的 key 時也一樣，放進 slice 當 key 就會 panic。所以拿 interface 做比較或當 key 之前，要確定裡面只會裝可以比較的型別。

3. type assertion

透過 interface 只能呼叫清單上的方法。想拿回裡面那個具體的值，例如讀 SMS 的 Phone 欄位，要用 type assertion：n.(SMS)，意思是「我認為 n 裡裝的是 SMS」。

func assertDemo() {
	var n Notifier = SMS{Phone: "0912-345-678"}

	s := n.(SMS)
	fmt.Println(s.Phone)

	e, ok := n.(Email)
	fmt.Println(ok, e)
}

輸出

0912-345-678
false {}
  • n.(SMS)：裡面確實是 SMS，得到一個 SMS 型別的值，可以讀 Phone。
  • e, ok := n.(Email)：多接一個 bool。型別不符時 ok 是 false，e 是 Email 的零值 {}，不會出錯。這和 07 章 map 的 comma-ok 是同一個模式。
  • type assertion 只能用在 interface 型別的值上；對一個本來就是 SMS 的變數寫 s.(SMS) 是編譯錯誤。

只寫一個變數、型別又不符時，程式會 panic：

func assertPanic() {
	defer func() {
		fmt.Println("panic:", recover())
	}()
	var n Notifier = SMS{Phone: "0912-345-678"}
	e := n.(Email)
	fmt.Println(e.Addr)
}

輸出

panic: interface conversion: main.Notifier is main.SMS, not main.Email

這裡用 04 章的 recover 把 panic 接住印出來；沒有 recover，程式就整個結束了。除非你百分之百確定裡面的型別，否則都用帶 ok 的寫法。

問它「你還會做什麼」

type Urgent interface {
	NotifyUrgent(msg string)
}

func (s SMS) NotifyUrgent(msg string) {
	fmt.Printf("簡訊 %s：【緊急】%s\n", s.Phone, msg)
}

func alert(n Notifier, msg string) {
	if u, ok := n.(Urgent); ok {
		u.NotifyUrgent(msg)
		return
	}
	n.Notify(msg)
}

func optionalDemo() {
	alert(SMS{Phone: "0912-345-678"}, "訂單被取消了")
	alert(Email{Addr: "amei@example.com"}, "訂單被取消了")
}

輸出

簡訊 0912-345-678：【緊急】訂單被取消了
Email amei@example.com：訂單被取消了

assertion 的目標也可以是另一個 interface：n.(Urgent) 問的是「n 裡面那個值，是不是也有 NotifyUrgent 方法？」SMS 有，就發緊急簡訊；Email 沒有，就退回一般的 Notify。這讓 alert 只要求最基本的 Notifier，同時又能利用某些實作額外的能力。標準庫常用這一招，例如 io.Copy 會先檢查來源有沒有實作 io.WriterTo，有的話就讓它自己用更快的方式寫出去。

4. type switch 與 any

要依型別做好幾種不同的事時，連續寫 assertion 很囉嗦，改用 type switch：

func label(v any) string {
	switch x := v.(type) {
	case nil:
		return "什麼都沒有"
	case int, int64:
		return fmt.Sprintf("整數 %v", x)
	case string:
		return "字串 " + x
	case error:
		return "錯誤：" + x.Error()
	case Notifier:
		return fmt.Sprintf("通知方式 %T", x)
	default:
		return fmt.Sprintf("不認得的 %T", x)
	}
}

func typeSwitchDemo() {
	values := []any{nil, 42, int64(7), "排骨飯", errors.New("賣完了"), SMS{Phone: "0912"}, 3.5}
	for _, v := range values {
		fmt.Println(label(v))
	}
}

輸出

什麼都沒有
整數 42
整數 7
字串 排骨飯
錯誤：賣完了
通知方式 main.SMS
不認得的 float64
  • switch x := v.(type) 的 .(type) 只能寫在 switch 裡。每個只列一個型別的 case 裡，x 就是那個型別：case string 裡的 x 是 string，所以可以直接寫 "字串 " + x。
  • 一個 case 列了好幾個型別（case int, int64）或 default 時，x 不知道該是哪一個，就維持原本的型別 any，只能拿去印、不能拿來算。
  • case nil 接住的是空的 interface（兩格都是 nil）。
  • case 可以是 interface：case error 接住所有有 Error 方法的值，case Notifier 接住 SMS。3.5 是 float64，哪一格都不符合，走到 default。
  • 比對由上往下，第一個符合的勝出，和 03 章的 switch 一樣。一個值可能同時符合好幾個 case（例如某個型別既是 error 又有 String 方法），所以具體的型別要寫在比較寬的 interface 前面。練習 7 就是這個 bug。

any

any 是 interface{} 的別名（09 章的 alias）。它的方法清單是空的，所以每一個型別都滿足它，什麼都能放。fmt.Println(a ...any) 能印任何東西就是因為這樣，舊的程式碼裡則會看到 interface{} 這種寫法。

代價是編譯器幫不上忙了：放進 any 的值，要用 assertion 或 type switch 取出來才能使用，型別錯了要到執行期才知道。所以 any 適合真的什麼都要收的地方（印出、序列化），自己的程式優先用具體型別或小的 interface；需要「同一段程式套用到很多型別」時，用 12 泛型，型別檢查仍然在編譯期完成。

5. nil interface 陷阱

這是 Go 最有名的陷阱，而且通常出現在錯誤處理裡：

type FormError struct {
	Field string
}

func (e *FormError) Error() string {
	return e.Field + "沒有填"
}

func checkNameBuggy(name string) error {
	var err *FormError
	if name == "" {
		err = &FormError{Field: "姓名"}
	}
	return err
}

func checkName(name string) error {
	if name == "" {
		return &FormError{Field: "姓名"}
	}
	return nil
}

func nilTrapDemo() {
	err := checkNameBuggy("王小明")
	fmt.Println(err == nil)
	fmt.Printf("%T\n", err)

	fmt.Println(checkName("王小明") == nil)
	fmt.Println(checkName(""))
}

輸出

false
*main.FormError
true
姓名沒有填

checkNameBuggy 宣告了一個 *FormError 型別的變數 err，名字有填，所以 err 一直是 nil 指標。問題出在 return err：函式的回傳型別是 error（一個 interface），nil 指標被放進 interface 時，型別格填上了 *main.FormError，值格才是 nil。呼叫的人檢查 err == nil，比的是「兩格都空嗎」，答案是否定的，於是一個正常的名字被當成錯誤。

為什麼不乾脆把它當成 nil？因為裝著 nil 指標的 interface 仍然可以呼叫方法，指標 receiver 的方法也可以自己處理 receiver 是 nil 的情況。它不是「什麼都沒有」，而是「一個 *FormError，剛好是 nil」。

規則很簡單：回傳 interface（尤其是 error）的函式，沒有東西要回傳時就直接寫 return nil，不要先宣告一個具體型別的變數再把它回傳出去，像 checkName 那樣。11 錯誤處理會一直用到這條規則。練習 6 就是這個 bug。

6. 標準庫裡的 interface

標準庫的 interface 大多只有一兩個方法，你會一直遇到這幾個：

interface方法誰會用它
fmt.StringerString() stringfmt 印出值的時候（02 章）
errorError() string所有會失敗的函式（11 章）
io.ReaderRead(p []byte) (n int, err error)bufio.Scanner、io.Copy、json.Decoder…
io.WriterWrite(p []byte) (n int, err error)fmt.Fprintf、io.Copy、log…
sort.InterfaceLen、Less、Swapsort.Sort
http.HandlerServeHTTP(w, r)HTTP 伺服器（HTTP 服務那一章）

自己寫一個 io.Writer

var ErrOutOfPaper = errors.New("紙用完了")

type PaperRoll struct {
	Cap int
	buf []byte
}

func (r *PaperRoll) Write(p []byte) (int, error) {
	room := r.Cap - len(r.buf)
	if len(p) <= room {
		r.buf = append(r.buf, p...)
		return len(p), nil
	}
	r.buf = append(r.buf, p[:room]...)
	return room, ErrOutOfPaper
}

func writerDemo() {
	roll := &PaperRoll{Cap: 19}
	n, err := fmt.Fprintf(roll, "排骨飯 x%d\n", 2)
	fmt.Println(n, err)
	n, err = fmt.Fprintf(roll, "滷蛋 x%d\n", 3)
	fmt.Println(n, err)
	fmt.Printf("%q\n", roll.buf)
}

輸出

13 <nil>
6 紙用完了
"排骨飯 x2\n滷蛋"

PaperRoll 只有一個 Write 方法，就能直接交給 Fprintf，因為 Fprintf 只要求 io.Writer；換成 Fprintln、io.WriteString、io.Copy 也一樣。Fprintf 先把整段文字格式化好，再呼叫一次 Write，並把 Write 回傳的 n 和 err 原封不動地交還給你。

實作 Write 要遵守 io.Writer 的約定（寫在 io.Writer 的文件裡）：回傳的 n 是真正寫出去的 byte 數；只要 n 小於 len(p)，就一定要回傳一個錯誤，呼叫的人才知道後面沒寫到。紙捲還剩 6 個 byte，「滷蛋 x3\n」有 10 個 byte，於是只印出「滷蛋」，回傳 6 和 ErrOutOfPaper。另外，Write 不可以修改 p 的內容，也不可以在回傳之後還留著 p，所以 PaperRoll 是把資料 append 到自己的 buf。02 章介紹過 io.Reader 和 io.Writer 的用法，這裡是反過來，自己當實作的那一方。

sort.Interface

type Order struct {
	No  int
	VIP bool
}

type byPriority []Order

func (o byPriority) Len() int      { return len(o) }

func (o byPriority) Swap(i, j int) { o[i], o[j] = o[j], o[i] }

func (o byPriority) Less(i, j int) bool {
	if o[i].VIP != o[j].VIP {
		return o[i].VIP
	}
	return o[i].No < o[j].No
}

func sortDemo() {
	orders := []Order{{No: 3}, {No: 1, VIP: true}, {No: 2}, {No: 4, VIP: true}}
	sort.Sort(byPriority(orders))
	fmt.Println(orders)

	slices.SortFunc(orders, func(a, b Order) int {
		return cmp.Compare(a.No, b.No)
	})
	fmt.Println(orders)
}

輸出

[{1 true} {4 true} {2 false} {3 false}]
[{1 true} {2 false} {3 false} {4 true}]

sort.Sort 不知道你要排什麼，它只透過三個方法操作：有幾個（Len）、第 i 個要不要排在第 j 個前面（Less）、交換兩個（Swap）。byPriority(orders) 是型別轉換（09 章），讓同一個 slice 帶上這三個方法，不會複製資料。

這是 interface 的經典用法，你會在很多程式裡看到。不過 Go 1.21 起有了 slices.SortFunc，只要傳一個比較函式，不必另外定義型別和三個方法，新程式通常用它（06 章的 slices 套件）。

7. 設計 interface

小，而且可以組合

type Loader interface {
	Load(key string) (string, bool)
}

type Saver interface {
	Save(key, value string)
}

type Store interface {
	Loader
	Saver
}

type memStore struct {
	data map[string]string
}

func (m *memStore) Load(key string) (string, bool) {
	v, ok := m.data[key]
	return v, ok
}

func (m *memStore) Save(key, value string) {
	m.data[key] = value
}

func lastOrder(l Loader, member string) string {
	if v, ok := l.Load(member); ok {
		return v
	}
	return "第一次來"
}

func embedInterfaceDemo() {
	s := &memStore{data: map[string]string{}}
	var st Store = s
	st.Save("小明", "排骨飯")
	fmt.Println(lastOrder(st, "小明"))
	fmt.Println(lastOrder(s, "阿美"))
}

輸出

排骨飯
第一次來
  • interface 可以嵌入其他 interface：Store 的方法清單就是 Loader 加上 Saver。標準庫的 io.ReadWriter 也是這樣由 Reader 和 Writer 組成的。
  • lastOrder 只需要讀，所以參數只要求 Loader，而不是整個 Store。要求得越少，能傳進來的東西就越多，測試時要做的假物件也越簡單。
  • 方法越多的 interface，能滿足它的型別就越少，用途也越窄。標準庫最常用的 interface 幾乎都只有一個方法，這不是巧合。

在使用端定義，測試時換成假的

func remindAll(n Notifier, waiting []int) {
	for _, no := range waiting {
		n.Notify(fmt.Sprintf("%d 號請取餐", no))
	}
}

func remindDemo() {
	remindAll(SMS{Phone: "0912-345-678"}, []int{17, 21})
}

輸出

簡訊 0912-345-678：17 號請取餐
簡訊 0912-345-678：21 號請取餐

remindAll 只依賴 Notifier。正式執行時傳 SMS，真的會發出簡訊；測試時當然不想真的發簡訊，就在測試檔裡寫一個假的 Notifier，只把收到的訊息記下來：

type recorder struct {
	msgs []string
}

func (r *recorder) Notify(msg string) {
	r.msgs = append(r.msgs, msg)
}

func TestRemindAll(t *testing.T) {
	var r recorder
	remindAll(&r, []int{17, 21})
	want := []string{"17 號請取餐", "21 號請取餐"}
	if !slices.Equal(r.msgs, want) {
		t.Errorf("收到 %q, want %q", r.msgs, want)
	}
}

這是 Go 測試最常用的手法：依賴 interface，測試時換成假的實作。不需要任何 mock 框架，一個 struct 加一個方法就夠了（完整的測試技巧在測試那一章）。

注意 interface 由誰定義。在 Java，通常是提供功能的一方先寫好 interface，實作類別再宣告 implements。Go 是隱式實作，提供功能的一方不需要知道 interface 的存在，所以慣例反過來：使用的一方依照自己需要的方法定義 interface，提供的一方回傳具體的型別就好。常聽到的說法是「接受 interface，回傳 struct」。

也因此，不要替每一個 struct 都先配一個 interface。等到真的有第二種實作，或者測試需要換成假的時候，再在使用的地方定義一個剛好夠用的 interface，這時候它的方法清單才會是對的。

常見錯誤

1. 回傳裝著 nil 指標的 error

錯誤寫法：沒有錯誤時，呼叫的人看到的 err 也不是 nil

func checkNameBuggy(name string) error {
	var err *FormError
	if name == "" {
		err = &FormError{Field: "姓名"}
	}
	return err
}

正確寫法

func checkName(name string) error {
	if name == "" {
		return &FormError{Field: "姓名"}
	}
	return nil
}

沒有錯誤時一律寫 return nil（第 5 節）。

2. 不帶 ok 的 type assertion

n.(Email) 型別不符就 panic（第 3 節）。除非前面的程式已經保證了型別，否則寫成 e, ok := n.(Email)，或用 type switch。

3. 指向 interface 的指標

package main

import "fmt"

type Notifier interface {
	Notify(msg string)
}

type SMS struct {
	Phone string
}

func (s SMS) Notify(msg string) {
	fmt.Println(s.Phone, msg)
}

func send(n *Notifier, msg string) {
	n.Notify(msg)
}

func main() {
	var n Notifier = SMS{Phone: "0912-345-678"}
	send(&n, "餐點好了")
}

編譯錯誤

./main.go:18:4: n.Notify undefined (type *Notifier is pointer to interface, not interface)

習慣「大的東西傳指標」的人常會寫出 *Notifier。interface 值本身只有兩格，複製它很便宜；需要共用狀態時，應該把具體型別的指標放進 interface（像第 2 節的 &b），而不是取 interface 的地址。參數寫 n Notifier 就對了。

4. 方法是指標 receiver，卻把值放進 interface

編譯錯誤 “method Notify has pointer receiver”（第 2 節）。改成放指標 &b；如果這個型別的方法其實都不需要修改 receiver，也可以考慮全部改成值 receiver。

5. type switch 裡，寬的 interface 寫在前面

case fmt.Stringer 寫在 case Price 前面，有 String 方法的 Price 就永遠走不到自己的 case，而且編譯器不會警告（第 4 節、練習 7）。具體的型別寫在前面，interface 寫在後面。

6. 比較裝著 slice 或 map 的 interface

編譯會過，執行時 panic：comparing uncomparable type []string（2.1 節）。把 any 當 map 的 key 時也一樣。

7. 先寫一個大 interface，再寫唯一的實作

替每個 struct 先配一個把所有方法都列出來的 interface，只多了一層要維護的東西，卻沒有帶來彈性。等有第二種實作或測試需要時，再在使用端定義只包含需要的方法的小 interface（第 7 節）。

重點回顧

  • interface 是一份方法清單；有這些方法的型別就自動滿足它，不必宣告。
  • var _ I = T{} 讓編譯器檢查 T 是否滿足 I。
  • interface 值有兩格：實際的型別和實際的值；兩格都空才是 nil。
  • 方法是指標 receiver 時，只有指標滿足 interface：放 &b，不是 b。
  • type assertion v.(T) 取出具體的值；不確定就用 t, ok := v.(T)，否則會 panic。
  • assertion 的目標也可以是 interface，用來檢查額外的能力。
  • type switch 由上往下比對，第一個符合的勝出；具體型別寫在 interface 前面。
  • any 什麼都能裝，但型別檢查就延到了執行期；能用具體型別、小 interface 或泛型就不要用 any。
  • 回傳 error 的函式，沒有錯誤時直接 return nil。
  • interface 要小、可以組合、由使用的一方定義；測試時換成手寫的假實作。
