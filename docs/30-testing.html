1. go test 怎麼運作

這一章測試的是 parking 套件：一個停車場的計費、車牌整理、柵欄機和日報表。先看計費規則，後面每一節都在測它：

// Package parking 是第 30 章用來練習寫測試的停車場：計費、車牌、柵欄機和日報表。
package parking

import (
	"errors"
	"time"
)

// 計費規則。
const (
	Grace     = 10 * time.Minute // 整段停車不到 10 分鐘免費
	Unit      = 30 * time.Minute // 每 30 分鐘一個單位，不足一個單位也算一個
	UnitPrice = 20               // 每個單位 20 元
	DailyCap  = 240              // 每個日曆日最多收 240 元
)

// ErrOutBeforeIn 表示出場時間比進場時間早。
var ErrOutBeforeIn = errors.New("出場時間比進場時間早")

// Fee 計算從 in 停到 out 的停車費。
// 整段停車不到 Grace 免費；否則在 in 所在時區的每個午夜切開，
// 每一天各自以 Unit 為單位進位計費，每天最多收 DailyCap。
func Fee(in, out time.Time) (int, error) {
	if out.Before(in) {
		return 0, ErrOutBeforeIn
	}
	if out.Sub(in) < Grace {
		return 0, nil
	}
	total := 0
	for start := in; start.Before(out); {
		end := nextMidnight(start)
		if end.After(out) {
			end = out
		}
		total += dayFee(end.Sub(start))
		start = end
	}
	return total, nil
}

// nextMidnight 回傳 t 之後的第一個午夜。
func nextMidnight(t time.Time) time.Time {
	y, m, d := t.Date()
	return time.Date(y, m, d+1, 0, 0, 0, 0, t.Location())
}

// dayFee 是同一天裡停了 d 的費用。
func dayFee(d time.Duration) int {
	units := int((d + Unit - 1) / Unit)
	return min(units*UnitPrice, DailyCap)
}

  • t.Errorf 記下失敗、繼續執行，所以兩個錯的案例都看得到。大部分的檢查用它。
  • t.Fatalf 記下失敗、立刻結束這個測試函式。後面的檢查都依賴前面的結果（檔案讀不到、物件建不起來）時才用它。它只能在測試本身的 goroutine 呼叫，在自己開的 goroutine 裡呼叫是錯的，go vet 會抓出來。
  • 失敗訊息要讓人不看程式碼就知道哪裡錯：寫出呼叫、實際得到的值、期望的值，例如 MemberPrice(95) = 81，want 86。這是 Go 標準庫的慣例：got 在前，want 在後。
  • 沒有失敗也沒有 panic，測試就算通過。t.Log 的訊息只有在失敗或加上 -v 時才會印出來。

2. table-driven 與子測試

同一個函式要用很多組輸入測，就把案例排成一張表，用一個迴圈跑完。每一列用 t.Run 包成子測試：

var taipei = time.FixedZone("UTC+8", 8*60*60)

func at(day, hour, min int) time.Time {
	return time.Date(2026, 11, day, hour, min, 0, 0, taipei)
}

func TestFee(t *testing.T) {
	tests := []struct {
		name    string
		in, out time.Time
		want    int
	}{
		{"剛進場就出來", at(20, 9, 0), at(20, 9, 0), 0},
		{"9 分 59 秒免費", at(20, 9, 0), at(20, 9, 0).Add(Grace - time.Second), 0},
		{"剛好 10 分鐘", at(20, 9, 0), at(20, 9, 10), 20},
		{"剛好 30 分鐘", at(20, 9, 0), at(20, 9, 30), 20},
		{"31 分鐘進位", at(20, 9, 0), at(20, 9, 31), 40},
		{"整個白天到上限", at(20, 8, 0), at(20, 20, 0), DailyCap},
		{"跨夜分兩天算", at(20, 23, 0), at(21, 1, 0), 40 + 40},
		{"跨夜各自進位", at(20, 23, 50), at(21, 0, 20), 20 + 20},
		{"出場在午夜整", at(20, 23, 0), at(21, 0, 0), 40},
		{"停三天", at(20, 12, 0), at(22, 12, 0), 3 * DailyCap},
	}
	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			got, err := Fee(tt.in, tt.out)
			if err != nil || got != tt.want {
				t.Errorf("Fee(%s, %s) = %d, %v；want %d",
					tt.in.Format("01-02 15:04"), tt.out.Format("01-02 15:04"), got, err, tt.want)
			}
		})
	}
}

表格也可以是 map，名稱當 key。map 的走訪順序每次不同，順便確認案例之間沒有互相依賴。子測試裡呼叫 t.Parallel()，這些子測試就會同時執行：

func TestNormalizePlate(t *testing.T) {
	tests := map[string]struct {
		in, want string
		err      error
	}{
		"已經是標準寫法": {"ABC-1234", "ABC-1234", nil},
		"小寫加空白":   {" abc 1234 ", "ABC-1234", nil},
		"兩個字母":    {"ab1234", "AB-1234", nil},
		"數字在前":    {"1234-ab", "1234-AB", nil},
		"空字串":     {"", "", ErrBadPlate},
		"數字太少":    {"ABC-123", "", ErrBadPlate},
		"字母太多":    {"ABCD-1234", "", ErrBadPlate},
		"全形字母":    {"ＡＢＣ-1234", "", ErrBadPlate},
	}
	for name, tt := range tests {
		t.Run(name, func(t *testing.T) {
			t.Parallel()
			got, err := NormalizePlate(tt.in)
			if got != tt.want || !errors.Is(err, tt.err) {
				t.Errorf("NormalizePlate(%q) = %q, %v；want %q, %v", tt.in, got, err, tt.want, tt.err)
			}
		})
	}
}
  • Go 1.22 起，for 迴圈的變數每一圈都是新的，閉包裡直接用 tt 就好，不必再寫 tt := tt（03 章）。
  • 案例的名稱寫「這個案例在測什麼」，不要寫 case1、case2。失敗時只看名稱就知道是哪一條規則壞了。
  • 表格裡的期望值要自己算，不要呼叫被測的函式來產生，否則永遠會通過。

深入：第一次讀可以先跳過

平行的子測試什麼時候執行

呼叫 t.Parallel 的子測試會先暫停，等外層的測試函式執行完畢，才和其他平行的子測試一起跑。所以外層函式裡的 defer 會在子測試開始之前就執行：用 defer 關掉的資料庫，子測試拿到的已經是關掉的。要在所有子測試結束後才清理，用 t.Cleanup：外層測試會等全部子測試都結束，才執行它的 Cleanup。

t.Setenv 和 t.Chdir 會改到整個程式共用的環境變數和目前目錄，所以不能用在平行的測試裡，呼叫了會 panic。

3. 測試替身

柵欄機要收錢，收錢要呼叫外部的金流公司。測試不能真的刷卡，所以 Gate 不直接呼叫金流，而是依賴一個小 interface；現在幾點也不直接呼叫 time.Now，而是用傳進來的函式：

type Payments interface {
	Charge(ctx context.Context, plate string, amount int) error
}

type Gate struct {
	now func() time.Time
	pay Payments

	mu     sync.Mutex
	inside map[string]time.Time
	done   []Record
}

func NewGate(now func() time.Time, pay Payments) *Gate {
	return &Gate{now: now, pay: pay, inside: make(map[string]time.Time)}
}

func (g *Gate) Exit(ctx context.Context, plate string) (Record, error) {
	p, err := NormalizePlate(plate)
	if err != nil {
		return Record{}, err
	}
	g.mu.Lock()
	in, ok := g.inside[p]
	delete(g.inside, p) // 先拿出來：同一台車同時出場兩次，也只會收一次錢
	g.mu.Unlock()
	if !ok {
		return Record{}, fmt.Errorf("%s：%w", p, ErrNotInside)
	}

	rec := Record{Plate: p, In: in, Out: g.now()}
	rec.Fee, err = Fee(rec.In, rec.Out)
	if err == nil && rec.Fee > 0 {
		ctx, cancel := context.WithTimeout(ctx, ChargeTimeout)
		err = g.pay.Charge(ctx, p, rec.Fee)
		cancel()
	}

	g.mu.Lock()
	defer g.mu.Unlock()
	if err != nil {
		g.inside[p] = in // 放回場內
		return Record{}, fmt.Errorf("%s 出場失敗：%w", p, err)
	}
	g.done = append(g.done, rec)
	return rec, nil
}

Payments 定義在使用它的 parking 裡，只有 Gate 需要的那一個方法（10 章：interface 由使用的一方定義）。測試裡的假金流和假時鐘都只有幾行：

type fakePayments struct {
	mu      sync.Mutex
	charges []string
	err     error
}

func (f *fakePayments) Charge(ctx context.Context, plate string, amount int) error {
	f.mu.Lock()
	defer f.mu.Unlock()
	if f.err != nil {
		return f.err
	}
	f.charges = append(f.charges, fmt.Sprintf("%s %d", plate, amount))
	return nil
}

func (c *fakeClock) Now() time.Time          { return c.now }

func (c *fakeClock) Advance(d time.Duration) { c.now = c.now.Add(d) }

func TestGatePaymentFails(t *testing.T) {
	g, clock, pay := newTestGate(t)
	pay.err = errors.New("刷卡機沒有回應")
	mustEnter(t, g, "ABC-1234")
	clock.Advance(time.Hour)

	if _, err := g.Exit(t.Context(), "ABC-1234"); !errors.Is(err, pay.err) {
		t.Fatalf("err = %v，want %v", err, pay.err)
	}
	pay.err = nil // 刷卡機好了，車還在場內，可以再試一次
	if rec, err := g.Exit(t.Context(), "ABC-1234"); err != nil || rec.Fee != 40 {
		t.Errorf("再試一次 = %+v, %v，want 40 元", rec, err)
	}
}

這些替身各有名字，知道名字就知道該用哪一種：

  • stub：回傳固定的答案。fakePayments 的 err 欄位就是一個 stub：設定了就每一筆都失敗。
  • fake：真的能動的簡化版，例如用 map 取代資料庫、用一個欄位取代時鐘。
  • spy：記下自己被怎麼呼叫，讓測試事後檢查。fakePayments 的 charges 就是。
  • mock：事先設定「應該被呼叫哪些方法、參數是什麼、順序如何」，不符合就失敗。通常用工具產生。

Go 的習慣是手寫 fake 和 spy，然後檢查結果（收了幾元、車還在不在場內），而不是用 mock 鎖住呼叫的過程。鎖住過程的測試，在你重構內部實作（例如把兩次呼叫合成一次）時就會壞掉，即使行為完全沒變。interface 小，手寫的 fake 就很短；需要 mock 工具才寫得出測試，常常表示 interface 太大了。

4. 測試輔助函式

每個 Gate 的測試都要建立假時鐘、假金流和柵欄機，進場失敗時也都要停止。重複的部分寫成輔助函式：

func newTestGate(t *testing.T) (*Gate, *fakeClock, *fakePayments) {
	t.Helper()
	clock := &fakeClock{now: at(20, 9, 0)}
	pay := &fakePayments{}
	g := NewGate(clock.Now, pay)
	t.Cleanup(func() {
		if t.Failed() {
			t.Logf("出場紀錄：%+v", g.Records())
		}
	})
	return g, clock, pay
}

func mustEnter(t *testing.T, g *Gate, plate string) {
	t.Helper()
	if err := g.Enter(plate); err != nil {
		t.Fatalf("Enter(%q)：%v", plate, err)
	}
}
  • t.Helper()：沒有它，mustEnter 失敗時訊息會指向 mustEnter 裡的 t.Fatalf 那一行，每個測試失敗都指到同一個地方。有了它，訊息指向呼叫 mustEnter 的那一行（練習 4 會檢查有沒有呼叫）。
  • t.Cleanup(f)：測試結束時執行 f，後註冊的先執行。newTestGate 用它在測試失敗時印出出場紀錄，所有用到它的測試都自動有這個功能。
  • t.TempDir()：建立一個只給這個測試用的暫存目錄，測試結束後自動刪除。測檔案的程式一律用它，不要寫到固定的路徑：
func TestSaveReport(t *testing.T) {
	dir := t.TempDir() // 測試結束後自動刪除
	path, err := SaveReport(dir, reportRecords)
	if err != nil {
		t.Fatal(err)
	}
	if want := filepath.Join(dir, "report-2026-11-20.txt"); path != want {
		t.Errorf("path = %q，want %q", path, want)
	}
	got, err := os.ReadFile(path)
	if err != nil {
		t.Fatal(err)
	}
	var want bytes.Buffer
	WriteReport(&want, reportRecords)
	if !bytes.Equal(got, want.Bytes()) {
		t.Errorf("存檔的內容和 WriteReport 不一樣：\n%s", got)
	}
}
  • t.Context()（Go 1.24 起）：測試用的 context，在 Cleanup 執行之前被取消。測試裡呼叫需要 ctx 的函式，用它而不是 context.Background()，測試結束時還沒停下來的工作就會收到取消。
  • t.Setenv(key, value)、t.Chdir(dir)（Go 1.24 起）：在這個測試裡改環境變數和目前目錄，結束時自動還原。不能和 t.Parallel 一起用。
  • t.Skip 搭配 testing.Short()：慢的測試在 go test -short 時略過。本章的 module_test.go 會執行 go 指令，就是這樣處理的。
  • Go 1.25 起還有 t.Output()（一個 io.Writer，寫進去的東西和 t.Log 一樣出現在測試輸出裡），Go 1.26 起有 t.ArtifactDir()（測試產生的檔案放這裡，加上 -artifacts 旗標時會保留下來，方便事後檢查）。

日報表有好幾行，每一行的對齊都重要。期望的輸出存在 testdata/report.golden：

var update = flag.Bool("update", false, "用目前的輸出覆寫 testdata 裡的 golden file")

var reportRecords = []Record{
	{"XY-5678", at(19, 22, 30), at(20, 8, 10), 300},
	{"ABC-1234", at(20, 8, 5), at(20, 9, 40), 80},
	{"1234-AB", at(20, 12, 0), at(20, 12, 8), 0},

func TestWriteReport(t *testing.T) {
	var buf bytes.Buffer
	if err := WriteReport(&buf, reportRecords); err != nil {
		t.Fatal(err)
	}
	golden := filepath.Join("testdata", "report.golden")
	if *update {
		if err := os.WriteFile(golden, buf.Bytes(), 0o644); err != nil {
			t.Fatal(err)
		}
	}
	want, err := os.ReadFile(golden)
	if err != nil {
		t.Fatalf("%v（第一次請加 -update 產生）", err)
	}
	if got := buf.String(); got != string(want) {
		t.Errorf("報表和 %s 不一樣：\n--- got\n%s--- want\n%s", golden, got, want)
	}
}

func TestFeesInReport(t *testing.T) {
	for _, r := range reportRecords {
		if fee, _ := Fee(r.In, r.Out); fee != r.Fee {
			t.Errorf("%s 的費用寫成 %d，Fee 算出來是 %d", r.Plate, r.Fee, fee)
		}
	}
}

改了報表的格式之後，用 -update 重新產生，再看 diff：

go test ./chapters/30-testing/parking -run TestWriteReport -update
git diff chapters/30-testing/parking/testdata
  • -update 是這個 package 的測試自己用 flag 定義的，所以只能用在這個 package。對 ./... 加上它，其他沒有定義這個旗標的 package 會失敗。
  • golden file 鎖住的是「目前的輸出」，不管它對不對。所以 TestFeesInReport 另外確認報表用的金額真的是 Fee 算出來的，並且第一次產生之後一定要親眼看過內容。
  • testdata 是 go 指令保留的名字：它底下的檔案不會被當成 package 編譯，./... 也會略過它。測試執行時，目前目錄就是 package 的目錄，所以用相對路徑 testdata/… 就讀得到。

6. 時間與並行的測試

注入假時鐘（第 3 節）適合「現在幾點」這種問題。程式裡有逾時、Sleep、Timer 時，假時鐘就不夠了：context.WithTimeout 用的是真正的時間。synctest 讓整個測試，連同標準庫的計時器，都用假的時間：

type slowPayments struct{}

func (slowPayments) Charge(ctx context.Context, plate string, amount int) error {
	<-ctx.Done()
	return ctx.Err()
}

func TestGateChargeTimeout(t *testing.T) {
	synctest.Test(t, func(t *testing.T) {
		g := NewGate(time.Now, slowPayments{})
		mustEnter(t, g, "ABC-1234")
		time.Sleep(time.Hour)

		start := time.Now()
		_, err := g.Exit(t.Context(), "ABC-1234")
		if !errors.Is(err, context.DeadlineExceeded) {
			t.Fatalf("err = %v，want DeadlineExceeded", err)
		}
		if waited := time.Since(start); waited != ChargeTimeout {
			t.Errorf("等了 %v，want %v", waited, ChargeTimeout)
		}
		if err := g.Enter("ABC-1234"); !errors.Is(err, ErrInside) {
			t.Errorf("收費逾時後車應該還在場內，Enter 回傳 %v", err)
		}
	})
}

慢的金流永遠不回應，Exit 等滿 ChargeTimeout 之後放棄，車留在場內。這個測試證明了三件事：真的會逾時、逾時的時間剛好是 5 秒、逾時後狀態正確，而它跑完只要幾毫秒。

並行的 bug 則交給 -race。同一台車同時按兩次出場，只能收一次錢：

func TestGateConcurrentExit(t *testing.T) {
	g, clock, pay := newTestGate(t)
	mustEnter(t, g, "ABC-1234")
	clock.Advance(time.Hour)

	var wg sync.WaitGroup
	errs := make([]error, 2)
	for i := range errs {
		wg.Go(func() {
			_, errs[i] = g.Exit(t.Context(), "ABC-1234")
		})
	}
	wg.Wait()
	if n := len(pay.charges); n != 1 {
		t.Errorf("收了 %d 次錢，want 1", n)
	}
	if !errors.Is(errs[0], ErrNotInside) && !errors.Is(errs[1], ErrNotInside) {
		t.Errorf("其中一次應該是 ErrNotInside，拿到 %v", errs)
	}
}
  • 這個測試沒有 -race 也會跑，但只有加上 go test -race，忘了加鎖這種 data race 才會被確實抓到。CI 一律用 -race 跑測試。
  • Exit 在收費之前就把車從 inside 拿出來，所以第二次 Exit 一定看到 ErrNotInside。如果改成收費成功後才刪除，兩次 Exit 都會收到錢，這個測試就會失敗。
  • 不要用 time.Sleep 等另一個 goroutine「應該已經做完了」：機器忙的時候就會失敗。用 channel、WaitGroup 等它真的做完，或在 synctest 裡用 synctest.Wait。

7. fuzz

fuzz 測試不寫「這個輸入應該得到什麼」，而是寫「任何輸入都要成立的性質」。車牌整理的性質：不能 panic；整理成功的結果，再整理一次要一模一樣：

func FuzzNormalizePlate(f *testing.F) {
	for _, s := range []string{"ABC-1234", " abc 1234", "1234ab", ""} {
		f.Add(s)
	}
	f.Fuzz(func(t *testing.T, s string) {
		p, err := NormalizePlate(s)
		if err != nil {
			return
		}
		again, err := NormalizePlate(p)
		if err != nil || again != p {
			t.Errorf("NormalizePlate(%q) = %q，再整理一次變成 %q, %v", s, p, again, err)
		}
	})
}

為了看 fuzz 怎麼找到 bug，testdata/fuzzbug 有一個寫錯的版本：使用者沒打 - 時，它在最後 4 個字之前補一個。它的一般測試全部通過：

func NormalizePlate(s string) (string, error) {
	s = strings.ToUpper(strings.ReplaceAll(s, " ", ""))
	if !strings.Contains(s, "-") {
		// 使用者沒打 -：在最後 4 碼前面補一個。
		s = s[:len(s)-4] + "-" + s[len(s)-4:]
	}
	if !plateRE.MatchString(s) {
		return "", errBadPlate
	}
	return s, nil
}

常見錯誤

1. 只測一般的情況

bug 幾乎都在邊界：剛好 10 分鐘、剛好 30 分鐘、出場在午夜整、空字串。表格裡每一條規則的兩側都放一個案例（第 2 節）。

2. 在自己開的 goroutine 裡呼叫 t.Fatal

t.Fatal 只會結束呼叫它的 goroutine，測試函式本身還在跑。把錯誤傳回測試的 goroutine 再回報，go vet 也會警告（第 1 節）。

3. 測試之間共用狀態

套件層級的變數、固定路徑的檔案、真的資料庫：單獨跑會過、一起跑就壞，或反過來。每個測試自己建立需要的東西，用 t.TempDir、t.Cleanup；用 -shuffle=on 抓出依賴順序的測試（第 1、4 節）。

4. 用 time.Sleep 等

睡太短在忙碌的 CI 上會失敗，睡太長測試變慢。時間用注入的時鐘或 synctest，等 goroutine 用 channel 或 WaitGroup（第 3、6 節）。

5. 依賴這台機器的環境

真的網路、目前時間、機器的時區、家目錄裡的檔案。換一台機器就失敗。用 FixedZone、假的時鐘和金流、testdata 裡的檔案（第 2、3、5 節）。

6. 失敗訊息只寫「錯了」

看到失敗還得打開程式碼、加 print 才知道輸入是什麼。訊息寫出呼叫、得到的值和期望的值（第 1 節）。

7. golden file 直接 -update 了事

測試會變綠，但錯誤的輸出也被鎖進去了。-update 之後一定看 git diff（第 5 節）。

8. 把每一個呼叫都 mock 起來

測試鎖住的是實作的過程，一重構就全部壞掉。用小 interface 加手寫的 fake，檢查結果而不是過程（第 3 節）。

    寫檔之前用 os.MkdirAll(filepath.Dir(path), 0o755) 建立目錄。讀檔失敗時 tb.Fatalf，內容不同時 tb.Errorf 一次，把 DiffLines 的結果用換行接起來放進訊息。

  5. 挑戰練習 5：縮小失敗的輸入

    fuzz 找到 27 個 byte 的失敗輸入後，會把它縮到 1 個字。自己做一個簡單的版本。

    func Shrink(input []int, fails func([]int) bool) []int {
	// TODO: 實作
	return nil
}

    測試：TestShrink，用四種不同的失敗條件檢查結果是不是縮到不能再縮。

    提示

    先複製一份。依序試著拿掉每一個元素（slices.Delete(slices.Clone(cur), i, i+1)），拿掉後還會失敗就保留拿掉的版本。重複整輪，直到一整輪都拿不掉任何元素為止。

  6. 找錯練習 6：清理的順序

    資料庫比檔案先關掉了，而且呼叫兩次 Run 會關兩次。

    func (c *Cleanups) Run() {
	for _, f := range c.fns {
		f()
	}
}

    測試：TestCleanupsRun。

    提示

    從最後一個往前執行（slices.Backward），並且在執行之前把 c.fns 設成 nil，第二次 Run 就沒有東西可以執行。

參考解答：先自己寫完再看。測試通過的寫法都是對的。

重點回顧

  • 測試放在同目錄的 _test.go，函式以 Test 開頭；比較用 if，t.Errorf 繼續、t.Fatalf 停止。
  • 失敗訊息寫出呼叫、得到的值和期望的值。
  • 多組輸入排成表格，用 t.Run 拆成子測試；-run 的每一段是沒有錨點的 regexp。
  • 依賴小 interface 和注入的時間，測試時換成手寫的 fake；檢查結果，不鎖住過程。
  • 重複的步驟寫成有 t.Helper 的輔助函式，清理交給 t.Cleanup、t.TempDir。
  • 長的輸出用 golden file，-update 之後一定看 diff。
  • 逾時和 Timer 用 synctest 測，並行用 -race 跑。
  • fuzz 檢查「任何輸入都成立的性質」，找到的輸入 commit 進 testdata/fuzz。
  • Example 是會被執行的文件；覆蓋率用來找漏掉的地方，不是目標；benchmark 要和改之前比。
