select

select 是同時顧好幾個窗口的店員：內用、外帶、外送哪一邊先有人，就先處理哪一邊；等太久就去做別的，老闆說打烊就收工。

本章你會學到

  • 用 select 同時等好幾個 channel 的送或收，以及好幾個同時準備好時怎麼挑。
  • 用 time.After 加上逾時，分清楚「每一次等待的逾時」和「整段工作的期限」。
  • 用 default 做不等待的收和送。
  • 用 for-select 持續處理好幾個 channel，並用 nil channel 關掉已經結束的那一邊。
  • 用一個 done channel 叫送的一方停下來，這是 context 取消的基礎。
  • select 沒有優先順序時，怎麼讓急件先處理。

1. 同時等好幾個 channel

上一章的收和送，一次只能等一個 channel。select 長得像 switch，但每個 case 都是一個 channel 的送或收，它會等到其中一個能進行，然後只執行那一個：

func readyDemo() {
	pickup := make(chan string, 1)
	delivery := make(chan string, 1)
	delivery <- "外送單 A-07"

	select {
	case o := <-pickup:
		fmt.Println("外帶", o)
	case o := <-delivery:
		fmt.Println("處理", o)
	}
}

輸出

處理 外送單 A-07
  • case 可以是收（v := <-ch、v, ok := <-ch、<-ch），也可以是送（ch <- v）。
  • 沒有任何一個能進行時，select 就等，直到有一個能進行為止。
  • 只執行被選中的那一個 case，沒有被選中的 case 什麼都不會發生，那個 channel 上的值也不會被拿走。
  • 沒有 case 的 select {} 會永遠等下去，偶爾用在「main 不要結束」的程式。

和 switch 最大的不同：好幾個 case 同時能進行時，select 不是挑最上面那個，而是隨機挑一個：

func fairDemo() {
	a := make(chan struct{})
	b := make(chan struct{})
	close(a)
	close(b)

	na, nb := 0, 0
	for range 1000 {
		select {
		case <-a:
			na++
		case <-b:
			nb++
		}
	}
	fmt.Println(na > 0, nb > 0, na+nb)
}

輸出

true true 1000

兩個已經 close 的 channel 每一次都收得到東西，跑一千次，兩邊都被選到過。規格規定的是「均勻的偽隨機」，所以不會有哪一邊永遠搶不到。這是刻意的設計，避免某一個 channel 一直很忙時，另一個永遠輪不到。反過來說，你不能靠 case 的順序決定優先順序，需要優先順序要另外寫（第 6 節）。

2. 逾時

time.After(d) 回傳一個 channel，過了 d 之後會收到一個值。把它和要等的 channel 放在同一個 select 裡，誰先到就用誰：

func ready(v string) <-chan string {
	ch := make(chan string, 1)
	ch <- v
	return ch
}

func never() <-chan string {
	return make(chan string)
}

func waitFor(ch <-chan string, limit time.Duration) string {
	select {
	case v := <-ch:
		return "拿到 " + v
	case <-time.After(limit):
		return "逾時"
	}
}

func timeoutDemo() {
	fmt.Println(waitFor(ready("排骨飯"), time.Second))
	fmt.Println(waitFor(never(), 10*time.Millisecond))
}

輸出

拿到 排骨飯
逾時

ready 的 channel 一開始就有值，select 立刻拿到；never 的 channel 永遠不會有值，10 毫秒後計時器先到，回報逾時。真實的程式裡，結果通常來自另一個 goroutine。注意那個 goroutine 送結果用的 channel 要有一格緩衝：逾時之後就沒有人會收了，無緩衝的話，它會永遠卡在送出（15 章的洩漏）。

逾時有兩種意思，寫法不一樣：

  • 每一次等待的逾時：每次等都最多等 d。像 waitFor 一樣，把 time.After(d) 直接寫在 select 裡，每次執行 select 都建立一個新的計時器。
  • 整段工作的期限：從開始算起，總共最多 d。計時器要在迴圈外面建立一次，迴圈裡的每一次 select 都等同一個計時器：
func collectUntil(ch <-chan string, limit time.Duration) []string {
	var got []string
	deadline := time.After(limit)
	for {
		select {
		case v, ok := <-ch:
			if !ok {
				return got
			}
			got = append(got, v)
		case <-deadline:
			return got
		}
	}
}

func deadlineDemo() {
	ch := make(chan string, 3)
	ch <- "排骨飯"
	ch <- "雞腿飯"
	fmt.Println(collectUntil(ch, 20*time.Millisecond))
}

輸出

[排骨飯 雞腿飯]

channel 裡的兩份收完之後，ch 沒有 close、也沒有新的值，select 只剩 deadline 能等，20 毫秒一到就回傳。如果把 time.After(limit) 寫進 select 裡，每收到一份就重新計時，只要來源一直有新的值進來，就永遠不會因為時間到而停下來（練習 7）。

和時間有關的行為，用真的時間測試又慢又不穩定。上一章用過的 testing/synctest 在泡泡裡提供假時間：time.Sleep、time.After 都不會真的等，只要泡泡裡所有的 goroutine 都在等，時間就直接跳到下一個計時器響的時刻，結果每次都一樣：

func TestCollectUntilIsOverallDeadline(t *testing.T) {
	synctest.Test(t, func(t *testing.T) {
		ch := make(chan string, 10)
		go func() {
			for _, o := range []string{"a", "b", "c", "d", "e"} {
				time.Sleep(time.Second)
				ch <- o
			}
			close(ch)
		}()
		start := time.Now()
		got := collectUntil(ch, 3500*time.Millisecond)
		if !slices.Equal(got, []string{"a", "b", "c"}) || time.Since(start) != 3500*time.Millisecond {
			t.Errorf("collectUntil = %q，花了 %v；want [a b c]，3.5s", got, time.Since(start))
		}
		for range ch {
		}
	})
}

這個測試模擬「每秒來一份、期限 3.5 秒」，實際執行不到一毫秒，而且可以精確地檢查花了 3.5 秒。最後要把剩下的收完：測試函式一結束，泡泡裡的時間就停止前進，送的 goroutine 如果還在 Sleep，就永遠醒不來，synctest 會把它當成卡住的 goroutine，整個測試 panic。

2.1 time.After、Timer 與 Go 1.23

Go 1.23 以前，用 time.After 建立、還沒響的計時器，要等到它響了才會被回收，所以在跑很多圈的迴圈裡用 time.After，會累積大量的計時器，官方文件當時建議改用 time.NewTimer，不用時呼叫 Stop。Go 1.23 起，沒有人再參考的計時器就算沒有 Stop 也會被回收，time.After 的文件改成「沒有理由在 time.After 夠用時改用 NewTimer」。這個新行為只在 go.mod 寫 go 1.23 以上時生效，舊文章裡的警告是寫給以前的版本看的。

需要重複使用同一個計時器時，用 t := time.NewTimer(d)，在 select 裡等 t.C，要重新計時就呼叫 t.Reset(d)。Go 1.23 起，Reset 之後保證不會從 t.C 收到舊的那次計時，以前必須先 Stop、再把 t.C 清空，現在不用了。每隔固定時間就要做一次事，用 time.Ticker；22 章「時間」會再細談。

3. default：不等

select 加上 default，就變成「試一下」：當下有 case 能進行就執行它，一個都沒有就立刻走 default，完全不等。收和送都能這樣用：

func tryReceive(ch <-chan int) string {
	select {
	case v := <-ch:
		return fmt.Sprint("收到 ", v)
	default:
		return "現在沒有"
	}
}

func tryReceiveDemo() {
	ch := make(chan int, 1)
	fmt.Println(tryReceive(ch))
	ch <- 17
	fmt.Println(tryReceive(ch))
}

輸出

現在沒有
收到 17

不等待的送，常用在「做不到就算了」的事情上，例如寫紀錄、發通知，不能因為它們卡住主要的流程：

func dropDemo() {
	logs := make(chan string, 2)
	dropped := 0
	for _, o := range []string{"排骨飯", "雞腿飯", "魚排飯", "滷肉飯", "控肉飯"} {
		select {
		case logs <- o:
		default:
			dropped++
		}
	}
	fmt.Println(len(logs), dropped)
}

輸出

2 3

logs 只有兩格，前兩份放得進去，後面三份遇到 channel 已滿，走 default 被丟掉，點餐流程一路都沒有停下來。丟掉是不是可以接受，要看業務需求；至少要像這裡一樣數一數丟了幾個，才看得出系統是不是忙不過來。

小心不要寫出「只有 default 和收」的 for-select 迴圈：沒有值的時候它每一圈都馬上走 default、再進下一圈，一顆 CPU 會被吃滿，什麼正事也沒做（常見錯誤 3）。要等就讓它等，不要加 default。

4. for-select 與 nil channel

把 select 放進 for 迴圈，就能持續處理好幾個 channel。難的是結束條件：兩個來源各自會 close，要兩邊都收完才結束：

func from(items ...string) <-chan string {
	out := make(chan string)
	go func() {
		defer close(out)
		for _, it := range items {
			out <- it
		}
	}()
	return out
}

func combine(dineIn, takeout <-chan string) []string {
	var all []string
	for dineIn != nil || takeout != nil {
		select {
		case o, ok := <-dineIn:
			if !ok {
				dineIn = nil
				continue
			}
			all = append(all, "內用 "+o)
		case o, ok := <-takeout:
			if !ok {
				takeout = nil
				continue
			}
			all = append(all, "外帶 "+o)
		}
	}
	return all
}

func loopDemo() {
	all := combine(from("排骨飯", "雞腿飯"), from("魚排飯"))
	slices.Sort(all)
	for _, o := range all {
		fmt.Println(o)
	}
}

輸出

內用 排骨飯
內用 雞腿飯
外帶 魚排飯

關鍵在 dineIn = nil。一個已經 close 的 channel，每次收都立刻回傳零值和 false（15 章），如果不處理，select 會一直選到它，迴圈原地空轉。把變數設成 nil 之後，nil channel 永遠收不到東西，那個 case 就再也不會被選中，select 只剩另一邊能等。兩邊都是 nil 時，for 的條件不成立，迴圈結束。

只改變數，不會影響 channel 本身：設成 nil 的是 combine 裡的區域變數，送的 goroutine 手上的 channel 沒有變。

5. 叫送的一方停下來

上一章的 find 提早 return 時，只能把剩下的值收完，送的 goroutine 才能結束。有了 select，送的一方可以在每次送出時，同時等一個「不用送了」的訊號：

func fromUntil(done <-chan struct{}, items ...string) <-chan string {
	out := make(chan string)
	go func() {
		defer close(out)
		for _, it := range items {
			select {
			case out <- it:
			case <-done:
				return
			}
		}
	}()
	return out
}

func find(items []string, want string) int {
	done := make(chan struct{})
	defer close(done)
	i := 0
	for o := range fromUntil(done, items...) {
		if o == want {
			return i
		}
		i++
	}
	return -1
}

func findDemo() {
	fmt.Println(find([]string{"排骨飯", "雞腿飯", "魚排飯", "滷肉飯"}, "雞腿飯"))
}

輸出

1
  • fromUntil 的每一次送出都放在 select 裡：有人收就送出去；done 被 close 就直接 return，defer 再 close out。
  • find 用 defer close(done)，不管是找到提早 return，還是全部看完，都會通知送的一方。不再需要把剩下的值收完，送的一方也不會白白產生用不到的值。
  • done 用 close 而不是送一個值：close 會叫醒所有在等它的 goroutine，管線有好幾站時，一個 close 就能讓每一站都停下來。

同樣用 synctest 證明沒有洩漏：

func TestFindNoLeak(t *testing.T) {
	synctest.Test(t, func(t *testing.T) {
		if got := find([]string{"排骨飯", "雞腿飯", "魚排飯"}, "排骨飯"); got != 0 {
			t.Errorf("find = %d, want 0", got)
		}
		if got := find([]string{"排骨飯"}, "紅茶"); got != -1 {
			t.Errorf("find(紅茶) = %d, want -1", got)
		}
	})
}

這個「傳一個 done channel 進去，select 等它」的模式非常常見，標準庫把它包成了 context.Context：ctx.Done() 回傳的就是這樣一個 channel，取消時被 close。下下一章「context」會用它取代自己寫的 done，還多了逾時和取消原因。

6. 優先順序

第 1 節看過，好幾個 case 同時能進行時，select 隨機挑。急件和普通單都有時，急件有一半的機率被普通單插隊。要讓急件優先，就分成兩步：

func next(urgent, normal <-chan string) string {
	select {
	case o := <-urgent:
		return o
	default:
	}
	select {
	case o := <-urgent:
		return o
	case o := <-normal:
		return o
	}
}

func priorityDemo() {
	urgent := make(chan string, 3)
	normal := make(chan string, 3)
	normal <- "普通 1"
	normal <- "普通 2"
	urgent <- "急件 1"
	urgent <- "急件 2"

	for range 4 {
		fmt.Println(next(urgent, normal))
	}
}

輸出

急件 1
急件 2
普通 1
普通 2
  • 第一個 select 只有急件和 default：有急件就立刻拿走，沒有就走 default，不等。
  • 第二個 select 才同時等兩邊。到了這裡，代表剛剛沒有急件，誰先來就處理誰。
  • 普通單比急件早放進去，但前兩次拿到的都是急件。

同樣的問題也出現在「停止訊號」上：工作 channel 一直有東西時，就算 done 已經被 close，select 每一圈仍有一半的機率選到工作，會多做幾份才停。通常這沒關係；如果停下來之後絕對不能再做任何事，就在每一圈開頭先用帶 default 的 select 檢查一次 done。這不是絕對的保證，只是把「還會多做幾份」減到最少，工作本身是否已經開始，還是要靠程式其他地方判斷。

常見錯誤

1. 以為 select 由上往下挑

好幾個 case 同時能進行時是隨機挑的（第 1 節）。需要優先順序，就用兩個 select（第 6 節）。

2. 把整段期限的 time.After 寫在 for-select 裡

每一圈都建立新的計時器，等於每收到一個值就重新計時；來源一直有值進來，就永遠不會逾時。整段的期限要在迴圈外面建立一次（第 2 節，練習 7）。

3. for-select 只有 default 和收，原地空轉

沒有值時每一圈都馬上走 default，CPU 被吃滿。拿掉 default 讓它等，或是讓 default 去做真正有意義的事。

4. 已經 close 的 channel 還留在 select 裡

它每次都收得到零值，會一直被選到。用 v, ok := <-ch 檢查，ok 是 false 就把變數設成 nil（第 4 節）。

5. 逾時之後，送結果的 goroutine 卡住

select 因為逾時離開了，送結果的 goroutine 之後要送時，已經沒有人收。結果 channel 給一格緩衝，或讓它也 select 一個 done（第 2、5 節）。

6. 在 select 裡用 break 想跳出 for 迴圈

select 裡的 break 只會跳出 select，和 switch 裡的 break 一樣，外面的 for 會繼續跑。要離開迴圈就用 return，或在 for 前面加標籤，寫 break loop。

	close(out)
	return out
}

    測試：TestDebounce。

    提示

    在 goroutine 裡用 for-select 等兩件事：in 的新值，和一個計時 channel fire。fire 一開始是 nil（沒有等著送的值，這個 case 不會被選到，第 4 節）。收到新值就記下來，fire = time.After(wait) 重新計時；fire 響了就送出記下的值，再把 fire 設回 nil。in 被 close 時，fire 不是 nil 代表還有值沒送，先送出再 return。

  7. 找錯練習 7：說好的期限呢

    來源每秒來一個值、期限 3.5 秒，結果它一直收到來源結束為止。

    func CollectFor[T any](ch <-chan T, d time.Duration) []T {
	var got []T
	for {
		select {
		case v, ok := <-ch:
			if !ok {
				return got
			}
			got = append(got, v)
		case <-time.After(d):
			return got
		}
	}
}

    測試：TestCollectFor。

    提示

    常見錯誤 2。

參考解答：先自己寫完再看。測試通過、而且 -race 沒有警告的寫法都是對的。

重點回顧

  • select 同時等好幾個 channel 的送或收，執行第一個能進行的 case；都不能就等。
  • 好幾個 case 同時能進行時隨機挑，不能靠 case 的順序決定優先順序。
  • time.After(d) 放進 select 就是逾時；整段工作的期限要在迴圈外建立一次計時器。
  • Go 1.23 起計時器沒有 Stop 也會被回收，Reset 不會收到舊的計時。
  • 加上 default 的 select 不等待：可以做「有就收」和「放不下就丟」。
  • for-select 收到 close 的 channel 時，把變數設成 nil 關掉那個 case。
  • 送的一方在 select 裡同時等 done，收的一方 close(done) 就能叫它停下來；context 就是這個模式。
  • 需要優先順序時，先用帶 default 的 select 檢查重要的那一個。
  • 和時間有關的程式，用 testing/synctest 的假時間測試。
