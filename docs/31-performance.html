效能與 profiling

中午出餐太慢，老闆的直覺是「再請一個人炸排骨」。站在旁邊拿碼表量一下才發現，大部分的時間花在找零錢。效能調校也一樣：先量，找出真正慢的地方，改了再量一次。憑感覺改的程式，常常變得難讀，卻沒有變快。

1. 先確認正確，再量測

便當店每天有上千筆訂單紀錄，每一行像「10:05,排骨飯,2,90」。我們要算每道菜的營業額。第一版用 regexp 解析每一行，第二版用 strings.Cut。改寫之前，先確認兩個版本的結果完全一樣：

type Order struct {
	Time  string
	Dish  string
	Qty   int
	Price int
}

var lineRE = regexp.MustCompile(`^(\d{2}:\d{2}),([^,]+),(\d+),(\d+)$`)

func parseRegexp(line string) (Order, error) {
	m := lineRE.FindStringSubmatch(line)
	if m == nil {
		return Order{}, fmt.Errorf("%w：%q", errBadLine, line)
	}
	qty, _ := strconv.Atoi(m[3])
	price, _ := strconv.Atoi(m[4])
	return Order{Time: m[1], Dish: m[2], Qty: qty, Price: price}, nil
}

func parseCut(line string) (Order, error) {
	t, rest, ok1 := strings.Cut(line, ",")
	dish, rest, ok2 := strings.Cut(rest, ",")
	q, p, ok3 := strings.Cut(rest, ",")
	qty, err1 := strconv.Atoi(q)
	price, err2 := strconv.Atoi(p)
	if !ok1 || !ok2 || !ok3 || err1 != nil || err2 != nil || len(t) != 5 || dish == "" {
		return Order{}, fmt.Errorf("%w：%q", errBadLine, line)
	}
	return Order{Time: t, Dish: dish, Qty: qty, Price: price}, nil
}

func revenue(log string, parse func(string) (Order, error)) (map[string]int, error) {
	totals := make(map[string]int)
	for line := range strings.Lines(log) {
		o, err := parse(strings.TrimSuffix(line, "\n"))
		if err != nil {
			return nil, err
		}
		totals[o.Dish] += o.Qty * o.Price
	}
	return totals, nil
}
func revenueDemo() {
	log := sampleLog(1000)
	slow, err1 := revenue(log, parseRegexp)
	fast, err2 := revenue(log, parseCut)
	for _, dish := range slices.Sorted(maps.Keys(fast)) {

	_, err := parseCut("10:05,排骨飯,兩個,90")
	fmt.Println(err)
}

main_test.go 的 TestParsersAgree 用好幾種正確和錯誤的行，逐一比對兩個版本的結果。有了這個測試，之後怎麼改都不怕改錯。接著用 benchmark 量，兩個版本用子 benchmark 放在一起，輸入完全相同：

func BenchmarkRevenue(b *testing.B) {
	log := sampleLog(1000) // 準備資料不算在時間裡：b.Loop 會在第一次呼叫時重設計時
	for _, bc := range []struct {
		name  string
		parse func(string) (Order, error)
	}{
		{"regexp", parseRegexp},
		{"cut", parseCut},
	} {
		b.Run(bc.name, func(b *testing.B) {
			for b.Loop() {
				revenue(log, bc.parse)
			}
		})
	}
}

1,000 行的紀錄，regexp 版要 0.24 毫秒、每次配置 2,002 次；Cut 版快了 5 倍多，只配置 2 次。這一章接下來會說明這些數字怎麼來、怎麼找出原因。

  • 改之前、改之後各跑 10 次存成檔案，用官方的 benchstat 工具（golang.org/x/perf/cmd/benchstat，要另外安裝）比較，它會算出中位數、變動範圍，以及差異是不是真的（練習 1 會自己算中位數和變動範圍）。
  • 準備資料的時間不算進去：b.Loop() 在第一次被呼叫時才開始計時，迴圈前面的 sampleLog 不會影響結果。b.Loop 也保證迴圈裡的呼叫不會被編譯器當成「結果沒用到」而整個省略。
  • benchmark 量的是你給的輸入。真實資料比較長、比較亂的話，用真實資料的樣本來量。

2. 用 pprof 找出瓶頸

benchmark 告訴你「多慢」，profile 告訴你「慢在哪裡」。go test 可以在跑 benchmark 的同時記錄 profile：

go test -run='^$' -bench='Revenue/regexp' -cpuprofile=cpu.out ./chapters/31-performance   # 時間花在哪裡
go test -run='^$' -bench='Revenue/regexp' -memprofile=mem.out ./chapters/31-performance   # 記憶體配置在哪裡
go tool pprof -top cpu.out            # 依花費排序的清單
go tool pprof -list=parseRegexp cpu.out   # 逐行標出花費
go tool pprof -http=localhost:8080 cpu.out   # 在瀏覽器裡看呼叫圖和 flame graph

  • alloc_space 是「總共配置過多少」，找出讓 GC 忙碌的地方。inuse_space（預設）是「profile 當下還活著多少」，找出記憶體為什麼一直漲。
  • regexp 很方便，但在每秒處理大量資料的熱點上，固定格式的解析用 strings 的函式就夠了（24 章）。
  • 不是 benchmark 的程式：一般的程式用 runtime/pprof 的 StartCPUProfile、WriteHeapProfile 寫出 profile；HTTP 服務 import net/http/pprof，就能從 /debug/pprof/ 隨時抓正在執行的服務的 profile（這個端點不要對外公開）。

CPU profile 的讀法完全一樣，只是單位從 MB 換成秒。它是每隔一小段時間記下「現在在執行哪個函式」取樣而來的，程式要跑得夠久（至少一兩秒）才有足夠的樣本；樣本太少時，每個函式的比例只是雜訊。記憶體 profile 則是在配置時記錄，數字比較穩定，這一節就用它示範。

3. 數配置的次數

同一行收據有好幾種組法。testing.AllocsPerRun 把一個函式跑很多次，回傳平均每次配置幾次：

func allocDemo() {
	dish, qty, price := "排骨飯", 2, 180
	buf := make([]byte, 0, 64) // 重複使用的緩衝區

	ways := []struct {
		name string
		f    func()
	}{
		{"fmt.Sprintf", func() {
			sink = fmt.Sprintf("%s x%d %d", dish, qty, price)
		}},
		{"字串相加", func() {
			sink = dish + " x" + strconv.Itoa(qty) + " " + strconv.Itoa(price)
		}},
		{"strings.Builder", func() {
			var b strings.Builder
			b.Grow(32)
			b.WriteString(dish)
			b.WriteString(" x")
			b.WriteString(strconv.Itoa(qty))
			b.WriteString(" ")
			b.WriteString(strconv.Itoa(price))
			sink = b.String()
		}},
		{"append 到舊的 buf", func() {
			b := append(buf[:0], dish...)
			b = append(b, " x"...)
			b = strconv.AppendInt(b, int64(qty), 10)
			b = append(b, ' ')
			b = strconv.AppendInt(b, int64(price), 10)
			sinkBytes = b
		}},
	}
	for _, w := range ways {
		fmt.Printf("%s：每次配置 %.0f 次\n", w.name, testing.AllocsPerRun(100, w.f))
	}
}
fmt.Sprintf：每次配置 1 次
字串相加：每次配置 2 次
strings.Builder：每次配置 2 次
append 到舊的 buf：每次配置 0 次
  • fmt.Sprintf 最方便，配置一次產生結果字串。在熱點以外的地方，用它就好。
  • 字串相加和 Builder 版各配置 2 次：結果 1 次，strconv.Itoa(180) 1 次。目前的實作裡，100 以下的數字有現成的字串，Itoa(2) 不用配置。
  • append 到重複使用的 buf 完全不配置：strconv.AppendInt 把數字直接寫進既有的 []byte。練習 2、5 用的就是這個技巧。
  • AllocsPerRun 也很適合寫成測試：「這個函式不能配置記憶體」寫成 if n := testing.AllocsPerRun(…); n != 0 { t.Errorf(…) }，以後有人不小心加了配置，測試就會抓到。

4. 逃逸分析

05 章提過逃逸分析，這裡實際看編譯器的判斷：

package main

import "fmt"

// Ticket 是一張號碼牌。
type Ticket struct {
	No   int
	Note string
}

// newTicket 回傳指標：t 在函式結束後還要被用到，只能放在 heap。
func newTicket(no int) *Ticket {
	t := Ticket{No: no}
	return &t
}

// ticketValue 回傳值：複製一份給呼叫的人，t 本身留在 stack。
func ticketValue(no int) Ticket {
	t := Ticket{No: no}
	return t
}

// announce 把 no 交給 fmt.Println。參數型別是 any，編譯器看不出它會被留多久。
func announce(no int) {
	fmt.Println("請", no, "號到櫃台")
}

// lastFive 的陣列大小固定，而且沒有離開函式，留在 stack。
func lastFive(nos []int) int {
	var recent [5]int
	copy(recent[:], nos[max(len(nos)-5, 0):])
	sum := 0
	for _, n := range recent {
		sum += n
	}
	return sum
}

// queueOf 的大小要到執行時才知道，只能放在 heap。
func queueOf(n int) []int {
	return make([]int, n)
}

// escapeDemo 呼叫上面的函式。哪些變數放在 heap，要用 go build -gcflags=-m 看。
func escapeDemo() {
	p := newTicket(7)
	v := ticketValue(8)
	announce(p.No + v.No)
	fmt.Println(lastFive([]int{1, 2, 3, 4, 5, 6}), len(queueOf(3)))
}

  • 第 25 行：fmt.Println 的參數是 any，放進 any 的值會被標成 escapes to heap。常數字串和小整數有現成的資料可以指，實際上不一定會配置，但編譯器不能把它們放在 stack 上。
  • 第 29 行：lastFive 只讀 nos，nos does not escape；陣列 recent 大小固定，留在 stack。
  • 第 41 行和第 49 行：queueOf 裡的 make([]int, n) 大小執行時才知道，escapes to heap。但 escapeDemo 呼叫 queueOf(3) 時，queueOf 被內嵌（inline）進來，大小變成常數 3，同一行 make 就 does not escape 了。內嵌讓逃逸分析看到更多資訊，所以小函式很少需要為了效能手動改寫。

不要為了避免逃逸而扭曲 API（例如所有東西都改成傳值、不敢用 interface）。先寫清楚的程式，profile 顯示某個熱點的配置太多，再用 -m 找原因。本章的 escape_test.go 會實際執行上面的指令，確認頁面上的判斷沒有過時。

5. 預先配置與重複使用

func collectNames(orders []Order) []string {
	var names []string
	for _, o := range orders {
		names = append(names, o.Dish)
	}
	return names
}

func collectNamesPrealloc(orders []Order) []string {
	names := make([]string, 0, len(orders))
	for _, o := range orders {
		names = append(names, o.Dish)
	}
	return names
}

func preallocDemo() {
	orders := make([]Order, 1000)
	a, b := collectNames(orders), collectNamesPrealloc(orders)
	fmt.Printf("沒有預先配置：len %d cap %d\n", len(a), cap(a))
	fmt.Printf("預先配置：len %d cap %d\n", len(b), cap(b))
}

  • strings.Builder.Grow(n)、bytes.Buffer.Grow(n)：知道結果大概多長時先預留（08 章）。練習 5 先算出精確的長度，整份收據只配置一次。
  • 重複使用緩衝區：buf = buf[:0] 保留容量、清空內容，再 append。迴圈裡每一圈都用同一個 buf。
  • strconv.AppendInt、AppendFloat、AppendQuote：直接寫進 []byte，不產生中間的字串。
  • 避免 []byte 和 string 來回轉換：每次轉換都會複製。bytes 和 strings 套件的函式幾乎都成對存在，資料是什麼型別就用哪一個。
  • 小心子切片留住大陣列：從 1 MB 的檔案內容切出第一行，整個 1 MB 都不會被回收（06 章）。只要留一小段時用 bytes.Clone 複製出來（練習 6）。

6. sync.Pool

var bufPool = sync.Pool{
	New: func() any { return new(bytes.Buffer) },
}

const maxPooled = 4 << 10

func receipt(orders []Order) string {
	var b bytes.Buffer
	writeReceipt(&b, orders)
	return b.String()
}

func receiptPooled(orders []Order) string {
	b := bufPool.Get().(*bytes.Buffer)
	b.Reset() // 上一個人留下的內容要清掉
	writeReceipt(b, orders)
	s := b.String() // 先複製出字串，緩衝區還回去之後就可能被別人改掉
	if b.Cap() <= maxPooled {
		bufPool.Put(b)
	}
	return s
}

  • 每次都用新的 bytes.Buffer，要隨著內容變長擴充好幾次；從 pool 借來的緩衝區已經夠大，只剩 String() 複製結果和 Itoa 那 2 次。
  • Reset：借到的緩衝區可能還留著上一個人的內容。
  • 先複製再還：b.String() 會複製一份；如果回傳的是 b.Bytes()，還回去之後別人寫進來，你手上的結果就變了。
  • 大的不要還：偶爾一張特別長的收據把緩衝區撐大到幾 MB，還回去之後會一直佔著那塊記憶體。練習 4 會實作這個規則。
  • pool 會增加程式的複雜度。只有 profile 顯示某個暫存物件的配置真的很多時才用，不要預設就用。

7. GC 與記憶體上限

GC 什麼時候開始，由 GOGC 決定。預設是 100：上一次 GC 後存活 4 MB，heap 長到 8 MB 時就再做一次。設定 GODEBUG=gctrace=1，每次 GC 都會印出一行：

GODEBUG=gctrace=1 go test -run='^$' -bench='Revenue/regexp' -benchtime=300x ./chapters/31-performance 2>&1 | grep '^gc ' | tail -2

輸出

gc 15 @0.079s 0%: 0.017+0.18+0.019 ms clock, 0.17+0/0.080/0.014+0.19 ms cpu, 3->3->0 MB, 4 MB goal, 0 MB stacks, 0 MB globals, 10 P
gc 16 @0.085s 0%: 0.026+0.11+0.035 ms clock, 0.26+0.007/0.064/0.043+0.35 ms cpu, 3->3->0 MB, 4 MB goal, 0 MB stacks, 0 MB globals, 10 P
  • gc 16 @0.085s 0%：第 16 次 GC，程式開始後 0.085 秒，GC 到目前為止用掉的 CPU 比例。
  • 3->3->0 MB, 4 MB goal：GC 開始時 heap 3 MB，結束時 3 MB，其中還活著的只有不到 1 MB，下一次的目標是 4 MB（4 MB 是最小的目標）。
  • regexp 版每一行都配置，heap 很快就到目標，0.085 秒就做了 16 次 GC。把 GOGC 調大，GC 次數就變少：
GODEBUG=gctrace=1 go test -run='^$' -bench='Revenue/regexp' -benchtime=300x ./chapters/31-performance 2>&1 | grep -c '^gc '
GOGC=400 GODEBUG=gctrace=1 go test -run='^$' -bench='Revenue/regexp' -benchtime=300x ./chapters/31-performance 2>&1 | grep -c '^gc '

輸出

40
9
  • GOGC：越大，GC 越少、記憶體用得越多。GOGC=off 完全關掉，只適合很短的批次程式。
  • GOMEMLIMIT（Go 1.19 起，也可以用 runtime/debug.SetMemoryLimit）：給整個程式一個記憶體上限，快到上限時 GC 會更積極。在容器裡跑時，設成容器限制的九成左右，可以避免被系統強制終止，又不必把 GOGC 調得很小。
  • Go 1.26 起預設使用新的 GC 實作（Green Tea），對大量小物件的程式更有效率。這是執行環境的改進，程式碼不需要改。
  • 調 GC 參數是最後的手段。減少配置（第 3、5、6 節）同時減少配置本身和 GC 的工作，效果通常比調參數好得多。

深入：第一次讀可以先跳過

PGO 與 goroutine 洩漏的 profile

PGO（profile-guided optimization，Go 1.21 起）：把正式環境收集到的 CPU profile 存成 main package 目錄下的 default.pgo，go build 就會自動用它，針對真正的熱點做更積極的內嵌等最佳化。官方說明一般能有幾個百分點的改善，而且完全不用改程式碼。profile 要來自有代表性的正式環境負載，benchmark 的 profile 不一定代表真實情況。

goroutine 洩漏的 profile（Go 1.27 起正式提供）：runtime/pprof 新增 goroutineleak 這種 profile，net/http/pprof 也有對應的 /debug/pprof/goroutineleak。它利用 GC 找出「卡在一個沒有任何其他 goroutine 能碰到的 channel 或鎖上」的 goroutine，這種 goroutine 永遠不會醒來。測試裡抓洩漏，仍然建議用 15 章的 synctest。

常見錯誤

1. 沒量就改

憑直覺改的地方，常常不是真正慢的地方。先 benchmark、再 profile，只改 profile 指出來的熱點（第 1、2 節）。

2. 改快了，結果也改錯了

最佳化之前先寫測試鎖住結果，像 TestParsersAgree 那樣逐一比對新舊版本（第 1 節）。

3. 只跑一次就下結論

一次的數字可能只是雜訊。用 -count 跑好幾次，差距比變動範圍大才算數（第 1 節）。

4. 最佳化不重要的地方

把只佔 1% 的函式加快一倍，整體只快 0.5%。從 cum 最大的地方往下找（第 2 節）。

5. 熱點上用 regexp、fmt 解析固定格式

方便但每次都配置。固定格式用 strings.Cut、strconv（第 2、3 節）。

6. sync.Pool 用錯

沒有 Reset、還回去之後還在用、把特別大的緩衝區還回去，或把它當成快取（第 6 節）。

7. 子切片留住整個大陣列

只想留一小段，卻讓整個檔案都不能回收。需要長期保留的一小段，複製出來（第 5 節）。

8. 先調 GOGC

調參數治標，減少配置才治本。真的要調，GOMEMLIMIT 通常比把 GOGC 調小更合適（第 7 節）。

從 Java 來的你

主題JavaGo
microbenchmarkJMH，另外的專案和註解測試檔裡的 Benchmark 函式
profilerJFR、async-profiler、VisualVMpprof，go test 和 net/http/pprof 內建

Java 的效能調校很大一部分是在挑 GC 和調 JVM 參數；Go 把這些旋鈕減到只剩兩個，把重點放在程式本身：少配置、用值型別、讓資料連續排在記憶體裡。另一個差別是 Go 沒有 JIT，benchmark 不用暖機，跑出來的數字比較直接反映程式碼本身。

  1. 入門練習 1：整理 benchmark 的結果

    同一個 benchmark 跑好幾次，用中位數和變動範圍判斷數字可不可靠。

    func Summarize(samples []float64) (median, spread float64) {
	// TODO: 實作
	return 0, 0
}

    測試：TestSummarize。

    提示

    slices.Sorted(slices.Values(samples)) 會回傳排序好的新 slice，不會動到原本的。變動範圍用 math.Abs(x-median)/median*100 取最大值。

  2. 入門練習 2：不配置的一行收據

    第 3 節「append 到舊的 buf」的寫法。

    func AppendLine(dst []byte, dish string, qty, price int) []byte {
	// TODO: 實作
	return dst
}

    測試：TestAppendLine，用 AllocsPerRun 檢查是 0 次。

    提示

    append(dst, dish...) 可以直接把字串接到 []byte 後面；數字用 strconv.AppendInt(dst, int64(n), 10)。

  3. 進階練習 3：不配置的解析

    比本章的 parseCut 更嚴格，而且解析正確的一行時完全不配置。

    func ParseOrder(line string) (Order, error) {
	// TODO: 實作
	return Order{}, nil
}

    測試：TestParseOrder。

    提示

    strings.Cut 切三次。錯誤時直接回傳 ErrBadLine，不要用 fmt.Errorf 包裝（那會配置，雖然只在錯誤時）。時間逐一檢查 5 個 byte。

  4. 進階練習 4：有上限的緩衝區 pool

    第 6 節的三條規則：借到的是空的、太大的不要還、可以同時使用。

    func (p *BufferPool) Get() *bytes.Buffer {
	// TODO: 實作
	return nil
}

func (p *BufferPool) Put(b *bytes.Buffer) {
	// TODO: 實作
}

    測試：TestBufferPool，用 -race 跑。

    提示

    b, _ := p.pool.Get().(*bytes.Buffer)，pool 是空的時候 b 是 nil，這時 new 一個。sync.Pool 本身可以同時使用，不用另外加鎖。

  5. 挑戰練習 5：只配置一次的收據

    先算出總長度，一次配置好，再寫進去。

    func Receipt(items []Item) string {
	// TODO: 實作
	return ""
}

    測試：TestReceipt，用 AllocsPerRun 檢查最多 1 次。

    提示

    宣告一個 var scratch [64]byte，用 AppendLine(scratch[:0], …) 量出每一行的長度（它不會逃逸，留在 stack），加總之後 b.Grow(size)，再把每一行 Write 進 strings.Builder。String() 不會再複製。

  6. 找錯練習 6：留住整個檔案的第一行

    只想留下第一行，結果整個 1 MB 都留在記憶體裡，而且 data 被重複使用後，第一行也跟著變了。

    func FirstLine(data []byte) []byte {
	if before, _, ok := bytes.Cut(data, []byte{'\n'}); ok {
		return before
	}
	return data
}

    測試：TestFirstLine。

    提示

    回傳的是 data 的子切片，和 data 共用同一塊記憶體。用 bytes.Clone 複製出來。

參考解答：先自己寫完再看。測試通過的寫法都是對的。

重點回顧

  • 先用測試鎖住結果，再量；只改 profile 指出的熱點，改完再量一次。
  • benchmark 用 b.Loop、-benchmem，跑好幾次看變動範圍；比較用 benchstat。
  • pprof：從 cum 大的地方往下找到 flat 大的那一層；alloc_space 看總配置量。
  • 少配置是 Go 最有效的最佳化：AllocsPerRun 數次數，也能寫成測試。
  • 逃逸分析由編譯器決定，-gcflags=-m 看得到；不要為了它扭曲 API。
  • 預先配置容量、重複使用緩衝區、strconv.Append 系列、需要時複製子切片。
  • sync.Pool 給頻繁建立的暫存物件：Reset、先複製再還、大的不還。
  • GOGC 決定 GC 的頻率，GOMEMLIMIT 給記憶體上限；減少配置比調參數有效。
