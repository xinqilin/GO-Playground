1. Handler 與 ResponseWriter

net/http 的核心是 http.Handler，一個只有一個方法 ServeHTTP(ResponseWriter, *Request) 的 interface。任何有這個方法的型別都是 Handler。大部分時候寫的是一個函式，用 http.HandlerFunc 轉型就變成 Handler（它是一個函式型別，ServeHTTP 就是呼叫自己）。需要帶著狀態的時候，寫一個型別自己實作 ServeHTTP：

func hello(w http.ResponseWriter, r *http.Request) {
	name := r.URL.Query().Get("name")
	if name == "" {
		name = "客人"
	}
	fmt.Fprintf(w, "歡迎光臨，%s\n", name)
}

type counter struct {
	n atomic.Int64
}

func (c *counter) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	fmt.Fprintf(w, "您是今天第 %d 位客人\n", c.n.Add(1))
}

func handlerDemo() {
	send(http.HandlerFunc(hello), "GET", "/hello?name=Amei", "", "Content-Type")
	send(http.HandlerFunc(hello), "GET", "/hello", "")

	c := &counter{}
	send(c, "GET", "/", "")
	send(c, "GET", "/", "")
}

歡迎光臨，Amei
GET /hello → 200
歡迎光臨，客人
GET / → 200
您是今天第 1 位客人
GET / → 200
您是今天第 2 位客人
  • 本章的示範都用 send 這個小工具送請求：它用 httptest 直接呼叫 handler，不用開 port（第 8 節）。
  • 每個請求在自己的 goroutine 裡執行，同一個 handler 會同時被很多 goroutine 呼叫。counter 用 atomic 計數；用一般的 int 就是 data race（17 章）。
  • r.URL.Query().Get("name") 讀查詢字串，沒有這個參數時是空字串。

ResponseWriter 有順序：標頭、狀態碼、內容。順序錯了不會有錯誤，只是設定沒有效果：

func lateHeader(w http.ResponseWriter, r *http.Request) {
	io.WriteString(w, `{"ok":true}`)
	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(http.StatusCreated)
}

func rightOrder(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(http.StatusCreated)
	io.WriteString(w, `{"ok":true}`)
}
POST /late → 200，Content-Type: text/plain; charset=utf-8
{"ok":true}
POST /right → 201，Content-Type: application/json
{"ok":true}

lateHeader 想回 201 和 JSON，客戶端拿到的卻是 200 和 text/plain：第一次 Write 時標頭已經送出，net/http 從內容猜了 Content-Type。真的 server 還會在 log 裡留下一行 http: superfluous response.WriteHeader call。

2. ServeMux 的路由

Go 1.22 起，http.ServeMux 的 pattern 可以寫 HTTP 方法和路徑變數："GET /orders/{id}"。路徑變數用 r.PathValue("id") 取出，Go 1.23 起 r.Pattern 是對到的那個 pattern。用一個印出結果的 handler 看各種請求會對到哪裡：

func whichRoute(w http.ResponseWriter, r *http.Request) {
	fmt.Fprintf(w, "pattern=%q id=%q path=%q", r.Pattern, r.PathValue("id"), r.PathValue("path"))
}

func routeDemo() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /orders/{id}", whichRoute)
	mux.HandleFunc("GET /orders/latest", whichRoute)
	mux.HandleFunc("POST /orders", whichRoute)
	mux.HandleFunc("GET /menu/", whichRoute)
	mux.HandleFunc("GET /files/{path...}", whichRoute)
	mux.HandleFunc("GET /{$}", whichRoute)

	for _, req := range []struct{ method, target string }{
		{"GET", "/orders/42"},
		{"GET", "/orders/latest"},
		{"HEAD", "/orders/42"},
		{"DELETE", "/orders/42"},
		{"GET", "/menu/today"},
		{"GET", "/menu"},
		{"GET", "/files/2026/11/menu.pdf"},
		{"GET", "/"},
		{"GET", "/about"},
	} {
		send(mux, req.method, req.target, "", "Allow", "Location")
	}
}

  • 方法：GET 的 pattern 也接受 HEAD。路徑對了但方法不對，回 405，Allow 標頭列出可以用的方法。沒寫方法的 pattern 接受所有方法。
  • {id} 對一段路徑（兩個 / 之間）。{path...} 只能放在最後，對剩下的全部，包含 /。
  • 結尾的 /：/menu/ 對 /menu/ 底下的所有路徑；請求 /menu（沒有斜線）會被轉址到 /menu/。
  • {$} 表示「到這裡結束」。"GET /" 會對到所有的路徑（是最後的備案），只要首頁的話寫 "GET /{$}"。
  • 兩個 pattern 一樣具體、又會對到同一個請求（例如 /orders/{id} 和 /orders/{num}），HandleFunc 註冊時就 panic，程式一啟動就會發現。

路徑變數拿到的永遠是字串，數字要自己轉、自己檢查（第 4 節）。內建的 ServeMux 夠大部分的 API 用；需要更多功能（依標頭路由、正規表示式）時才考慮第三方的路由套件。

3. 讀取與驗證請求

請求的資料有四個來源：路徑變數 r.PathValue、查詢字串 r.URL.Query()、標頭 r.Header.Get，以及內容 r.Body（一個 io.Reader）。內容最需要小心：大小沒有上限、格式可能是任何東西。把檢查集中在一個函式裡：

const maxBody = 1 << 20

func decodeJSON(w http.ResponseWriter, r *http.Request, v any) error {
	if mt, _, _ := mime.ParseMediaType(r.Header.Get("Content-Type")); mt != "application/json" {
		return &httpError{http.StatusUnsupportedMediaType, "Content-Type 要是 application/json"}
	}
	r.Body = http.MaxBytesReader(w, r.Body, maxBody)
	err := json.UnmarshalRead(r.Body, v, json.RejectUnknownMembers(true))
	if err == nil {
		return nil
	}
	if _, ok := errors.AsType[*http.MaxBytesError](err); ok {
		return &httpError{http.StatusRequestEntityTooLarge, "內容太大"}
	}
	if errors.Is(err, json.ErrUnknownName) {
		se, _ := errors.AsType[*json.SemanticError](err)
		return &httpError{http.StatusBadRequest, "不認得的欄位 " + string(se.JSONPointer)}
	}
	if se, ok := errors.AsType[*json.SemanticError](err); ok && se.JSONPointer != "" {
		return &httpError{http.StatusBadRequest, "欄位 " + string(se.JSONPointer) + " 的型別不對"}
	}
	if _, ok := errors.AsType[*jsontext.SyntacticError](err); ok || errors.Is(err, io.ErrUnexpectedEOF) {
		return &httpError{http.StatusBadRequest, "JSON 格式不對"}
	}
	return err // 讀取 body 時的其他錯誤，例如連線中斷
}
  • http.MaxBytesReader 讀超過上限時回傳 *http.MaxBytesError，並讓 server 在回應後關掉這個連線，對方就不能繼續灌資料。
  • 用 23 章的 json/v2 加上 RejectUnknownMembers：客戶端把 qty 拼成 qyt，會得到 400 和「不認得的欄位」，而不是默默地被當成 0。
  • 給客戶端的訊息用 JSON Pointer 指出是哪個欄位，不直接回傳 err.Error()：v2 的錯誤訊息每次可能不同（23 章），而且內部的型別名稱不需要讓外面知道。
  • mime.ParseMediaType 讓 application/json; charset=utf-8 也能通過。

用各種錯法送給點餐的 API（它在下一節）：

4. JSON API 與錯誤回應

店家的邏輯和 HTTP 無關：它只回傳 11 章的那種錯誤值，不知道什麼是 404：

var (
	ErrNotFound    = errors.New("找不到這筆訂單")
	ErrSoldOut     = errors.New("賣完了")
	ErrUnknownDish = errors.New("沒有這道菜")
)

type Order struct {
	ID    int    `json:"id"`
	Dish  string `json:"dish"`
	Qty   int    `json:"qty"`
	Total int    `json:"total"`
}

type shop struct {
	mu     sync.Mutex
	prices map[string]int
	stock  map[string]int
	orders map[int]Order
	nextID int
}

func (s *shop) place(dish string, qty int) (Order, error) {
	s.mu.Lock()
	defer s.mu.Unlock()
	price, ok := s.prices[dish]
	if !ok {
		return Order{}, fmt.Errorf("%w：%s", ErrUnknownDish, dish)
	}
	if s.stock[dish] < qty {
		return Order{}, fmt.Errorf("%s %w，剩 %d 份", dish, ErrSoldOut, s.stock[dish])
	}
	s.stock[dish] -= qty
	o := Order{ID: s.nextID, Dish: dish, Qty: qty, Total: price * qty}
	s.orders[o.ID] = o
	s.nextID++
	return o, nil
}

func (s *shop) find(id int) (Order, error) {
	s.mu.Lock()
	defer s.mu.Unlock()
	o, ok := s.orders[id]
	if !ok {
		return Order{}, ErrNotFound
	}
	return o, nil
}

HTTP 這一層讓 handler 回傳 error，由 handle 統一轉成回應。客戶端犯的錯用 httpError 帶著狀態碼；店家的錯用 errors.Is 對應；其他沒預期到的一律 500，細節只記在 log：

type api struct {
	shop   *shop
	logger *slog.Logger
}

func (a *api) routes() *http.ServeMux {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /menu", a.handle(a.listMenu))
	mux.HandleFunc("POST /orders", a.handle(a.createOrder))
	mux.HandleFunc("GET /orders/{id}", a.handle(a.getOrder))
	mux.HandleFunc("GET /healthz", func(w http.ResponseWriter, r *http.Request) {
		io.WriteString(w, "ok\n")
	})
	return mux
}

type apiFunc func(w http.ResponseWriter, r *http.Request) error

func (a *api) handle(f apiFunc) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		err := f(w, r)
		if err == nil {
			return
		}
		status, msg := statusOf(err)
		if status == http.StatusInternalServerError {
			// 內部錯誤的細節只記在 log，不告訴客戶端。
			a.logger.ErrorContext(r.Context(), "內部錯誤", "path", r.URL.Path, "err", err)
		}
		writeJSON(w, status, errorBody{Error: msg})
	}
}

type errorBody struct {
	Error string `json:"error"`
}

type httpError struct {
	status int
	msg    string
}

func statusOf(err error) (int, string) {
	if he, ok := errors.AsType[*httpError](err); ok {
		return he.status, he.msg
	}
	switch {
	case errors.Is(err, ErrNotFound):
		return http.StatusNotFound, err.Error()
	case errors.Is(err, ErrSoldOut):
		return http.StatusConflict, err.Error()
	case errors.Is(err, ErrUnknownDish):
		return http.StatusBadRequest, err.Error()
	}
	return http.StatusInternalServerError, "伺服器發生錯誤"
}

func writeJSON(w http.ResponseWriter, status int, v any) error {
	b, err := json.Marshal(v)
	if err != nil {
		return err
	}
	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(status)
	w.Write(b) // 寫失敗通常是客戶端已經斷線，沒有什麼能做的
	return nil
}
func (a *api) createOrder(w http.ResponseWriter, r *http.Request) error {
	var in struct {
		Dish string `json:"dish"`
		Qty  int    `json:"qty"`
	}
	if err := decodeJSON(w, r, &in); err != nil {
		return err
	}
	if in.Qty < 1 || in.Qty > 20 {
		return &httpError{http.StatusBadRequest, "qty 要在 1 到 20 之間"}
	}
	o, err := a.shop.place(in.Dish, in.Qty)
	if err != nil {
		return err
	}
	w.Header().Set("Location", "/orders/"+strconv.Itoa(o.ID))
	return writeJSON(w, http.StatusCreated, o)
}

func (a *api) getOrder(w http.ResponseWriter, r *http.Request) error {
	id, err := strconv.Atoi(r.PathValue("id"))
	if err != nil {
		return &httpError{http.StatusBadRequest, "訂單編號要是數字"}
	}
	o, err := a.shop.find(id)
	if err != nil {
		return err
	}
	return writeJSON(w, http.StatusOK, o)
}

  • 500 的訊息故意很籠統。資料庫的錯誤訊息可能包含資料表名稱、SQL、主機名稱，這些都不該讓外面的人看到。

5. middleware

每個請求都要做的事（記錄、驗證身分、限流、加標頭）寫成 middleware，包在路由外面，handler 就不用每一個都寫一次。記錄每個請求需要知道 handler 寫了哪個狀態碼，但 ResponseWriter 沒有提供讀取的方法，所以包一層把它記下來：

type statusWriter struct {
	http.ResponseWriter
	status int
	bytes  int
}

func (sw *statusWriter) WriteHeader(code int) {
	if sw.status == 0 {
		sw.status = code
	}
	sw.ResponseWriter.WriteHeader(code)
}

func (sw *statusWriter) Write(b []byte) (int, error) {
	if sw.status == 0 {
		sw.status = http.StatusOK // 沒有呼叫 WriteHeader 就直接 Write，等於 200
	}
	n, err := sw.ResponseWriter.Write(b)
	sw.bytes += n
	return n, err
}

func (sw *statusWriter) Unwrap() http.ResponseWriter {
	return sw.ResponseWriter
}

func logRequests(logger *slog.Logger, next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		sw := &statusWriter{ResponseWriter: w}
		next.ServeHTTP(sw, r)
		logger.InfoContext(r.Context(), "request",
			"method", r.Method, "path", r.URL.Path, "pattern", r.Pattern,
			"status", sw.status, "bytes", sw.bytes, "took", time.Since(start))
	})
}
  • 嵌入 http.ResponseWriter，只覆寫要攔下來的方法（09 章）。
  • 原本的 ResponseWriter 可能還有 Flush（串流回應）這類額外的功能，包一層之後型別斷言就找不到了。加上 Unwrap 方法，http.NewResponseController(w).Flush() 會一層一層往裡找。
  • r.Pattern 是 ServeMux 對到之後才填上的，所以在 next.ServeHTTP 之後讀。記錄 pattern（GET /orders/{id}）而不是實際的路徑，統計時才不會每個訂單編號都是不同的一類。

handler panic 時，net/http 會記下 panic、直接切斷這個連線，客戶端只看到連線被關掉。recoverPanic 把它改成一般的 500：

func recoverPanic(logger *slog.Logger, next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		defer func() {
			v := recover()
			if v == nil {
				return
			}
			if v == http.ErrAbortHandler {
				panic(v) // 這是 handler 故意中止連線的訊號，交給 net/http 處理
			}
			logger.ErrorContext(r.Context(), "panic", "path", r.URL.Path, "value", v)
			writeJSON(w, http.StatusInternalServerError, errorBody{Error: "伺服器發生錯誤"})
		}()
		next.ServeHTTP(w, r)
	})
}

func (a *api) handler() http.Handler {
	return logRequests(a.logger, recoverPanic(a.logger, a.routes()))
}
func middlewareDemo() {

  • 範例的 Logger 拿掉了時間和 took（耗時），輸出才會每次一樣（dropVolatile，和 25 章的 dropTime 同樣的做法）。
  • recoverPanic 救得了 handler 的 goroutine，救不了 handler 自己開的 goroutine：那裡的 panic 一樣會讓整個程式結束。
  • panic 發生時如果 handler 已經寫了一部分的內容，就來不及改成 500 了。recover 是最後的防線，不是錯誤處理的方式。
  • 給瀏覽器用的服務（用 cookie 登入的表單），Go 1.25 起標準庫有現成的 http.NewCrossOriginProtection()，它的 Handler 方法就是一個擋跨站請求偽造（CSRF）的 middleware。

6. http.Server 與逾時

http.ListenAndServe(":8080", h) 很方便，但它用的 http.Server 每個逾時都是 0。正式的服務自己建立 http.Server，至少設 ReadHeaderTimeout：

func newServer(addr string, h http.Handler, logger *slog.Logger) *http.Server {
	return &http.Server{
		Addr:              addr,
		Handler:           h,
		ReadHeaderTimeout: 5 * time.Second,  // 讀完請求標頭的期限
		ReadTimeout:       10 * time.Second, // 讀完整個請求（含 body）的期限
		WriteTimeout:      15 * time.Second, // 從讀完標頭到寫完回應的期限
		IdleTimeout:       60 * time.Second, // keep-alive 連線閒置多久就關掉
		ErrorLog:          slog.NewLogLogger(logger.Handler(), slog.LevelError),
	}
}
  • ReadHeaderTimeout 擋住「慢慢送標頭」的連線，是最重要的一個，幾秒就夠了。
  • WriteTimeout 也限制了 handler 的執行時間。下載大檔案、串流這類需要很久的路由，可以在 handler 裡用 http.NewResponseController(w).SetWriteDeadline 單獨延長。
  • 只想限制某些 handler 的執行時間，用 http.TimeoutHandler(h, 時間, 訊息) 包住它，逾時回 503。
  • ErrorLog 是 net/http 自己記錄問題（例如 panic、TLS 握手失敗）用的 *log.Logger。slog.NewLogLogger 讓它也寫進同一個 slog Handler（25 章）。
  • MaxHeaderBytes 限制標頭的大小，預設 1 MB；Go 1.27 起還有 MaxHeaderValueCount 限制標頭值的數量。

7. 優雅關機

main 用 21 章的 signal.NotifyContext 等關機訊號，run 在另一個 goroutine 跑 ListenAndServe，收到訊號後呼叫 Shutdown：

func main() {
	logger := slog.New(slog.NewTextHandler(os.Stderr, nil))
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()

	a := &api{shop: newShop(), logger: logger}
	srv := newServer(":8080", a.handler(), logger)
	logger.Info("開始營業", "addr", srv.Addr)
	if err := run(ctx, srv, logger); err != nil {
		logger.Error("server 停止", "err", err)
		os.Exit(1)
	}
	logger.Info("打烊")
}

func run(ctx context.Context, srv *http.Server, logger *slog.Logger) error {
	errc := make(chan error, 1)
	go func() { errc <- srv.ListenAndServe() }()

	select {
	case err := <-errc:
		return err // 還沒收到關機訊號就停了，例如 port 已經被佔用
	case <-ctx.Done():
	}

	logger.Info("關機中，等進行中的請求做完")
	shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()
	if err := srv.Shutdown(shutdownCtx); err != nil {
		return err // 10 秒內沒做完
	}
	if err := <-errc; !errors.Is(err, http.ErrServerClosed) {
		return err
	}
	return nil
}
  • ListenAndServe 在 Shutdown 之後回傳 http.ErrServerClosed，這是正常結束，不是錯誤。
  • Shutdown 的 ctx 決定最多等多久。容器平台通常在 SIGTERM 之後等一段時間（常見是 30 秒）才強制結束，期限要比它短。
  • Shutdown 不會取消 handler 的 r.Context()。handler 裡有很長的工作時，可以用 BaseContext 欄位給所有請求一個共同的父 context，關機時自己取消它。
  • port 被佔用時 ListenAndServe 會立刻回傳錯誤，run 的 select 讓這種情況直接回傳，不會一直等關機訊號。

Shutdown 真的會等進行中的請求嗎？這可以測試。下一節的 NewTestServer 搭配 22 章的 synctest，「做 3 秒的便當」不用真的等 3 秒：

func TestShutdownWaits(t *testing.T) {
	synctest.Test(t, func(t *testing.T) {
		started := make(chan struct{})
		slow := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			close(started)
			time.Sleep(3 * time.Second) // 正在做便當
			io.WriteString(w, "便當好了")
		})
		srv := httptest.NewTestServer(t, slow)
		client := srv.Client()

		got := make(chan string)
		go func() {
			res, err := client.Get("http://shop.test/")
			if err != nil {
				got <- "錯誤：" + err.Error()
				return
			}
			defer res.Body.Close()
			b, _ := io.ReadAll(res.Body)
			got <- string(b)
		}()

		<-started
		start := time.Now()
		ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
		defer cancel()
		if err := srv.Config.Shutdown(ctx); err != nil {
			t.Fatalf("Shutdown：%v", err)
		}
		if waited := time.Since(start); waited < 3*time.Second {
			t.Errorf("Shutdown 只等了 %v，進行中的請求還沒做完", waited)
		}
		if body := <-got; body != "便當好了" {
			t.Errorf("客戶端拿到 %q，want 便當好了", body)
		}
	})
}

8. 測試

httptest.NewRequest 建一個假的請求，httptest.NewRecorder 是一個把回應存起來的 ResponseWriter。把兩個交給 handler 的 ServeHTTP，就能檢查狀態碼、標頭和內容。本章所有的示範都透過這個小工具：

func send(h http.Handler, method, target, body string, headers ...string) {
	contentType := ""
	if body != "" {
		contentType = "application/json"
	}
	sendAs(h, contentType, method, target, body, headers...)
}

func sendAs(h http.Handler, contentType, method, target, body string, headers ...string) {
	req := httptest.NewRequest(method, target, strings.NewReader(body))
	if contentType != "" {
		req.Header.Set("Content-Type", contentType)
	}
	rec := httptest.NewRecorder()
	h.ServeHTTP(rec, req)

	res := rec.Result() // 標頭是第一次寫出內容時的樣子，和真的 server 送出去的一樣
	fmt.Printf("%s %s → %d", method, target, res.StatusCode)
	for _, k := range headers {
		if v := res.Header.Get(k); v != "" {
			fmt.Printf("，%s: %s", k, v)
		}
	}
	fmt.Println()
	if b, _ := io.ReadAll(res.Body); len(b) > 0 {
		fmt.Println(strings.TrimRight(string(b), "\n"))
	}
}
  • 用 rec.Result() 取得回應，不要直接讀 rec.Header()：後者是 handler 一直在改的那個 map，連 Write 之後才設的標頭都看得到，和客戶端實際收到的不一樣（第 1 節的 lateHeader 就會被誤判成對的）。
  • Recorder 不經過 http.Server，所以 server 的逾時、MaxBytesReader 讀超過上限後關掉連線這類行為測不到。

Go 1.27 加入了 httptest.NewTestServer(t, handler)：一個真的 http.Server，但網路在記憶體裡，不用開 port，也不會碰到 port 被佔用這類問題。測試結束時它會自動關掉，handler panic 會讓測試失敗：

func TestEndToEnd(t *testing.T) {
	a := &api{shop: newShop(), logger: slog.New(slog.DiscardHandler)}
	srv := httptest.NewTestServer(t, a.handler())
	client := srv.Client() // 一定要用這個 client，它才會把請求送到記憶體裡的 server

	res, err := client.Post("http://shop.test/orders", "application/json", strings.NewReader(`{"dish":"滷肉飯","qty":3}`))
	if err != nil {
		t.Fatal(err)
	}
	res.Body.Close()
	loc := res.Header.Get("Location")
	if res.StatusCode != http.StatusCreated || loc != "/orders/1" {
		t.Fatalf("POST /orders = %d，Location %q；want 201、/orders/1", res.StatusCode, loc)
	}

	res, err = client.Get("http://shop.test" + loc)
	if err != nil {
		t.Fatal(err)
	}
	defer res.Body.Close()
	var got Order
	if err := json.UnmarshalRead(res.Body, &got); err != nil {
		t.Fatal(err)
	}
	if want := (Order{ID: 1, Dish: "滷肉飯", Qty: 3, Total: 150}); got != want {
		t.Errorf("GET %s = %+v，want %+v", loc, got, want)
	}
}
  • 一定要用 srv.Client()。它會把所有的請求送到記憶體裡的 server，不管網址的主機名稱寫什麼。用 http.Get 或 http.DefaultClient 的話，請求會真的送上網路。
  • 舊的寫法 httptest.NewServer 會在本機開一個真的 port，測試結束時要自己 Close。
  • handler 會被同時呼叫，所以也要測並發：本章的 TestConcurrentOrders 讓 20 個人同時搶 5 份排骨飯，用 -race 跑，確認剛好 5 個成功。

常見錯誤

1. http.Error 之後沒有 return

http.Error 只是寫出回應，不會結束函式。下面的程式照樣執行：資料被改了，錯誤訊息後面還接著成功的內容（練習 6）。

2. 寫了內容才設標頭和狀態碼

第一次 Write 時標頭和狀態碼就送出了，之後的設定沒有效果，也不會報錯。順序是標頭、狀態碼、內容（第 1 節）。

3. 用 http.ListenAndServe 上線

它沒有任何逾時，慢速的連線可以把 server 拖垮。自己建立 http.Server，至少設 ReadHeaderTimeout（第 6 節）。

4. handler 之間共用的資料沒有保護

每個請求在不同的 goroutine 裡，共用的 map、計數器要用 Mutex 或 atomic。用 -race 跑並發的測試（第 1、8 節）。

5. 沒有限制 body 的大小，也沒有拒絕不認得的欄位

一個很大的請求就能吃光記憶體；拼錯的欄位被默默當成零值。用 MaxBytesReader 和 RejectUnknownMembers（第 3 節）。

6. 把內部錯誤的訊息回給客戶端

資料庫的錯誤可能包含 SQL、資料表、主機名稱。500 只回籠統的訊息，細節記在 log（第 4 節）。

7. 包裝 ResponseWriter 卻沒有 Unwrap

包一層之後，Flush 這類額外的功能就找不到了，串流的回應會卡在緩衝區。加上 Unwrap，並用 http.NewResponseController 呼叫這些功能（第 5 節）。

8. 測 NewTestServer 時用 http.Get

預設的 client 不知道記憶體裡的網路，請求會真的送到網路上。一律用 srv.Client()（第 8 節）。

重點回顧

  • Handler 只有 ServeHTTP 一個方法；函式用 HandlerFunc 轉型。每個請求在自己的 goroutine 裡執行。
  • 回應的順序是標頭、狀態碼、內容；第一次 Write 之後就改不了。
  • ServeMux 的 pattern 有方法和路徑變數，最具體的贏；方法不對自動回 405。
  • 請求的內容要檢查 Content-Type、限制大小、拒絕不認得的欄位，再檢查值。
  • handler 回傳 error，由一個地方轉成狀態碼和一致的 JSON；500 不外洩細節。
  • middleware 是 Handler 包 Handler，順序有意義；包裝 ResponseWriter 要加 Unwrap。
  • 正式的服務自己建立 http.Server，設好逾時。
  • 收到關機訊號時呼叫 Shutdown，等進行中的請求做完；ErrServerClosed 是正常結束。
  • handler 的邏輯用 NewRecorder 測，整個服務用 NewTestServer 和 srv.Client() 測，並發的部分用 -race。
