context

context 是跟著訂單一路傳下去的單據：櫃台、廚房、外送員手上都有一張。客人一取消，或是超過說好的時間，每個拿著單據的人都知道該停手；單據上也能寫著這張訂單的編號。

1. 為什麼需要 context

16 章用一個 done channel 叫送的一方停下來。真實的程式裡，一個請求會經過櫃台、廚房、外送好幾層函式，每一層可能又開 goroutine、打資料庫、呼叫其他服務。每一層都要知道「客人取消了」「已經超過時間了」，而且這個訊號要能一路往下傳。標準庫的 context 套件就是這件事的標準做法，HTTP 伺服器、資料庫、gRPC 都用它。

context.Context 是一個介面，只有四個方法：

方法回傳什麼
Done() <-chan struct{}被取消時會被 close 的 channel，放進 select 裡等
Err() error還沒取消時是 nil；取消後是 context.Canceled 或 context.DeadlineExceeded
Deadline() (time.Time, bool)期限是什麼時候；沒有期限時 ok 是 false
Value(key any) any跟著這個請求的值（第 6 節）

最上層的 ctx 是 context.Background()：永遠不會被取消、沒有期限、沒有值。其他的 ctx 都是從某一個 ctx 衍生出來的。一個會聽 ctx 的函式，最基本的樣子是這樣：

func cook(ctx context.Context, d time.Duration) error {
	select {
	case <-time.After(d):
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}
}

func basicsDemo() {
	if err := cook(context.Background(), time.Millisecond); err == nil {
		fmt.Println("滷蛋 好了")
	}

	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Millisecond)
	defer cancel()
	if err := cook(ctx, time.Hour); err != nil {
		fmt.Println("佛跳牆 放棄：", err)
	}
}

輸出

滷蛋 好了
佛跳牆 放棄： context deadline exceeded

cook 同時等兩件事：菜煮好，或是 ctx 被取消，和 16 章的逾時一模一樣，只是取消的訊號換成了 ctx.Done()。佛跳牆要煮一小時，但 ctx 只給 10 毫秒，時間一到 Done 被 close，cook 回傳 ctx.Err() 告訴呼叫的人為什麼停下來。

2. 取消樹

context.WithCancel(parent) 從 parent 衍生出一個新的 ctx，同時回傳一個 cancel 函式。衍生出來的 ctx 會在兩種情況被取消：呼叫它自己的 cancel，或是它的上層被取消。一層一層衍生下去，就形成一棵樹：

func treeDemo() {
	shop, closeShop := context.WithCancel(context.Background())
	defer closeShop()
	east, closeEast := context.WithCancel(shop)
	defer closeEast()
	west, closeWest := context.WithCancel(shop)
	defer closeWest()
	order, closeOrder := context.WithTimeout(east, time.Hour)
	defer closeOrder()

	closeEast()
	<-order.Done()
	fmt.Println("總店", shop.Err())
	fmt.Println("東區", east.Err())
	fmt.Println("東區的訂單", order.Err())
	fmt.Println("西區", west.Err())

	closeShop()
	<-west.Done()
	fmt.Println("總店關門之後，西區", west.Err())
}

輸出

總店 <nil>
東區 context canceled
東區的訂單 context canceled
西區 <nil>
總店關門之後，西區 context canceled
  • 取消東區，東區底下的訂單跟著取消；總店和西區不受影響。最後關掉總店，西區也被取消。
  • 這就是為什麼函式要「從收到的 ctx 衍生」，而不是自己用 Background 重新開始：重新開始就和上層斷了線，上層的取消傳不下來（練習 6）。
  • cancel 一定要呼叫，即使工作已經順利做完。cancel 會把這個 ctx 從上層的名單上拿掉、停掉計時器；不呼叫的話，這些資源要等到上層被取消才會釋放。慣例是拿到 cancel 的下一行就寫 defer cancel()。
  • cancel 呼叫好幾次沒關係，第二次之後什麼都不做。示範裡 closeEast 被呼叫了兩次（一次直接呼叫，一次是 defer），就是這個原因。

忘記呼叫 cancel，go vet 抓得到：

package main

import (
	"context"
	"fmt"
	"time"
)

func main() {
	ctx, _ := context.WithTimeout(context.Background(), time.Second)
	fmt.Println(ctx.Err())
}

go vet

main.go:10:7: the cancel function returned by context.WithTimeout should be called, not discarded, to avoid a context leak

3. 期限

context.WithTimeout(parent, d) 從現在算起 d 之後自動取消；context.WithDeadline(parent, t) 在指定的時間點 t 自動取消。兩者都回傳 cancel，時間還沒到也可以提早取消。被取消的原因有兩種，用 errors.Is 分辨：

func errDemo() {
	canceled, cancel := context.WithCancel(context.Background())
	cancel()
	expired, cancel2 := context.WithTimeout(context.Background(), time.Millisecond)
	defer cancel2()

	for _, ctx := range []context.Context{canceled, expired} {
		<-ctx.Done()
		err := ctx.Err()
		fmt.Printf("%v：Canceled=%t DeadlineExceeded=%t\n",
			err, errors.Is(err, context.Canceled), errors.Is(err, context.DeadlineExceeded))
	}
}

輸出

context canceled：Canceled=true DeadlineExceeded=false
context deadline exceeded：Canceled=false DeadlineExceeded=true

呼叫的人主動取消（例如 HTTP 的客戶端斷線）是 Canceled；時間到了是 DeadlineExceeded。前者通常不用當成錯誤處理，後者常常要記錄下來，看看哪裡太慢。

期限也會沿著樹往下：衍生的 ctx 期限只能比上層早，不能比較晚：

func deadlineDemo() {
	parent, cancel := context.WithTimeout(context.Background(), time.Second)
	defer cancel()
	long, cancelLong := context.WithTimeout(parent, time.Hour)
	defer cancelLong()
	short, cancelShort := context.WithTimeout(parent, 10*time.Millisecond)
	defer cancelShort()

	pd, _ := parent.Deadline()
	ld, _ := long.Deadline()
	sd, _ := short.Deadline()
	fmt.Printf("要 1 小時，實際期限和上層一樣：%t\n", ld.Equal(pd))
	fmt.Printf("要 10 毫秒，期限比上層早：%t\n", sd.Before(pd))

	_, ok := context.Background().Deadline()
	fmt.Printf("Background 有期限：%t\n", ok)
}

輸出

要 1 小時，實際期限和上層一樣：true
要 10 毫秒，期限比上層早：true
Background 有期限：false

整個請求只有 1 秒，底下哪一層要求 1 小時都沒有用。這讓「整個請求最多 1 秒」這種規定只要在最上層設一次，底下每一層自動遵守。反過來，底下也可以用 ctx.Deadline() 看還剩多少時間，時間不夠就不要開始做一件注定做不完的事（練習 2）。

4. 取消的原因

ctx.Err() 只會告訴你「被取消了」或「超過期限了」，看 log 時常常不知道到底是誰、為什麼取消的。Go 1.20 加入 context.WithCancelCause：它的 cancel 收一個 error 當原因，之後用 context.Cause 取出；Go 1.21 再加入 WithTimeoutCause、WithDeadlineCause，指定時間到的時候用什麼原因：

func causeDemo() {
	ctx, cancel := context.WithCancelCause(context.Background())
	child, cancelChild := context.WithCancel(ctx)
	defer cancelChild()
	cancel(errSoldOut)
	fmt.Println(ctx.Err(), "/", context.Cause(ctx))
	fmt.Println("衍生的 ctx 也拿得到原因：", context.Cause(child))

	slow, cancelSlow := context.WithTimeoutCause(context.Background(), 10*time.Millisecond, errSlow)
	defer cancelSlow()
	<-slow.Done()
	fmt.Println(slow.Err(), "/", context.Cause(slow))

	plain, cancelPlain := context.WithCancel(context.Background())
	cancelPlain()
	fmt.Println("沒有指定原因：", context.Cause(plain))
}

輸出

context canceled / 排骨賣完了
衍生的 ctx 也拿得到原因： 排骨賣完了
context deadline exceeded / 廚房出餐太慢
沒有指定原因： context canceled
  • Err 照舊是 Canceled 或 DeadlineExceeded，原本用 errors.Is 判斷的程式不必改。
  • 從它衍生出來的 ctx，Cause 也拿得到同一個原因。
  • 沒有指定原因時，Cause 回傳和 Err 一樣的值，所以記錄 log 時一律寫 context.Cause(ctx) 就好。

5. 寫一個聽 ctx 的函式

context 不會強迫任何 goroutine 停下來，它只是一個訊號，要每個函式自己去聽。依照函式在做什麼，有三種聽法。第一種是在等東西的時候（等 channel、等計時器），把 ctx.Done() 放進同一個 select。把 16 章的 done channel 換成 ctx：

func prepare(ctx context.Context, items ...string) <-chan string {
	out := make(chan string)
	go func() {
		defer close(out)
		for _, it := range items {
			select {
			case out <- it:
			case <-ctx.Done():
				return
			}
		}
	}()
	return out
}

func listenDemo() {
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()
	for o := range prepare(ctx, "排骨飯", "雞腿飯", "魚排飯", "滷肉飯") {
		fmt.Println(o)
		if o == "雞腿飯" {
			break
		}
	}
}

輸出

排骨飯
雞腿飯

收到雞腿飯就 break，離開時 defer 的 cancel 讓 prepare 的 goroutine 選到 Done、結束並 close channel，不會洩漏。和 done channel 比起來，ctx 多了期限、原因和整棵取消樹，而且呼叫的人可以直接把自己手上的 ctx 傳進來。

第二種是一直在算、沒有在等任何東西的工作，沒有 channel 可以 select，就每做一段檢查一次 ctx.Err()：

func tally(ctx context.Context, amounts []int) (int, error) {
	sum := 0
	for i, a := range amounts {
		if i%1000 == 0 {
			if err := ctx.Err(); err != nil {
				return 0, err
			}
		}
		sum += a
	}
	return sum, nil
}

func tallyDemo() {
	amounts := make([]int, 5000)
	for i := range amounts {
		amounts[i] = i + 1
	}
	fmt.Println(tally(context.Background(), amounts))

	ctx, cancel := context.WithCancel(context.Background())
	cancel()
	fmt.Println(tally(ctx, amounts))
}

輸出

12502500 <nil>
0 context canceled

不用每一圈都檢查：ctx.Err() 本身有成本，每一千筆看一次，取消之後最多多算一千筆，已經夠快了。第三種是呼叫別人：把 ctx 原封不動傳下去，或從它衍生一個加了期限的。標準庫裡會等待的 API 大多有收 ctx 的版本，例如 http.NewRequestWithContext、(*sql.DB).QueryContext；HTTP 伺服器的 handler 用 r.Context() 拿到這個請求的 ctx，客戶端斷線時它就會被取消（「HTTP 服務」那一章）。

ctx 在 API 裡的慣例，context 套件文件寫得很清楚：

  • ctx 是函式的第一個參數，名字叫 ctx：func Deliver(ctx context.Context, o Order) error。
  • 不要把 ctx 存在 struct 裡，每個需要它的方法都明確地收一個。ctx 代表「這一次呼叫」，存起來就分不清是哪一次了。
  • 不要傳 nil。還不確定要用哪個 ctx 時，傳 context.TODO()，它和 Background 一樣，但標明「這裡之後要接上真正的 ctx」。
  • context.Background() 只出現在最上層：main、程式初始化、測試。測試裡更好的選擇是 Go 1.24 加入的 t.Context()，測試結束前它會被取消。
  • 因為 ctx 而停下來時，回傳 ctx.Err()（或包住它），呼叫的人才能用 errors.Is 判斷。
  • 同一個 ctx 可以同時交給好幾個 goroutine 使用，它是並行安全的。

6. 帶值

context.WithValue(parent, key, val) 衍生一個帶著一組 key/值的 ctx，之後從它衍生的 ctx 都查得到。適合放的是跟著這個請求、跨越 API 邊界的資料：請求編號、追蹤用的 trace ID、登入的使用者。標準的寫法是一個不匯出的 key 型別，加上一對存取函式：

type orderIDKey struct{}

func withOrderID(ctx context.Context, id string) context.Context {
	return context.WithValue(ctx, orderIDKey{}, id)
}

func orderID(ctx context.Context) (string, bool) {
	id, ok := ctx.Value(orderIDKey{}).(string)
	return id, ok
}

func logLine(ctx context.Context, msg string) {
	id, ok := orderID(ctx)
	if !ok {
		id = "-"
	}
	fmt.Printf("[%s] %s\n", id, msg)
}

func valueDemo() {
	ctx := withOrderID(context.Background(), "A-07")
	ctx, cancel := context.WithTimeout(ctx, time.Second)
	defer cancel()
	logLine(ctx, "開始備餐")
	logLine(context.Background(), "沒有訂單的紀錄")
}

輸出

[A-07] 開始備餐
[-] 沒有訂單的紀錄
  • key 用自己定義、不匯出的型別。用 string 當 key，兩個套件都用 "id" 就會互相蓋掉；不匯出的型別，別的套件根本寫不出來。struct{} 型別的 key 不佔空間。
  • 只透過 withOrderID / orderID 存取，型別斷言集中在一個地方，呼叫的人拿到的是有型別的值。
  • 不要用它傳一般參數。函式需要的東西寫在參數列上，看簽名就知道它需要什麼；藏在 ctx 裡的依賴，編譯器不會檢查，讀程式的人也看不到。資料庫連線、設定這類依賴，放在 struct 欄位或參數裡。
  • 放進去的值要當成唯讀的：同一個 ctx 可能同時被好幾個 goroutine 讀（練習 3）。
  • 查詢是一層一層往上找，層數多時會慢一點。不要把它當成可以頻繁讀寫的 map。

7. WithoutCancel 與 AfterFunc

Go 1.21 加入兩個比較少用、但遇到時很好用的函式。第一個是 context.WithoutCancel：請求已經結束（ctx 被取消）了，還有事情要做，例如寫對帳紀錄、更新快取。直接用請求的 ctx 會馬上被取消；用 Background 又會丟掉請求編號這些值。WithoutCancel 回傳一個保留值、但不會被取消的 ctx：

func detachDemo() {
	req, cancel := context.WithCancel(withOrderID(context.Background(), "A-07"))
	audit := context.WithoutCancel(req)
	cancel()

	id, _ := orderID(audit)
	fmt.Println("請求：", req.Err())
	fmt.Println("對帳紀錄：", audit.Err(), id)
}

輸出

請求： context canceled
對帳紀錄： <nil> A-07

它也沒有期限，所以背景工作通常要自己再加一個：context.WithTimeout(context.WithoutCancel(ctx), 5*time.Second)，不然卡住時就永遠不會結束。

第二個是 context.AfterFunc：ctx 被取消時，在另一個 goroutine 執行一個函式。它用來把取消接到「不認得 ctx」的東西上，例如關掉一條網路連線，讓卡在讀取的 goroutine 醒過來：

func afterDemo() {
	ctx, cancel := context.WithCancel(context.Background())
	notified := make(chan struct{})
	context.AfterFunc(ctx, func() {
		fmt.Println("通知外送員：訂單取消")
		close(notified)
	})
	cancel()
	<-notified

	ctx2, cancel2 := context.WithCancel(context.Background())
	stop := context.AfterFunc(ctx2, func() {
		fmt.Println("這一行不會印出來")
	})
	fmt.Println("撤回通知：", stop())
	cancel2()
}

輸出

通知外送員：訂單取消
撤回通知： true
  • f 是在另一個 goroutine 執行的，所以示範用一個 channel 等它做完。
  • AfterFunc 回傳 stop。在 ctx 被取消前呼叫 stop，就撤回這個安排，stop 回傳 true；f 已經開始執行的話回傳 false。stop 不會等 f 做完。

常見錯誤

1. 沒有呼叫 cancel

WithCancel、WithTimeout、WithDeadline 拿到的 cancel 都要呼叫，最簡單的方法是下一行就寫 defer cancel()。go vet 會檢查（第 2 節）。

2. 在函式中間用 Background 重新開始

收到了 ctx，卻寫 context.WithTimeout(context.Background(), d)，上層的取消和期限就傳不下來了：呼叫的人早就放棄，這裡還在做。永遠從收到的 ctx 衍生（練習 6）。

3. 收了 ctx 卻不聽

函式簽名上有 ctx，裡面卻用 time.Sleep、沒有 select 的 channel 收送、不帶 ctx 的 API。取消時它照樣做完。會等待的地方都要放 ctx.Done()（第 5 節，練習 1）。

4. 把 ctx 存在 struct 裡

ctx 屬於某一次呼叫，存在 struct 裡，之後的每一次呼叫都會用到同一個、可能早就被取消的 ctx。每個方法各自收一個 ctx 參數。

5. 用 Value 傳參數、用 string 當 key

函式需要的東西寫在參數上；Value 只放跟著請求、跨越 API 邊界的資料。key 一律用不匯出的自訂型別（第 6 節）。

6. 被取消了卻回傳 nil，或把 Canceled 當嚴重錯誤

因為 ctx 停下來就回傳 ctx.Err()，呼叫的人才知道結果不完整。反過來，客戶端主動取消（Canceled）通常是正常現象，不必當成系統錯誤發警報；DeadlineExceeded 才代表某個地方太慢。

    先看 ctx.Err()；再用 ctx.Deadline()，ok 是 false 代表沒有期限。剩下的時間是 time.Until(deadline)。

  3. 進階練習 3：外送路線

    每經過一站就從上一個 ctx 衍生一個新的。同一個 ctx 分出去的兩條路線，互相不能影響。

    func WithStop(ctx context.Context, stop string) context.Context {
	// TODO: 實作
	return ctx
}

func Route(ctx context.Context) []string {
	// TODO: 實作
	return nil
}

    測試：TestRoute。

    提示

    不匯出的 key 型別，值存 []string。陷阱在 append：上一層的 slice 底層陣列還有空間時，兩條分支 append 會寫到同一格（slice 那一章）。WithStop 做一份新的 slice 再 append（slices.Clip 或 slices.Clone），Route 也回傳複本。

  4. 進階練習 4：轉送站

    把一個 channel 的東西轉送到另一個 channel，卡在收或卡在送時都要能被取消。

    func Pump[T any](ctx context.Context, in <-chan T, out chan<- T) error {
	// TODO: 實作
	return nil
}

    測試：TestPump。

    提示

    每一圈兩個 select：第一個收 in（ok 為 false 就回傳 nil）或等 ctx.Done()；第二個送 out 或等 ctx.Done()。只在收的地方聽 ctx 不夠，out 沒人收時會永遠卡在送。

  5. 挑戰練習 5：哪一間最快

    同時向好幾間分店下單，用最先做好的那一份，其他的通知取消，而且要等它們真的停下來。

    func Fastest(ctx context.Context, kitchens ...func(context.Context) (string, error)) (string, error) {
	// TODO: 實作
	return "", nil
}

    測試：TestFastest。

    提示

    先 ctx, cancel := context.WithCancel(ctx) 並 defer cancel，把這個 ctx 交給每一間。結果用容量 len(kitchens) 的 channel 收，誰送都不會卡住；每間用 wg.Go 開。收到第一個成功的：cancel()、wg.Wait()、回傳。失敗的錯誤存起來，全部失敗就 errors.Join。

  6. 找錯練習 6：問不到的等候時間

    客人已經離開了，系統還在等廚房回答。

    func Quote(ctx context.Context, ask func(context.Context) (time.Duration, error)) (time.Duration, error) {
	ctx, cancel := context.WithTimeout(context.Background(), time.Second)
	defer cancel()
	return ask(ctx)
}

    測試：TestQuote。

    提示

    常見錯誤 2。

參考解答：先自己寫完再看。測試通過、而且 -race 沒有警告的寫法都是對的。

重點回顧

  • context 把取消、期限和請求範圍的值，從最上層一路傳到最底層。
  • 最上層用 context.Background()，其他 ctx 都從上層衍生；取消只往下傳。
  • WithCancel、WithTimeout、WithDeadline 回傳的 cancel 一定要呼叫，慣例是 defer cancel()。
  • 衍生的 ctx 期限只能比上層早；用 errors.Is 分辨 Canceled 和 DeadlineExceeded。
  • 用 WithCancelCause、WithTimeoutCause 記下原因，context.Cause 取出，log 一律記 Cause。
  • 聽 ctx 的三種方式：select 等 Done、一直在算就定期看 Err、呼叫別人就把 ctx 傳下去。
  • ctx 是第一個參數，不存在 struct 裡，不傳 nil；測試用 t.Context()。
  • WithValue 只放跟著請求的資料，key 用不匯出的型別，值當成唯讀。
  • WithoutCancel 保留值、切斷取消；AfterFunc 在取消時執行一個函式。
