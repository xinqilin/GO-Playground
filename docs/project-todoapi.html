待辦事項 API

便當店想讓員工用手機記下待辦：訂明天的便當、繳電話費、倒垃圾。這個專題只用標準庫寫一個 REST API，重點不在功能多，而在每個環節都經得起真實的使用：輸入亂填、兩個人同時改同一筆、存檔到一半出錯、按下 Ctrl-C 時還有請求在處理。

這個專題做什麼

五個端點，管理一份待辦清單：

  • GET /todos：列出全部，?done=true 或 false 篩選。
  • POST /todos：新增，回 201 和新資源的網址（Location）。
  • GET /todos/{id}：取得一筆。
  • PATCH /todos/{id}：只改有傳的欄位。
  • DELETE /todos/{id}：刪除，回 204。

下面是一連串請求和回應。測試用 httptest 直接呼叫 handler，時間固定在 2026-11-21 09:30（台北），所以輸出每次都一樣：

1. 三層：api、service、Store

type api struct {
	svc    *service
	logger *slog.Logger
}
type service struct {
	store *Store
	now   func() time.Time // 測試時換成固定的時間
}
  • api：把 JSON 轉成 Go 的值、呼叫 service、把結果和錯誤轉成 HTTP 回應。它不判斷標題太長，也不知道資料存在哪裡。
  • service：這個服務的規則，例如標題要去掉前後空白、期限不能是過去的日期。它不知道請求從 HTTP 來，同一套規則也可以給命令列工具用。
  • Store：保存資料，處理並行和檔案。它不知道什麼樣的待辦是合法的。
  • 代價：多了轉手的程式。service 的 Get 和 Delete 沒有任何規則，只是直接呼叫 Store。這麼小的服務也可以把規則寫在 handler 裡；分層的好處要到規則變多、要換存檔方式、要寫測試的時候才看得出來。
  • 都在 package main：三層用型別分開，而不是用 package。服務長大之後，可以把它們搬到 internal/ 底下的不同 package，讓編譯器幫你擋住「Store 呼叫 api」這種反方向的依賴（33 章）。

2. 資料的樣子

type Todo struct {
	ID        int       `json:"id"`
	Title     string    `json:"title"`
	Done      bool      `json:"done"`
	Due       string    `json:"due,omitzero"` // 期限，格式是 2006-01-02；空字串代表沒有期限
	CreatedAt time.Time `json:"created_at"`
}

var ErrNotFound = errors.New("找不到這筆待辦")
  • 同一個 struct 給 API 和存檔用：欄位少的時候最省事。如果有不想讓客戶端看到的欄位（例如誰建立的），就要分成兩個型別：用 json:"-" 藏起來的話，存檔時也一起不見了。
  • omitzero（Go 1.24 起）：Due 是空字串時，整個欄位不出現在 JSON 裡。客戶端看到「沒有 due」就知道沒有期限（23 章）。
  • 期限用字串：期限只是一個日期，沒有時、分、時區。用 time.Time 的話，2026-11-22 要選一個時區的午夜，換個時區讀出來就變成前一天。建立時間 CreatedAt 才是真正的時間點，用 time.Time，JSON 裡是 RFC 3339 格式。
  • 空的清單是 []：encoding/json/v2 把 nil slice 編成 []，舊的 encoding/json 會編成 null（23 章）。客戶端不用特別處理 null。

3. 驗證：一次回報全部的問題

type ValidationError map[string]string

func (e ValidationError) Error() string {
	var b strings.Builder
	for i, field := range slices.Sorted(maps.Keys(e)) {
		if i > 0 {
			b.WriteString("；")
		}
		b.WriteString(field + "：" + e[field])
	}
	return b.String()
}
func (s *service) check(title, due *string) error {
	problems := ValidationError{}
	if title != nil {
		switch n := utf8.RuneCountInString(*title); {
		case n == 0:
			problems["title"] = "不能是空的"
		case n > maxTitle:
			problems["title"] = fmt.Sprintf("最多 %d 個字，現在是 %d 個字", maxTitle, n)
		}
	}
	if due != nil && *due != "" {
		now := s.now()
		d, err := time.ParseInLocation(time.DateOnly, *due, now.Location())
		y, m, day := now.Date()
		switch {
		case err != nil:
			problems["due"] = "格式要是 2006-01-02"
		case d.Before(time.Date(y, m, day, 0, 0, 0, 0, now.Location())):
			problems["due"] = "不能早於今天"
		}
	}
	if len(problems) > 0 {
		return problems
	}
	return nil
}
  • 錯誤也可以是 map：任何有 Error() string 方法的型別都是 error。ValidationError 的 key 是欄位名稱，值是給人看的說明。Error() 依欄位名稱排序，訊息才固定。
  • 沒有問題時回傳 nil，不要回傳空的 problems。函式的回傳型別是 error，空的 ValidationError 放進 error 裡就不是 nil 了，呼叫端的 err != nil 會成立（11 章）。
  • 字數用 rune 算：len 算的是 byte，一個中文字是 3 個 byte，100 個字的標題會被當成 300（08 章）。
  • 「今天」用注入的時鐘算：s.now() 在正式執行時是 time.Now，測試時固定在 2026-11-21。不然「期限不能早於今天」這個測試，明天就會失敗。日期也要在同一個時區比較。

api 這一層把 ValidationError 轉成 422（http.StatusUnprocessableEntity），問題放在 fields 裡。JSON 寫錯欄位名稱則是 400：那是格式的問題，不是內容的問題：

type errorBody struct {
	Error  string            `json:"error"`
	Fields map[string]string `json:"fields,omitzero"`
}

func errorResponse(err error) (int, errorBody) {
	if he, ok := errors.AsType[*httpError](err); ok {
		return he.status, errorBody{Error: he.msg}
	}
	if ve, ok := errors.AsType[ValidationError](err); ok {
		return http.StatusUnprocessableEntity, errorBody{Error: "輸入不合法", Fields: ve}
	}
	if errors.Is(err, ErrNotFound) {
		return http.StatusNotFound, errorBody{Error: err.Error()}
	}
	return http.StatusInternalServerError, errorBody{Error: "伺服器發生錯誤"}
}

  • TestCreateValidation 是一張表：合法的邊界（剛好 100 個字、期限是今天）和不合法的情況（101 個字、2 月 30 日、兩個欄位同時錯）都在裡面。

4. PATCH：沒有傳和傳了零值

type NewTodo struct {
	Title string `json:"title"`
	Due   string `json:"due"`
}

type Patch struct {
	Title *string `json:"title"`
	Done  *bool   `json:"done"`
	Due   *string `json:"due"` // 空字串代表清除期限
}

func (s *service) Update(id int, p Patch) (Todo, error) {
	if p == (Patch{}) {
		return Todo{}, ValidationError{"body": "至少要改一個欄位"}
	}
	if p.Title != nil {
		title := strings.TrimSpace(*p.Title)
		p.Title = &title
	}
	if err := s.check(p.Title, p.Due); err != nil {
		return Todo{}, err
	}
	return s.store.Update(id, func(t *Todo) {
		if p.Title != nil {
			t.Title = *p.Title
		}
		if p.Done != nil {
			t.Done = *p.Done
		}
		if p.Due != nil {
			t.Due = *p.Due
		}
	})
}
  • 只檢查有傳的欄位：期限過了之後，使用者只想打勾，不應該因為「期限早於今天」而失敗。TestUpdateChecksOnlyGivenFields 把時鐘往後撥三天，確認打勾可以、把期限改成過去的日期不行、清除期限可以。
  • struct 可以直接比較：Patch 的欄位都是指標，p == (Patch{}) 就是「全部都沒傳」（09 章）。
  • null 和沒傳一樣：{"due": null} 解碼後 Due 也是 nil。這裡用空字串表示「清除期限」，避開了這個差別；如果真的要分出 null，就要自己實作解碼。
  • 修改的內容交給一個函式：Update 沒有先讀出來、改好、再存回去，而是把「怎麼改」包成函式交給 Store，原因在下一節。

5. 讀、改、寫在同一把鎖裡

type Store struct {
	mu     sync.Mutex
	path   string
	todos  map[int]Todo
	nextID int
}

func (s *Store) Get(id int) (Todo, error) {
	s.mu.Lock()
	defer s.mu.Unlock()
	t, ok := s.todos[id]
	if !ok {
		return Todo{}, ErrNotFound
	}
	return t, nil
}

func (s *Store) Update(id int, change func(*Todo)) (Todo, error) {
	s.mu.Lock()
	defer s.mu.Unlock()
	t, ok := s.todos[id]
	if !ok {
		return Todo{}, ErrNotFound
	}
	change(&t)
	next := maps.Clone(s.todos)
	next[id] = t
	if err := s.commit(next, s.nextID); err != nil {
		return Todo{}, err
	}
	return t, nil
}
  • lost update：兩個人同時改同一筆，後寫的蓋掉先寫的。資料庫用交易或 UPDATE … SET done = true 只改一個欄位來避免；這裡用同一把鎖包住整個「讀、改、寫」。
  • 把修改當成參數：Store 不知道規則，但可以在鎖裡執行呼叫端給的函式。change 要很快，而且不能再呼叫 Store 的方法：sync.Mutex 不能重複鎖，會卡死自己。
  • Update 回傳修改後的值，而不是讓呼叫端再 Get 一次：再 Get 一次之間，可能又被別人改了。

TestConcurrentPatch 讓 100 個 goroutine 同時修改同一筆：一半改標題，一半打勾。最後標題和完成狀態都要是新的。

func TestConcurrentPatch(t *testing.T) {
	svc := newTestService(fixedNow)
	if _, err := svc.Create(NewTodo{Title: "訂便當"}); err != nil {
		t.Fatal(err)
	}
	var wg sync.WaitGroup
	for i := range 100 {
		wg.Go(func() {
			title, done := "訂排骨便當", true
			p := Patch{Title: &title}
			if i%2 == 0 {
				p = Patch{Done: &done}
			}
			if _, err := svc.Update(1, p); err != nil {
				t.Error(err)
			}
		})
	}
	wg.Wait()
	if got, _ := svc.Get(1); got.Title != "訂排骨便當" || !got.Done {
		t.Errorf("got %+v，標題和完成狀態都應該改到", got)
	}
}

6. 存進 JSON 檔

func (s *Store) Add(t Todo) (Todo, error) {
	s.mu.Lock()
	defer s.mu.Unlock()
	t.ID = s.nextID
	next := maps.Clone(s.todos)
	next[t.ID] = t
	if err := s.commit(next, s.nextID+1); err != nil {
		return Todo{}, err
	}
	return t, nil
}

func (s *Store) commit(todos map[int]Todo, nextID int) error {
	if s.path != "" {
		if err := saveAtomic(s.path, fileData{NextID: nextID, Todos: sortedTodos(todos)}); err != nil {
			return fmt.Errorf("存檔：%w", err)
		}
	}
	s.todos, s.nextID = todos, nextID
	return nil
}

func saveAtomic(path string, v any) (err error) {
	tmp, err := os.CreateTemp(filepath.Dir(path), filepath.Base(path)+".*.tmp")
	if err != nil {
		return err
	}
	defer func() {
		if err != nil {
			tmp.Close()
			os.Remove(tmp.Name())
		}
	}()
	if err = json.MarshalWrite(tmp, v, jsontext.WithIndent("  ")); err != nil {
		return err
	}
	if err = tmp.Sync(); err != nil { // 確定資料寫到磁碟上了，再換名字
		return err
	}
	if err = tmp.Close(); err != nil {
		return err
	}
	return os.Rename(tmp.Name(), path)
}
  • 先寫檔，再改記憶體：如果先改記憶體再寫檔，寫檔失敗時 API 已經改了資料，重新啟動之後卻不見了。commit 拿到的是複製出來改好的 map，寫檔成功才換上去；失敗的話，s.todos 完全沒有被動過，連復原的程式都不用寫。TestStoreSaveFails 用一個不存在的目錄讓寫檔失敗，確認記憶體裡沒有多出資料、下一筆的編號也沒有跳號。
  • 每次寫整份檔案：寫一次的成本和資料量成正比，複製 map 也是。幾千筆待辦完全沒問題；資料很多或寫入很頻繁時，就該換成資料庫（28 章）或只附加修改的紀錄（延伸挑戰 5）。
  • Sync 之後才 Rename：Sync 確定資料真的寫到磁碟上。少了它，系統當機時可能出現新檔名、內容卻是空的。
  • 暫存檔和目標在同一個目錄：Rename 跨檔案系統會失敗，所以不用系統的暫存目錄。
type fileData struct {
	NextID int    `json:"next_id"`
	Todos  []Todo `json:"todos"`
}

func OpenStore(path string) (*Store, error) {
	s := &Store{path: path, todos: map[int]Todo{}, nextID: 1}
	if path == "" {
		return s, nil
	}
	data, err := os.ReadFile(path)
	if errors.Is(err, fs.ErrNotExist) {
		return s, nil
	}
	if err != nil {
		return nil, err
	}
	var fd fileData
	if err := json.Unmarshal(data, &fd); err != nil {
		return nil, fmt.Errorf("讀取 %s：%w", path, err)
	}
	for _, t := range fd.Todos {
		s.todos[t.ID] = t
	}
	s.nextID = max(fd.NextID, 1)
	return s, nil
}

重新啟動後的新編號：3
  • next_id 要存：檔案裡只剩第 1 筆，但 next_id 是 3。如果只存清單、啟動時用最大的 ID 加 1，被刪掉的 2 就會再發給新的待辦；別人手上的舊網址 /todos/2 會突然指到另一筆資料。
  • 檔案不存在不是錯誤：第一次啟動時從空的開始。用 errors.Is(err, fs.ErrNotExist) 判斷，而不是先用 os.Stat 檢查再打開：檢查和打開之間，檔案可能被別人建立或刪掉。
  • 檔案壞掉就停下來：JSON 格式不對時，OpenStore 回傳錯誤，服務不會啟動。如果當成空的繼續跑，下一次存檔就會把壞掉但可能救得回來的資料整個蓋掉。

7. HTTP 這一層

func (a *api) routes() http.Handler {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /todos", a.handle(a.list))
	mux.HandleFunc("POST /todos", a.handle(a.create))
	mux.HandleFunc("GET /todos/{id}", a.handle(a.get))
	mux.HandleFunc("PATCH /todos/{id}", a.handle(a.update))
	mux.HandleFunc("DELETE /todos/{id}", a.handle(a.delete))
	// logRequests 在最外層，才記得到 recoverPanic 把 panic 改成的 500。
	return logRequests(a.logger, recoverPanic(a.logger, mux))
}

type apiFunc func(w http.ResponseWriter, r *http.Request) error

func (a *api) handle(f apiFunc) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		err := f(w, r)
		if err == nil {
			return
		}
		status, body := errorResponse(err)
		if status == http.StatusInternalServerError {
			// 內部錯誤的細節只記在 log，不告訴客戶端。
			a.logger.ErrorContext(r.Context(), "內部錯誤", "path", r.URL.Path, "err", err)
		}
		writeJSON(w, status, body)
	}
}
  • handler 回傳 error：和 26 章一樣，錯誤怎麼變成回應集中在 handle 決定，每個 handler 只要 return err。500 的細節只記在 log，不回給客戶端。
  • middleware 的順序：logRequests 在最外面，才記得到 recoverPanic 把 panic 改成的 500（26 章）。TestPanicBecomes500 確認 panic 不會讓連線直接斷掉。
func (a *api) create(w http.ResponseWriter, r *http.Request) error {
	var in NewTodo
	if err := decodeJSON(w, r, &in); err != nil {
		return err
	}
	t, err := a.svc.Create(in)
	if err != nil {
		return err
	}
	w.Header().Set("Location", "/todos/"+strconv.Itoa(t.ID))
	return writeJSON(w, http.StatusCreated, t)
}

func writeJSON(w http.ResponseWriter, status int, v any) error {
	b, err := json.Marshal(v, json.Deterministic(true))
	if err != nil {
		return err
	}
	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(status)
	w.Write(b)
	return nil
}
  • 201 加上 Location：新增成功時告訴客戶端新資源在哪裡，客戶端不用自己組網址。刪除成功回 204 No Content，沒有內容。
  • Deterministic：json/v2 為了速度，預設不排序 map 的 key，每次輸出的順序可能不同。錯誤回應的 fields 是 map，加上 json.Deterministic(true) 才每次一樣，Example 也才能比對（23 章）。
  • decodeJSON 檢查 Content-Type、用 MaxBytesReader 限制大小、拒絕不認得的欄位，和 26 章的寫法相同。

8. 組合、log 與關機

func main() {
	addr := flag.String("addr", "localhost:8080", "監聽的位址")
	data := flag.String("data", "todos.json", "存資料的 JSON 檔；空字串代表只放在記憶體")
	flag.Parse()

	logger := slog.New(slog.NewJSONHandler(os.Stderr, nil))
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	err := run(ctx, *addr, *data, logger)
	stop()
	if err != nil {
		logger.Error("server 停止", "err", err)
		os.Exit(1)
	}
}

func run(ctx context.Context, addr, dataPath string, logger *slog.Logger) error {
	store, err := OpenStore(dataPath)
	if err != nil {
		return err
	}
	svc := &service{store: store, now: time.Now}
	a := &api{svc: svc, logger: logger}
	srv := &http.Server{
		Addr:              addr,
		Handler:           a.routes(),
		ReadHeaderTimeout: 5 * time.Second,
		ReadTimeout:       10 * time.Second,
		WriteTimeout:      15 * time.Second,
		IdleTimeout:       60 * time.Second,
		ErrorLog:          slog.NewLogLogger(logger.Handler(), slog.LevelError),
	}

	errc := make(chan error, 1)
	go func() { errc <- srv.ListenAndServe() }()
	logger.Info("開始服務", "addr", addr, "data", dataPath)

	select {
	case err := <-errc:
		return err // 例如 port 已經被佔用
	case <-ctx.Done():
	}
	logger.Info("關機中，等進行中的請求做完")
	shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()
	if err := srv.Shutdown(shutdownCtx); err != nil {
		return err
	}
	if err := <-errc; !errors.Is(err, http.ErrServerClosed) {
		return err
	}
	return nil
}
  • 在 run 裡組合三層：Store、service、api 都在這裡建立，依賴一層一層傳進去，沒有全域變數。測試用同樣的方式組合，只是換成固定的時鐘和丟掉的 log。
  • JSON 格式的 log 寫到 stderr：每個請求一筆，有方法、路徑、狀態碼和花了多久。log 收集系統可以直接依欄位查詢，例如找出所有 status 是 500 的請求（25 章）。
  • 伺服器的逾時：http.Server 的四個逾時預設都是 0，也就是沒有上限；一個很慢的客戶端就能一直佔著連線（26 章）。
  • 關機時沒有東西要補存：每次修改都是寫好檔案才回應，Shutdown 只要等進行中的請求做完。如果資料只在記憶體裡、關機時才存檔，程式被強制結束（例如 kill -9 或停電）就會遺失資料（26 章）。

大部分的測試直接呼叫 handler，不經過網路。最後一個測試用真的 http.Client 走完整個流程：Go 1.27 起的 httptest.NewTestServer 預設用記憶體裡的網路，不用開 port：

func TestEndToEnd(t *testing.T) {
	srv := httptest.NewTestServer(t, newTestHandler(filepath.Join(t.TempDir(), "todos.json")))
	client := srv.Client()

	res, err := client.Post(srv.URL+"/todos", "application/json", strings.NewReader(`{"title": "訂便當"}`))
	if err != nil {
		t.Fatal(err)
	}
	res.Body.Close()
	if res.StatusCode != http.StatusCreated {
		t.Fatalf("POST 狀態碼 %d", res.StatusCode)
	}

	res, err = client.Get(srv.URL + res.Header.Get("Location"))
	if err != nil {
		t.Fatal(err)
	}
	defer res.Body.Close()
	var got Todo
	if err := json.UnmarshalRead(res.Body, &got); err != nil {
		t.Fatal(err)
	}
	if got.ID != 1 || got.Title != "訂便當" || !got.CreatedAt.Equal(fixedNow()) {
		t.Errorf("GET 拿到 %+v", got)
	}
}
  • 測試的層次：TestCreateValidation 只測 service 的規則；TestStoreReopen、TestStoreSaveFails 只測檔案；Example_api 測整個 handler；TestEndToEnd 再加上真的 HTTP 用戶端。越外層的測試越接近真實，但出錯時越難看出是哪一層的問題。
  • 並行的測試：TestConcurrentCreate 讓 50 個請求同時新增，重新讀檔後要剛好有 50 筆，編號是 1 到 50。go test -race 同時檢查有沒有 data race。

延伸挑戰

這些題目沒有附測試。先在對的那一層寫測試：規則寫在 service_test.go，存檔寫在 store_test.go，HTTP 的細節寫在 handler_test.go。

  1. 入門挑戰 1：搜尋標題

    讓 GET /todos?q=便當 只列出標題包含「便當」的待辦，而且可以和 done 一起用。

    提示

    把 List 的參數改成一個 struct（例如 Filter{Done *bool; Query string}），之後要加條件時就不用再改函式簽名。比對時想一想大小寫：英文的「Go」和「go」要不要算同一個？

  2. 進階挑戰 2：分頁

    待辦很多時，GET /todos?limit=20&after=40 只回傳 ID 大於 40 的前 20 筆，回應裡附上下一頁要用的 after。

    提示

    用「上一頁最後一個 ID」分頁，而不是 page=3：翻頁的途中有人新增或刪除，也不會重複或漏掉。回應要從陣列改成物件，例如 {"todos": [...], "next_after": 60}；想一想這對既有的客戶端有什麼影響。

  3. 進階挑戰 3：避免蓋掉別人的修改

    第 5 節解決了同一瞬間的衝突，但如果使用者打開編輯畫面五分鐘才送出，期間別人已經改過，他還是會蓋掉別人的修改。加上版本號：Todo 多一個 version，PATCH 要帶 If-Match 標頭，版本不同就回 412 Precondition Failed。

    提示

    GET 的回應用 ETag 標頭告訴客戶端目前的版本。檢查版本要在 Store.Update 的鎖裡做：change 函式可以回傳 error，Store 收到錯誤就不存。

  4. 進階挑戰 4：換成 SQLite

    用 28 章的 database/sql 寫一個 sqlStore，讓 service 可以選擇用檔案或資料庫。

    提示

    這時 service 才真的需要 interface：在 service.go 定義它用到的方法，兩種 Store 都實作。寫一組「合約測試」，用同樣的測試函式分別跑兩種 Store。Update 的「在鎖裡修改」要換成資料庫的交易。這個專題的根 module 沒有外部依賴，所以要在新的 module 裡做。

  5. 挑戰挑戰 5：只附加修改的紀錄

    每次修改都重寫整份檔案，資料多了就慢。改成每次修改只在檔案最後附加一行 JSON（例如 {"op":"done","id":3}），啟動時從頭重播；檔案太大時，再整理成一份完整的快照。

    提示

    附加用 os.OpenFile 加上 O_APPEND，每一行寫完都要 Sync。重播時最後一行可能只寫了一半（寫到一半當機），要能跳過它。整理快照時要擋住新的寫入，或先寫到新檔案再切換。

重點回顧

  • api 處理 HTTP、service 放規則、Store 保存資料；每一層只依賴下面那一層。
  • 驗證把全部的問題收集起來一次回報；沒有問題時回傳 nil，不是空的錯誤值。
  • PATCH 的欄位用指標，才分得出「沒傳」和「傳了零值」；只檢查有傳的欄位。
  • 讀、改、寫要在同一把鎖裡完成，不然後寫的會蓋掉先寫的；-race 抓不到這種錯。
  • 先寫好檔案（暫存檔、Sync、Rename），成功了才改記憶體；失敗時什麼都不變。
  • 存檔時連下一個編號一起存，刪掉的編號不會再被使用。
  • 時間從外面注入，跟「今天」有關的規則才測得了。
  • json/v2 的 map 預設不排序，需要固定輸出時加 Deterministic。
