並行網址檢查器

一次派好幾個人去敲門，最慢的那一家不會拖住其他人。

看圖

核心程式

func Check(ctx context.Context, urls []string, workers int, timeout time.Duration, f Fetcher) []Result {
	results := make([]Result, len(urls))
	sem := make(chan struct{}, max(workers, 1))
	var wg sync.WaitGroup
	for i, u := range urls {
		wg.Go(func() {
			select {
			case sem <- struct{}{}: // 拿到號碼牌才開始
			case <-ctx.Done():
				results[i] = Result{URL: u, Err: ctx.Err()}
				return
			}
			defer func() { <-sem }()

			reqCtx, cancel := context.WithTimeout(ctx, timeout)
			defer cancel()
			start := time.Now()
			status, err := f.Fetch(reqCtx, u)
			results[i] = Result{URL: u, Status: status, Err: err, Took: time.Since(start)}
		})
	}
	wg.Wait()
	return results
}

測試裡用假的 Fetcher 跑出的結果

OK   200 https://ok.test
FAIL 404 https://missing.test
FAIL --- https://slow.test（context deadline exceeded）

工程師筆記

  • 每個 goroutine 把結果寫進 results[i] 自己的格子，順序和輸入一樣，也不需要加鎖。
  • 每個請求用 context.WithTimeout 各自計時；外層 ctx 取消時，還沒拿到號碼牌的請求直接放棄。
  • 用 HEAD 只拿狀態碼、不下載內容；有些網站不支援 HEAD 會回 405，可以改用 GET。
  • http.Client 沒設 Timeout，因為逾時交給 context 控制；兩種方式擇一就好。
  • 有任何失敗就用非 0 結束，接在 CI 或排程裡可以直接判斷成功或失敗。
  • 測試用的 fakeFetcher 順便記錄同時執行的最大數量，用來驗證 semaphore 真的有限制住。
