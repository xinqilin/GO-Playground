專題 3 · worker pool、context、限速、重試、synctest

並行網址檢查器

便當店的網站有菜單、訂位、外送好幾個頁面，老闆想每天早上確認它們都還活著。一個一個檢查太慢；一口氣全部送出又可能把對方的伺服器打掛。這個專題寫一個工具：同時檢查、但有上限，每個請求有時間限制，失敗了等一下再試，隨時可以按 Ctrl-C 停下來。

這個專題做什麼

給它一串網址（或從標準輸入每行讀一個），它同時檢查，最後依原本的順序列出結果：

urlchecker -workers 2 -timeout 500ms https://ok.test https://missing.test https://flaky.test https://slow.test ftp://files.test
OK   200  120ms  https://ok.test
FAIL 404   80ms  https://missing.test
OK   200  750ms  https://flaky.test（試了 3 次）
FAIL ---   2.1s  https://slow.test（逾時，試了 3 次）
FAIL ---     0s  ftp://files.test（只檢查 http 和 https 網址）
共 5 個網址：2 個正常，3 個失敗，花了 2.22s

這段輸出不是在真的網路上跑的：ok.test、flaky.test 這些網址由測試裡的假 Fetcher 回應，時間由 synctest 的假時鐘計算，所以每一個數字都固定，可以逐字比對（第 7 節）。從上到下：

  • ok.test：120ms 後回 200。
  • missing.test：回 404，失敗，但不重試，因為再試幾次結果都一樣。
  • flaky.test：前兩次回 503，等一下再試，第三次成功。
  • slow.test：永遠不回應，每次都在 500ms 逾時，試了 3 次後放棄。
  • ftp://files.test：送出之前就被擋下來。

有任何一個失敗，exit code 就是 1，可以直接接在 CI 或排程裡。程式分成四個檔案：

  • fetch.go：Fetcher interface 和真正送出 HTTP 請求的 httpFetcher。
  • check.go：worker pool、逾時、限速、重試。
  • main.go：旗標、讀網址、輸出、Ctrl-C。
  • *_test.go：假的 Fetcher、synctest、golden file。

先備：14 章 goroutine、15 章 channel、18 章 context、19 章並行模式、27 章 HTTP 用戶端、30 章的 synctest。

1. 把網路藏在 interface 後面

type Fetcher interface {
	Fetch(ctx context.Context, rawURL string) (int, error)
}

type httpFetcher struct{ client *http.Client }

func (f httpFetcher) Fetch(ctx context.Context, rawURL string) (int, error) {
	status, err := f.do(ctx, http.MethodHead, rawURL)
	if err == nil && status == http.StatusMethodNotAllowed {
		return f.do(ctx, http.MethodGet, rawURL)
	}
	return status, err
}

func (f httpFetcher) do(ctx context.Context, method, rawURL string) (int, error) {
	req, err := http.NewRequestWithContext(ctx, method, rawURL, nil)
	if err != nil {
		return 0, err
	}
	resp, err := f.client.Do(req)
	if err != nil {
		return 0, err
	}
	resp.Body.Close() // 只需要狀態碼，GET 的內容不讀，直接關掉
	return resp.StatusCode, nil
}
  • 小的 interface：Fetcher 只有一個方法，剛好是 Check 需要的，不多也不少。方法越少，假的版本越好寫（10 章）。
  • HEAD 只拿標頭：檢查網址只需要狀態碼，HEAD 不下載內容。有些伺服器不接受 HEAD，回 405 Method Not Allowed，這時改用 GET。
  • Body 一定要關：就算不讀內容，也要 Close，否則底下的連線不會釋放（27 章）。這裡不讀 GET 的內容就關掉，連線可能沒辦法重複使用；檢查工具送的請求不多，這是可以接受的取捨。
  • http.Client 沒有設 Timeout：逾時由 ctx 控制（第 3 節）。轉址則用預設的規則，最多跟著轉 10 次，回報最後一個狀態碼。

httpFetcher 本身也要測，但 sandbox 和 CI 不一定能開 port。27 章的做法是換掉 Client 的 Transport，請求根本不會送到網路上：

type roundTripFunc func(*http.Request) (*http.Response, error)

func (f roundTripFunc) RoundTrip(r *http.Request) (*http.Response, error) { return f(r) }

TestHTTPFetcher 用它檢查三種情況：HEAD 就夠了、404 不要改用 GET、405 才改用 GET，而且每一個 Body 都被關掉。送出請求前，先擋掉明顯不對的網址，不必浪費一次請求：

func validateURL(rawURL string) error {
	u, err := url.Parse(rawURL)
	if err != nil {
		return err
	}
	if u.Scheme != "http" && u.Scheme != "https" {
		return errScheme
	}
	if u.Host == "" {
		return errors.New("網址裡沒有主機名稱")
	}
	return nil
}

2. worker pool

type Config struct {
	Workers   int           // 同時最多幾個請求，至少 1
	Timeout   time.Duration // 每一次請求最多等多久
	PerSecond int           // 每秒最多送出幾個請求；0 是不限制
	Retries   int           // 失敗後最多再試幾次
	Backoff   time.Duration // 第一次重試前等多久，之後每次加倍
}

type Result struct {
	URL      string
	Status   int           // HTTP 狀態碼；沒有收到回應時是 0
	Err      error         // 沒有收到回應的原因
	Attempts int           // 實際送出幾次請求
	Took     time.Duration // 包含等待限速和重試的時間
}

func (r Result) OK() bool { return r.Err == nil && r.Status < 400 }

func Check(ctx context.Context, urls []string, cfg Config, f Fetcher) []Result {
	var tick <-chan time.Time // nil 代表不限速
	if cfg.PerSecond > 0 {
		t := time.NewTicker(time.Second / time.Duration(cfg.PerSecond))
		defer t.Stop()
		tick = t.C
	}

	results := make([]Result, len(urls))
	jobs := make(chan int)
	var wg sync.WaitGroup
	for range max(cfg.Workers, 1) {
		wg.Go(func() {
			for i := range jobs {
				results[i] = checkOne(ctx, urls[i], cfg, f, tick)
			}
		})
	}
	for i := range urls {
		jobs <- i
	}
	close(jobs)
	wg.Wait()
	return results
}
  • 固定數量的 goroutine：不管有幾個網址，都只開 Workers 個 goroutine。舊版是每個網址開一個 goroutine，再用 buffered channel 當號碼牌限制同時的數量（19 章的 semaphore）。兩種都能限制同時的請求數；worker pool 的 goroutine 數量固定，網址有一萬個時也一樣。
  • 不需要鎖：每個 index 只會被一個 worker 拿到，不同的 results[i] 是不同的記憶體位置，同時寫不會互相干擾。wg.Wait() 回傳之後，所有的寫入都已經完成，主 goroutine 可以安全地讀（17 章）。go test -race 會檢查這件事。
  • unbuffered 的 jobs：派工的迴圈要等到有 worker 空下來才送得出去，自然不會一次塞一大堆工作。全部送完再 close，worker 的 for range 就會結束。
  • wg.Go（Go 1.25 起）把 Add(1)、go 和 defer Done() 合成一步，不會忘記其中一個（14 章）。

TestCheckWorkers 用 20 個網址、3 個 worker 驗證：同時最多 3 個請求，每個 120ms，分 7 輪做完，總共剛好 840ms。「剛好」是因為用了假的時鐘，第 7 節再說明。

3. 每一次請求的逾時

func fetchOnce(ctx context.Context, rawURL string, timeout time.Duration, f Fetcher) (int, error) {
	ctx, cancel := context.WithTimeout(ctx, timeout)
	defer cancel()
	return f.Fetch(ctx, rawURL)
}
  • 每一次請求一個逾時，不是每個網址一個：重試的時候，新的一次又有完整的 500ms。如果整個網址共用一個逾時，第一次就把時間用完，後面的重試根本來不及。
  • defer cancel()：請求提早完成時，計時器也要釋放。go vet 的 lostcancel 會檢查有沒有忘記呼叫 cancel。
  • ctx 要一路傳下去：httpFetcher 用 NewRequestWithContext 把 ctx 交給請求，逾時一到，正在等的連線就會被中斷。傳了 ctx 卻沒有往下傳，逾時就沒有作用（18 章）。

逾時和取消的錯誤會被一層一層包起來，例如 http.Client 回傳的是 Head "https://slow.test": context deadline exceeded。用 errors.Is 判斷，而不是比對字串（11 章）：

func describe(err error) string {
	switch {
	case errors.Is(err, context.DeadlineExceeded):
		return "逾時"
	case errors.Is(err, context.Canceled):
		return "已取消"
	}
	return err.Error()
}

4. 限速：節拍器

Check 開頭建立一個 time.Ticker，所有 worker 共用它的 channel；每次送出請求前，先拿走一拍：

func waitTurn(ctx context.Context, tick <-chan time.Time) error {
	if tick == nil {
		return ctx.Err()
	}
	select {
	case <-tick:
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}
}
  • 共用一個 channel：不管有幾個 worker，每一拍只有一個人拿得到，所以整體的速度不會超過設定（19 章）。
  • 不限速就不等：-rate 0 時 tick 是 nil。從 nil channel 接收會永遠卡住（15 章），所以 waitTurn 先檢查 nil；但還是回傳 ctx.Err()，已經取消的檢查就不再送出請求。
  • 拍子不會累積：沒人拿的拍子會被丟掉，閒置一陣子之後，不會突然一口氣送出一大批請求。
  • defer t.Stop()：Check 結束時停掉節拍器。

限速是不是真的照節拍送出？測試記錄每個請求開始的時間，精確地和 100、200、300、400、500ms 比較：

func TestCheckRate(t *testing.T) {
	synctest.Test(t, func(t *testing.T) {
		urls := slices.Repeat([]string{"https://ok.test"}, 5)
		f := newFake()
		start := time.Now()
		Check(t.Context(), urls, Config{Workers: 5, Timeout: time.Second, PerSecond: 10}, f)

		var got []time.Duration
		for _, s := range f.starts {
			got = append(got, s.Sub(start))
		}
		want := []time.Duration{100 * time.Millisecond, 200 * time.Millisecond,
			300 * time.Millisecond, 400 * time.Millisecond, 500 * time.Millisecond}
		if !slices.Equal(got, want) {
			t.Errorf("請求開始的時間 = %v，想要 %v", got, want)
		}
	})
}

5. 退避重試

func checkOne(ctx context.Context, rawURL string, cfg Config, f Fetcher, tick <-chan time.Time) Result {
	r := Result{URL: rawURL}
	if err := validateURL(rawURL); err != nil {
		r.Err = err
		return r
	}
	start := time.Now()
	backoff := cfg.Backoff
	for {
		if err := waitTurn(ctx, tick); err != nil {
			r.Status, r.Err = 0, err
			break
		}
		r.Attempts++
		r.Status, r.Err = fetchOnce(ctx, rawURL, cfg.Timeout, f)
		if r.Attempts > cfg.Retries || !retryable(ctx, r) {
			break
		}
		if err := sleep(ctx, backoff); err != nil {
			r.Status, r.Err = 0, err
			break
		}
		backoff *= 2
	}
	r.Took = time.Since(start)
	return r
}

func retryable(ctx context.Context, r Result) bool {
	if ctx.Err() != nil {
		return false
	}
	return r.Err != nil || r.Status == http.StatusTooManyRequests || r.Status >= 500
}

func sleep(ctx context.Context, d time.Duration) error {
	t := time.NewTimer(d)
	defer t.Stop()
	select {
	case <-t.C:
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}
}
  • 什麼值得重試：5xx 和 429 Too Many Requests 代表伺服器暫時有問題；沒有收到回應（逾時、連線失敗）也可能下一次就好。404 這種 4xx 是請求本身有問題，重試幾次都一樣。
  • 簡化之處：任何錯誤都重試，連 DNS 查不到主機這種不會自己好的錯誤也是。實務上還會加上隨機的抖動（jitter），避免很多用戶端同時重試（27 章）。
  • 只重試安全的請求：HEAD 和 GET 重送不會改變伺服器的狀態。POST 這類請求重送，可能訂了兩次便當（27 章）。
  • 等待也要能取消：sleep 用 select 同時等計時器和 ctx.Done()。如果寫成 time.Sleep，按了 Ctrl-C 還要等退避時間結束才會停。
  • 取消了就不重試：retryable 先看 ctx.Err()。整個檢查已經被取消時，這一次失敗正是因為取消，再試也沒有意義。

TestCheckRetry 是一張表：不同的 Retries 下，狀態碼、錯誤、送出幾次、花了多久，每一格都是精確的值，例如 flaky.test 允許重試 2 次時，剛好 750ms、送出 3 次。

6. Ctrl-C：取消整個檢查

func main() {
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt)
	context.AfterFunc(ctx, stop) // 第一次 Ctrl-C 之後恢復預設行為：再按一次就直接結束

	f := httpFetcher{client: &http.Client{}} // 逾時由 context 控制
	code := run(ctx, os.Args[1:], os.Stdin, os.Stdout, os.Stderr, f)
	stop()
	os.Exit(code)
}
  • signal.NotifyContext：收到 Ctrl-C（os.Interrupt）時取消回傳的 ctx（21 章）。這個 ctx 是整棵 context 樹的根，正在等的請求、退避中的 sleep、還在等節拍的 worker 都會馬上結束。
  • context.AfterFunc(ctx, stop)：第一次 Ctrl-C 取消 ctx 的同時呼叫 stop()，停止攔截訊號。收尾卡住時再按一次，就是預設的行為，直接結束程式。沒有這一行的話，stop() 要等 run 回傳才會執行，在那之前再按幾次 Ctrl-C 都會被攔下來。
  • os.Exit 不會執行 defer，所以沒有收到訊號、正常結束時的 stop() 寫在 os.Exit 之前，而不是 defer stop()。

取消之後，派工的迴圈仍然會把剩下的 index 送完，但 worker 拿到之後，waitTurn 立刻回傳 ctx.Err()，一個請求都不會送出：

func TestCheckCanceled(t *testing.T) {
	synctest.Test(t, func(t *testing.T) {
		ctx, cancel := context.WithCancel(t.Context())
		defer cancel()
		time.AfterFunc(300*time.Millisecond, cancel)

		urls := []string{"https://slow.test", "https://ok.test", "https://ok.test"}
		cfg := Config{Workers: 1, Timeout: time.Second, Retries: 2}
		start := time.Now()
		results := Check(ctx, urls, cfg, newFake())
		if took := time.Since(start); took != 300*time.Millisecond {
			t.Errorf("花了 %v，想要 300ms", took)
		}
		for i, r := range results {
			wantAttempts := 0
			if i == 0 {
				wantAttempts = 1
			}
			if !errors.Is(r.Err, context.Canceled) || r.Attempts != wantAttempts {
				t.Errorf("results[%d]：錯誤 %v、送了 %d 次；想要 Canceled、%d 次", i, r.Err, r.Attempts, wantAttempts)
			}
		}
	})
}

7. 假的時鐘：synctest 與 golden file

假的 Fetcher 用計時器模擬每個網址的延遲，同時記錄同時有幾個請求、每個請求什麼時候開始：

type fakeFetcher struct {
	mu      sync.Mutex
	calls   map[string]int // 每個網址被請求了幾次
	running int            // 現在有幾個請求在進行
	peak    int            // running 曾經到過的最大值
	starts  []time.Time    // 每個請求開始的時間
}

func (f *fakeFetcher) Fetch(ctx context.Context, rawURL string) (int, error) {
	f.mu.Lock()
	f.calls[rawURL]++
	n := f.calls[rawURL]
	f.running++
	f.peak = max(f.peak, f.running)
	f.starts = append(f.starts, time.Now())
	f.mu.Unlock()
	defer func() {
		f.mu.Lock()
		f.running--
		f.mu.Unlock()
	}()

	switch rawURL {
	case "https://ok.test":
		return respond(ctx, 120*time.Millisecond, 200)
	case "https://missing.test":
		return respond(ctx, 80*time.Millisecond, 404)
	case "https://flaky.test": // 前兩次 503，第三次才成功
		if n < 3 {
			return respond(ctx, 50*time.Millisecond, 503)
		}
		return respond(ctx, 50*time.Millisecond, 200)
	}
	<-ctx.Done() // 其他網址永遠不回應，直到逾時或被取消
	return 0, ctx.Err()
}

func respond(ctx context.Context, d time.Duration, status int) (int, error) {
	select {
	case <-time.After(d):
		return status, nil
	case <-ctx.Done():
		return 0, ctx.Err()
	}
}
  • 用計時器，不用真的網路：時鐘只有在 goroutine 全部「確實卡住」時才會跳。卡在網路 I/O 不算，因為事件可能從泡泡外面來；所以這個測試需要假的 Fetcher，不能接真的伺服器。
  • Mutex 只拿一下：fakeFetcher 用 Mutex 保護計數，鎖住的時間很短，不會影響時鐘。
  • 計時器要在泡泡裡建立：Check 裡的 Ticker、fetchOnce 裡的逾時、respond 裡的 time.After 都在 synctest.Test 的函式裡建立，才會用假的時鐘。

本頁開頭的輸出就是這個測試產生的。它跑完整支程式，把輸出和 testdata/report.golden 逐字比對；要更新時加上 -update（30 章）：

func TestReport(t *testing.T) {
	synctest.Test(t, func(t *testing.T) {
		args := []string{"-workers", "2", "-timeout", "500ms",
			"https://ok.test", "https://missing.test", "https://flaky.test", "https://slow.test", "ftp://files.test"}
		var out bytes.Buffer
		if code := run(t.Context(), args, nil, &out, &out, newFake()); code != 1 {
			t.Errorf("exit code = %d，想要 1", code)
		}

		golden := filepath.Join("testdata", "report.golden")
		if *update {
			if err := os.WriteFile(golden, out.Bytes(), 0o644); err != nil {
				t.Fatal(err)
			}
		}
		want, err := os.ReadFile(golden)
		if err != nil {
			t.Fatalf("%v（第一次請加 -update 產生）", err)
		}
		if got := out.String(); got != string(want) {
			t.Errorf("輸出和 %s 不一樣：\n--- got\n%s--- want\n%s", golden, got, want)
		}
	})
}
  • golden file 鎖住的是整個輸出的樣子：欄位對齊、括號裡的說明、合計那一行。改了 formatResult，測試就會失敗，用 -update 重新產生之後，再用 git diff 確認改變是不是你要的。
  • golden file 不證明數字是對的，只證明它沒變。數字本身由 TestCheckWorkers、TestCheckRate、TestCheckRetry 各自用算得出來的值驗證。

8. 命令列介面與 exit code

func run(ctx context.Context, args []string, stdin io.Reader, stdout, stderr io.Writer, f Fetcher) int {
	fs := flag.NewFlagSet("urlchecker", flag.ContinueOnError)
	fs.SetOutput(stderr)
	var cfg Config
	fs.IntVar(&cfg.Workers, "workers", 4, "同時最多幾個請求")
	fs.DurationVar(&cfg.Timeout, "timeout", 5*time.Second, "每一次請求最多等多久")
	fs.IntVar(&cfg.PerSecond, "rate", 0, "每秒最多送出幾個請求，0 是不限制")
	fs.IntVar(&cfg.Retries, "retries", 2, "失敗後最多再試幾次")
	fs.DurationVar(&cfg.Backoff, "backoff", 200*time.Millisecond, "第一次重試前等多久，之後每次加倍")
	if err := fs.Parse(args); err != nil {
		return 2
	}
	if cfg.Workers < 1 || cfg.Timeout <= 0 || cfg.PerSecond < 0 || cfg.Retries < 0 || cfg.Backoff < 0 {
		fmt.Fprintln(stderr, "urlchecker：-workers 至少是 1，-timeout 要大於 0，其他數值不能是負數")
		return 2
	}

	urls := fs.Args()
	if len(urls) == 0 {
		var err error
		if urls, err = readURLs(stdin); err != nil {
			fmt.Fprintf(stderr, "urlchecker：讀取網址：%v\n", err)
			return 2
		}
	}
	if len(urls) == 0 {
		fmt.Fprintln(stderr, "用法：urlchecker [旗標] URL...（或從標準輸入每行讀一個網址）")
		return 2
	}

	start := time.Now()
	results := Check(ctx, urls, cfg, f)
	ok := 0
	for _, r := range results {
		fmt.Fprintln(stdout, formatResult(r))
		if r.OK() {
			ok++
		}
	}
	fmt.Fprintf(stdout, "共 %d 個網址：%d 個正常，%d 個失敗，花了 %v\n",
		len(results), ok, len(results)-ok, time.Since(start).Round(time.Millisecond))
	if ok < len(results) {
		return 1
	}
	return 0
}
  • 參數都從外面傳進來：ctx、args、stdin、stdout、stderr 和 Fetcher。main 傳真的，測試傳假的，run 本身不知道差別（21 章）。
  • 先檢查旗標的值：-timeout 0 會讓每個請求一送出就逾時，-workers 0 則沒有意義。與其照做或偷偷改掉使用者的設定，不如在開始之前用 exit code 2 說清楚。
  • exit code：0 全部正常、1 有網址失敗、2 用法錯誤。CI 的腳本只要看 exit code 就知道要不要發警報。TestRunExitCodes 把每一種情況都跑過一次。

	sc := bufio.NewScanner(r)
	for sc.Scan() {
		s := strings.TrimSpace(sc.Text())
		if s != "" && !strings.HasPrefix(s, "#") {

		}
	}
	return urls, sc.Err()
}

func formatResult(r Result) string {
	mark, code := "OK", strconv.Itoa(r.Status)

		mark = "FAIL"
	}
	if r.Err != nil {

延伸挑戰

這些題目沒有附測試。用假的 Fetcher 和 synctest 先寫出你期望的時間，再改程式。

  1. 入門挑戰 1：標出慢的網址

    加一個 -slow 旗標（例如 1s）：成功但花的時間超過它的網址，標記從 OK 改成 SLOW，但不算失敗。

    提示

    Result 已經有 Took。改 formatResult 時要決定 SLOW 的判斷要放在 Result（例如一個方法）還是交給呼叫端；用 TestReport 的 golden file 看輸出的改變。

  2. 進階挑戰 2：不重試永久性的錯誤

    讓 retryable 不再重試「不會自己好」的錯誤，例如 DNS 查不到主機（*net.DNSError 的 IsNotFound 是 true）。

    提示

    用 errors.As（或 Go 1.26 起的 errors.AsType）取出 *net.DNSError。在假的 Fetcher 加一個網址，直接回傳 &net.DNSError{IsNotFound: true}，測試它只送出一次。

  3. 進階挑戰 3：照 Retry-After 等待

    伺服器回 429 或 503 時常帶 Retry-After 標頭（秒數），告訴你多久之後再來。有這個標頭時，用它取代退避的時間。

    提示

    Fetcher 現在只回傳狀態碼，需要改成回傳一個小的 struct（狀態碼和 Retry-After）。想一想：改 interface 會影響哪些地方？假的 Fetcher 和 roundTripFunc 的測試都要跟著改。

  4. 進階挑戰 4：每個主機分開限速

    -rate 改成「對每個主機」每秒最多幾個請求：檢查 shop.test 的十個頁面要排隊，但不同的主機互不影響。

    提示

    用 map[string]*time.Ticker，以 url.Parse 取出的 Host 當 key；這個 map 會被多個 worker 同時讀寫，要用 Mutex 保護（17 章）。測試兩個主機交錯時，各自的請求開始時間。

  5. 挑戰挑戰 5：第一個失敗就停

    加一個 -failfast 旗標：任何一個網址失敗，就取消其他還沒完成的檢查，並在輸出裡說明是因為哪一個網址而停止。

    提示

    在 Check 裡用 context.WithCancelCause 建立子 ctx，失敗的 worker 呼叫 cancel(fmt.Errorf("%s 失敗", url))；其他結果用 context.Cause(ctx) 取出原因（18 章）。小心：被取消的網址本身也是「失敗」，不要讓它們再觸發一次取消。

重點回顧

  • 把外部的依賴（網路）藏在小的 interface 後面，邏輯就能在沒有網路的地方測試。
  • worker pool 用固定數量的 goroutine；channel 傳 index，結果寫進 results[i]，順序不變也不需要鎖。
  • 每一次請求一個 WithTimeout 的子 context，逾時只影響自己；ctx 要一路傳到 NewRequestWithContext。
  • 多個 worker 共用一個 Ticker 的 channel，就是整體的限速。
  • 只重試暫時性的失敗，等待時間加倍，而且等待本身也要能被取消。
  • signal.NotifyContext 讓 Ctrl-C 變成 context 的取消；os.Exit 不會執行 defer。
  • synctest 的假時鐘讓並行和時間的測試又快又精確；golden file 鎖住整個輸出。
